# Stopped and multi-volume recovery (#801)

Status: implementation approved; runtime verification belongs to CI.

Existing backups default to powerPolicy=preserve and volumePolicy=primary-only. Opt-in stop-copy-restart uses the existing shared lifecycle owner and graceful stop sequence, never writes spec.suspend, and requires observed zero replicas and all source writers drained. all-data captures primary data, declared data extras, and active separate loader/mod claims in one Restic snapshot. Rebuildable extras are reported prerequisites; unclassified claims reject admission. CSI rejects either new policy and remains a single primary volume snapshot with no cross-volume atomicity.

The owner on GameServer durably records admitted power intent, original pod and stop stage before stopping. Existing persisted preparation/copy budgets bound waiting and copying. Stop failure, copy failure and cancellation revoke and drain workers before releasing the fence. An orphan owner preserves stop debt through recovery; malformed provenance fails closed with visible RecoveryIntervention. Release never overwrites current suspend, idle or restart intent. Automatic resumption requires admitted running intent, unchanged power intent and completed drain; user changes take precedence after cleanup.

Each new all-data manifest pins template/version provenance, claim names and UIDs, logical identities, original mount paths and disjoint /volumes/<identity> roots. Claim mounts in the worker are read-only. Primary-only keeps /data and older manifests remain legacy, without invented metadata.

Restore validates a manifest against an existing target before claiming ownership (which suspends), provisioning or creating a writer. It persists target claim UIDs/layout and revalidates both before Job creation and after the worker mounts become ready, immediately before Pod-bound authorization. PVC protection plus the final live UID check prevents name replacement while the mounted worker remains live. Missing/replaced required claims, changed mount paths/provenance, duplicate/traversing roots and ambiguous mappings fail visibly. A same-server restore requires original claim UIDs; a different existing server maps by exact logical identity and compatible template/version, pinning target UIDs. Excluded rebuildable claims may be absent: their logical declarations remain pinned, and the manifest reports reconstruction prerequisites. Restore never mounts or writes them. Only validated included roots receive --include and writable mounts. V2 restore uses lifecycle ownership to stop without changing spec.suspend; successful cleanup preserves current power intent, while failed or cancelled writes retain the established suspended safety behavior. Legacy primary-only restore retains /data behavior.

The existing coverage rows expose included/excluded claims and prerequisites; API types gain policy and manifest fields. No new dashboard controls or layout are introduced.
