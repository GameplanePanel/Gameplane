# Decisions for per-server access

D1 through D6 are decided. The three approved base server roles are **Viewer**, **Power User** and **Administrator**. The legacy collaborator mapping still requires verification against existing behavior. [Spec](spec.md) · [Implementation plan](plan.md)

## D1 · Editing a base role

**Decided.** A server role has one stable ID and one current permission set. Saving an edit changes what every assignee receives on their next request, across direct assignments and matching cluster or namespace grants. An unreachable cluster does not delay the edit. Existing streams recheck as specified in FR-09. The editor previews who gains or loses access before the single save. Count committed bindings and direct assignments in panel SQL. For inherited access, count distinct affected servers and show template matches from the available workload inventory. Label unavailable or last-known counts separately. Always show the impact preview, including future scope coverage. An offline inventory does not prevent saving after that review. There is no role revision, assignment upgrade or per-user opt-out from the edit. Audit the before/after action delta. An ordinary one-off permission selection is a distinct grant, and any independent source that still grants an action appears in effective access.

## D2 · Who can delegate

**Decided.** Delegation has its own permissions. Holding a gameplay, file or settings permission alone never lets someone give it to another person. Assign the following independently on a target server.

| Permission | What the holder may do |
| --- | --- |
| `members.view` | See that server's member roster and the grant details they are authorized to inspect. |
| `members.invite` | Add a new direct assignment for an existing account on that server. This does not provision a panel account or overwrite an existing assignment. |
| `members.edit` | Change an existing direct assignment within the actor's transferable rights. Editing a reusable role definition remains a panel-admin operation. |
| `members.remove` | Revoke an existing direct assignment within the actor's authority. Account deletion and removal of inherited fleet bindings have their own administrative paths. |

A delegated mutation requires the applicable membership permission and authority over the actions and selectors being assigned or affected. Checking one does not imply granting the other. Compare the full stored grant, including dormant actions. For example, a shift lead holding Invite and Kick on Match 1 can add a kick-only referee there. The lead cannot assign Ban, remove an existing referee, grant themselves a new permission or appoint another membership manager. Invite alone permits the minimal exact-account workflow without revealing the entire member roster or account directory.

The server owner and an admin authorized for the target may appoint membership managers. Owners can delegate only actions they hold with equal or narrower selectors. Delegates cannot edit or remove a superior assignment, grant membership-management powers onward, change inherited grants or manage Blocks. A panel admin editing a shared role later authorizes that change for every assignee. The edit preview includes people originally assigned by delegates and those who inherit the role through a scoped binding. Losing a delegation permission prevents subsequent membership changes and leaves independently authorized assignments in place.

## D3 · Invitations and migration order

**Decided.** The inviter must choose the access. Start manual general-account and server invitations with nothing selected. Creating an account requires selecting its panel access explicitly, including **Assigned servers only** if desired. For a direct server assignment, select one or more applicable live roles or choose **Custom permissions** and pick at least one action. For a cluster or namespace assignment, select a scoped role whose definition has an explicit base server role and review its scope-wide effects before saving. Editing an existing person's server access leaves their account role alone. Show **Assigned servers only** as an available account-level choice, never as a preselection. A blank form or omitted grant in an invitation request issues no grant and returns a validation error before creating an account. Keep the configured SSO first-sign-in flow and its independently configured fallback.

**Shipped roles and migration.** Viewer grants server status and events. Power User adds live and historical logs plus start, stop, restart and wake. Administrator includes all Power User permissions and adds viewing the player roster, kicking players, listing backups and creating backups. Ownership, delegation and the built-in primary panel admin keep their own authority. These approved sets are specified in the [permission catalog](contracts/permission-catalog.md). Next, verify legacy collaborator access against the old routes and preserve that contribution through its own migration-only grant.

## D4 · Where assignments live

**Decided.** Panel SQL is the source of truth for direct server memberships, live role definitions, scoped bindings and admin Blocks. Direct membership identifies the account, registered cluster, namespace, server name and immutable GameServer UID. Store each scoped binding once. Evaluate it against the trusted cluster, namespace and effective GameTemplate when listing or authorizing a server. Verify the live UID before workload access. A same-name replacement loses the previous direct membership and inherits the grants that match its own scope and template. Kubernetes continues to identify the live workload and its owner.

A panel admin can revoke a known, converted assignment and record the audit entry in one transaction while the cluster is offline. Creating a grant or acting as an owner or delegate requires verified target and authority. During legacy conversion, keep a durable record for each imported UID even after its last member is removed. After a database restore, reconcile subsequent direct and scoped revocations, role edits and Blocks against independent records before reopening affected scopes. [Migration and recovery](plan.md#7--convert-existing-collaborators)

## D5 · Panel, cluster and server access

**Decided.** Use three layers. The primary panel role governs the installation. A cluster or namespace role defines both infrastructure permissions in that scope and the server permissions every member inherits there. Direct assignments and ownership apply to individual server UIDs.

| Layer | Where an admin works | Example |
| --- | --- | --- |
| Panel access | **Users & RBAC** sets the primary role or shows its OIDC/Helm source. The built-in primary panel admin manages the reusable server-role library. | Set the default language, manage accounts or explicitly choose **Assigned servers only** for zero permissions from the primary role. |
| Cluster / namespace access | **Cluster → Roles & permissions** defines the scoped role and assigns it to accounts. **Users → Person → Access** shows the same binding. | A Tournament staff role grants `servers:create` in `eu/tournaments`, Viewer on every server there and Match referee on matching CS2 servers. |
| Individual server access | **Server → Access** shows inherited sources and lets an authorized inviter choose named roles or custom permissions directly for one UID. | Give Alex Power User directly on Match A. Removing Alex's Tournament staff grant leaves that direct assignment intact. |

Every new cluster or namespace role requires exactly one explicitly selected base server role from **Viewer**, **Power User** or **Administrator**, even when its only infrastructure duty is provisioning or inventory. A cluster binding covers all existing and future servers in its managed namespaces. A namespace binding covers all existing and future servers in that exact cluster and namespace. Every member receives the base on each such server. Any applicable admin Block still takes precedence. A bulk direct assignment remains available for a fixed set of existing UIDs.

GameTemplate authors may declare server-scoped permissions tied to supported game actions or settings and publish named role presets. The panel admin reviews their mappings and live definitions. The scoped role can reference additional approved roles by trusted template and stable role ID. On a matching server these add to the base. An unlisted or newly installed template receives the common base. A template cannot define panel or infrastructure privileges, grant membership, or bypass the canonical permission for an action. Publishing a new template or an expanded preset never silently assigns new permissions. Approved changes to a live role follow D1. When a server changes template, re-evaluate its applicable additions.

Always show an impact preview for scoped assignments, edits and removals in either view. Identify the person or affected members, exact scope, base, and each template addition. Show the distinct number of current servers covered, the matching count per template, and the effect on future servers. Show sources that survive removal where the actor may inspect them. Zero current matches still requires previewing future coverage. For example, granting Tournament staff for a namespace with two CS2 servers and one Valheim server shows Viewer on all three, Match referee on two, and the same rules for future servers there. Mark offline inventory as last known or unavailable. The count describes observed impact and never limits which servers inherit the grant.

Cluster discovery, inventory access and server delegation alone do not authorize binding changes. Check the grantor's authority over the account, role, cluster and namespace. Keep a local workload-cluster grant on combined installations distinct from the logical primary panel binding. Preserve the primary role across edits to workload grants, exact namespace eligibility, and restrictions on central/wildcard permissions for whole-cluster workload grants. Node inventory still requires eligible whole-cluster authority. Existing OIDC/Helm, provisioning and scoped grants retain their original scope and effective permissions on upgrade. Converting an old inventory-only grant into an inheriting role requires explicit base selection and the grant preview before granting new workload access. [Existing panel bindings](../../docs/multicluster-ui.md#user-access) · [Panel permission catalog](../../api/internal/rbac/catalog.go)

## D6 · Explicit exceptions to inherited access

**Decided.** Implement a scoped **Block** managed exclusively by the built-in primary panel admin. An owner, delegated membership manager, fleet-role editor or target-only admin cannot create, change or remove one. Applicable subjects are a user or role. The target is one server UID or an exact cluster/namespace. A rule names the ordinary workload action and applicable selectors, such as a networking field or file subtree. No existing grant is converted into a Block.

A user Block matches that account. A role Block matches an account only where it holds that role on the target. Holding the role on a sibling server is insufficient. Once the subject, target, action and selectors match, the Block wins over every direct or inherited allow for that action. Removing the Block reveals whatever access remains. It never manufactures a grant. Keep platform/credential limits and the built-in panel admin recovery path. Explain the affected action, scope and source to authorized viewers, and audit who imposed or removed it. Validate the same decision on fleet reads, detail, individual/compound writes, live streams and MCP reads. A namespace Block restricts matching actions throughout that cluster/namespace and grants no server membership.

For example, Alex inherits Power User throughout `eu/tournaments` and can also read logs directly on Final. A panel admin's Block on Alex reading logs on Final suppresses both allows there. The scope grant still permits logs on Match A. Removing the Block restores log access on Final if another grant allows it. [Reference comparison](reference-panels.md)
