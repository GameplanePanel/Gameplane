# Decisions for per-server access

The following decisions define the three access layers, optional server-role inheritance, role lifecycle and reuse of template permission approvals. [Spec](spec.md) · [Implementation plan](plan.md)

## Decisions before implementation

- **Reusable approvals.** One panel admin approval covers matching installations of the same verified module across this panel’s clusters. [Approval decision](#decided--sharing-template-approvals-across-installations)
- **Role availability.** Viewer, Power User, Operator and Administrator are permanent and editable. Panel admins can retire custom roles. [Role lifecycle](#d1--editing-a-base-role) · [Scope inheritance](#d5--panel-cluster-and-server-access)
- **Optional inheritance.** An infrastructure-only cluster or namespace role is valid. If server roles are selected, each applies only to matching servers in that scope. A direct assignment still targets one server UID.

## D1 · Editing a base role

**Decided.** A server role has one stable ID and one current permission set. Saving an edit changes what every assignee receives on their next request, across direct assignments and matching cluster or namespace grants. An unreachable cluster does not delay the edit. Existing streams recheck as specified in FR-09. The editor previews who gains or loses access before the single save. Count committed bindings and direct assignments in panel SQL. For inherited access, count distinct affected servers and show template matches from the available workload inventory. Label unavailable or last-known counts separately. Always show the impact preview, including future scope coverage. An offline inventory does not prevent saving after that review. There is no role revision, assignment upgrade or per-user opt-out from the edit. Audit the before/after action delta. An ordinary one-off permission selection is a distinct grant, and any independent source that still grants an action appears in effective access.

The four shipped roles always remain available to select and edit. The primary panel admin can retire custom roles. Existing direct and scoped assignees keep the live role, including on future matching servers reached through an existing binding. Retirement closes new direct and indirect assignments. Remove or replace a retired reference before assigning its scoped definition to another person. A referenced role cannot be deleted.

## D2 · Who can delegate

**Decided.** Delegation has its own permissions. Holding a gameplay, file or settings permission alone never lets someone give it to another person. Select each duty separately on a target server. Each mutation also requires effective `members.view` there.

| Permission | What the holder may do |
| --- | --- |
| `members.view` | See that server's member roster and the grant details they are authorized to inspect. |
| `members.invite` | Add a new direct assignment for an existing account on that server. This does not provision a panel account or overwrite an existing assignment. |
| `members.edit` | Change an existing direct assignment within the actor's transferable rights. Editing a reusable role definition remains a panel-admin operation. |
| `members.remove` | Revoke an existing direct assignment within the actor's authority. Account deletion and removal of inherited fleet bindings have their own administrative paths. |

A delegated change requires `members.view` on the target server, the specific invite, edit or remove action, and authority over the affected rights and selectors, including dormant actions. For example, a shift lead who can view members, invite, see the player roster and kick on Match 1 can grant that moderation duty there. They cannot grant Ban, remove members, promote themselves or appoint another membership manager. The target-scoped exact-account lookup keeps the global account directory private.

The server owner and an admin authorized for the target may appoint membership managers. Owners can delegate only actions they hold with equal or narrower selectors. Delegates cannot edit or remove a superior assignment, grant membership-management powers onward, change inherited grants or manage Blocks. A panel admin editing a shared role later authorizes that change for every assignee. The edit preview includes people originally assigned by delegates and those who inherit the role through a scoped binding. Losing a delegation permission prevents subsequent membership changes and leaves independently authorized assignments in place.

A workload-scope manager receives `bindings:assign`, `bindings:revoke` and `bindings:read` independently for a registered cluster or exact namespace. Creating or revoking a binding also requires effective `bindings:read` on the same scope and `scopeRoles:read` on the affected definitions. Switching an assignment checks all three keys. A scoped role author has a separate definition permission. On a shared definition edit, check the full effective delegation ceiling in every affected scope, including dormant rights and future coverage. Keep panel-account role assignment separate from both workflows. [Panel and workload catalog](contracts/fleet-permissions.md)

## D3 · Invitations and beta access reset

**Decided.** The inviter must choose the access. Start manual general-account and server invitations with nothing selected. Creating an account requires selecting its panel access explicitly, including **Assigned servers only** if desired. For a direct server assignment, select one or more applicable live roles or choose **Custom permissions** and pick at least one action. For a cluster or namespace assignment, select a scoped role and review its infrastructure permissions and any inherited server roles before saving. Its inheritance may be empty. Editing an existing person's server access leaves their account role alone. Show **Assigned servers only** as an available account-level choice, never as a preselection. An account invitation with no panel-access choice or a direct server invitation with no role or custom action fails validation before creating an account or membership. Keep the configured SSO first-sign-in flow and its independently configured fallback.

**Initial base roles.** The four shipped definitions are cumulative. Viewer receives basic server status and filtered workload events. Power User adds start, stop, restart, wake, live and historical logs, and interactive console input. Operator adds listing, inspecting metadata, reading, creating and editing approved non-critical files, creating directories within approved writable subtrees, and viewing and editing the server description. The path selectors and description field are explicit. A template with no reviewed editable paths grants no file access through the Operator preset. The preview explains that raw console commands can change game state wherever the game accepts them. [Base roles and selectors](contracts/permission-catalog.md#default-base-server-roles)

Administrator grants all 91 ordinary actions in this server catalog with their reviewed selectors, including member management and deletion of authorized files, backups and schedules. Deleting or wiping the server and transferring ownership require effective `server.view` plus the existing owner-or-target-admin authority. Personal credentials and share administration keep their existing checks. Other targets, provisioning, panel administration and Blocks have independent authority. Adding a new action or selector to a live role follows the impact review in D1. [Server actions](contracts/permission-catalog.md#operations)

**Archive, SFTP and settings duties.** A metadata reader can inspect backup history. The downloader needs `backups.download` on the source. A staging user needs `restores.upload` on the destination, and another person can confirm the overwrite with `restores.applyExisting` there. Each needs its catalogued views. `sftp.connect` permits using the SFTP transport on a visible server within the person's existing file actions and paths. Operator gets exact metadata inspection on reviewed paths. Administrator also receives SFTP, rename and the archive operations. A server-role grant to view or edit selected security fields still needs the independent scope-level `servers:security` authority for a change. [Server permissions and prerequisites](contracts/permission-catalog.md#view-prerequisites)

**Breaking 0.x release.** Reset both pre-upgrade sources of shared workload access: server collaborator lists and supplemental cluster/namespace bindings. Preserve ownership and primary OIDC/Helm or manual panel assignment. No legacy role or historical role revision is created. A persistent primary-panel-admin banner lists former assignments for review. For a server, choose named roles or custom permissions. For a cluster or namespace, choose a scoped role and preview its duties and any optional inheritance. Restoring only infrastructure access requires no server role. Choosing **Keep access removed** closes the item. Nothing is preselected or implicitly restored. A pending review grants no access, even when the old cluster reconnects. [Upgrade and reassignment](plan.md#7--reset-beta-access-and-review-assignments)

## D4 · Where assignments live

**Decided.** Panel SQL is the source of truth for direct server memberships, live role definitions, approved GameTemplate permission mappings and base-role additions, scoped bindings and admin Blocks. Direct membership identifies the account, registered cluster, namespace, server name and immutable GameServer UID. Store each scoped binding once. Evaluate it against the trusted cluster, namespace and effective GameTemplate when listing or authorizing a server. Verify the live UID before workload access. A same-name replacement loses the previous direct membership and inherits the grants that match its own scope and template. Kubernetes continues to identify the live workload and its owner.

Identify a scope by the cluster registration’s immutable identity and, for an exact namespace, its Kubernetes Namespace UID. Credential renewal for the same verified cluster keeps that identity. Deleting and re-registering a cluster or recreating a namespace with the same name requires a previewed rebind. Stale exact grants are inactive. If a stale Block could uncover an allow on the replacement, keep the affected subject, action and selectors restricted until the primary panel admin reviews the impact and reapplies or releases the restriction. A valid cluster-wide role still covers a newly created managed namespace in that registration. Unreachability alone is insufficient evidence of replacement.

Run a read-only reset dry run before maintenance and again under the writer fence, with SQL and workload backups and a verified primary admin. Treat the former relationships as review records only. A primary panel admin can revoke a known SQL assignment while its cluster is offline. Creating an assignment requires verified live identity and authority. After a database restore, reconcile the cutover and subsequent policy changes before reopening affected access. [Cutover and recovery](plan.md#7--reset-beta-access-and-review-assignments)

## D5 · Panel, cluster and server access

**Decided.** Use three layers. The primary panel role governs the installation. Cluster and namespace roles control infrastructure duties within that scope. Server roles control actions on a server. Assign them directly to one server UID or optionally include them in a scope role for inheritance on matching servers. Ownership is independent.

| Layer | Where an admin works | Example |
| --- | --- | --- |
| Panel access | **Users & RBAC** sets the primary role or shows its OIDC/Helm source. The built-in primary panel admin manages the reusable server-role library. | Set the default language, manage accounts or explicitly choose **Assigned servers only** for zero permissions from the primary role. |
| Cluster / namespace access | **Cluster → Roles & permissions** defines the scoped role and assigns it to accounts. **Users → Person → Access** shows the same binding. | A provisioner can create from selected templates in `eu/tournaments` with no inherited server roles. A Tournament staff role can also include Match referee on matching CS2 servers. |
| Individual server access | **Server → Access** shows inherited sources and lets an authorized inviter choose named roles or custom permissions directly for one UID. | Give Alex Power User directly on Match A. Removing Alex's Tournament staff grant leaves that direct assignment intact. |

A cluster or namespace role can have zero, one or multiple inherited named server roles. Leave the list empty for infrastructure duties alone. A panel-created role such as **Backup Operator** can be its sole server role. GameTemplate roles contribute on servers with the matching effective module. A cluster binding covers existing and future servers in every managed namespace of that registration. A namespace binding covers the servers in that exact namespace UID. Applicable Blocks take precedence. A direct bulk assignment remains available for a fixed set of existing server UIDs. The binding supplies no `server.view` of its own. If CS2 Match referee is the only selected role and the member has no other grants, they see and can referee matching CS2 servers. They have no access to Valheim. Future servers follow the same matching rule.

A GameTemplate can declare individually assignable permissions, add them to any of the four base roles, recommend further additions and offer optional named roles. Each declared permission has a stable ID within the trusted template and maps to reviewed server actions or fields with explicit selectors. Gameplane enforces the canonical action, effects and Blocks through every route. Panel, infrastructure and protected owner operations remain outside the template's authority. A new installation can use a matching approval already granted by this panel. Changes outside that approval require a new decision.

Only the built-in primary panel admin approves a template’s permission declaration set. After the before/after preview, one confirmation puts its declared `baseRoleAdditions` into effect for the specified bases on that template. The same approval makes the individual permissions and optional roles available for explicit assignment. A `baseRoleRecommendations` entry grants access only after separate activation. Both kinds of additions name each intended base explicitly. Cumulative initial role definitions do not propagate a template addition to another base.

For example, CS2 declares **Pause match** and **Resume match** for Administrator, recommends them separately for Power User, and offers both in the optional **Match referee** role. Approval gives the named controls to direct and inherited CS2 Administrators on their next decision. A CS2 Viewer gains the controls only through a separate grant, such as Match referee. Future matching servers follow the same rule within the binding’s scope. Other games, unnamed bases and independent custom copies keep their own permissions. Previews of approval, change or withdrawal identify the source, affected people and servers, future coverage, surviving grants and Blocks. Changing a server’s effective template re-evaluates its additions. A missing or materially changed underlying operation suspends the affected mapping until fresh review. [GameTemplate declaration and approval contract](contracts/permission-catalog.md#gametemplate-roles)

Always show an impact preview for scoped assignments, edits and removals in either view. Identify the person or affected members, exact scope, each selected role and where it applies, including declared additions and active recommendations on matching shipped bases. Show the distinct number of current servers matched, the count per role and template, which servers the person can actually see, and the effect on future servers. Show sources that survive removal where the actor may inspect them. Show the impact preview for infrastructure-only assignments too. An empty inheritance list contributes no server role now or in future. A selected role with zero current matches may still apply to future matching servers. For example, granting Tournament staff for a namespace with two CS2 servers and one Valheim server shows Viewer on all three, Match referee on two, and the same rules for future servers there. Mark offline inventory as last known or unavailable. The count describes observed impact and never limits which servers inherit the grant.

Show which actions and data will be newly visible, lost, blocked or retained, including when two sources overlap. For example, an existing `servers:read` grant can still expose files after a new scoped role grants only Viewer. Explain that contribution using the same decision and redaction as an actual request. Direct membership, ownership and a narrower selector each have their own effect on the result.

Cluster discovery, inventory access and server delegation alone do not authorize binding changes. Check the grantor's authority over the account, role, cluster and namespace. Keep a local workload-cluster grant on combined installations distinct from the logical primary panel binding. Preserve the primary role across edits to workload grants, exact namespace eligibility, and restrictions on central/wildcard permissions for whole-cluster workload grants. Node inventory still requires eligible whole-cluster authority. Existing OIDC/Helm primary role mappings retain their configured scope. Pre-upgrade supplemental provisioning and inventory grants expire at activation. Assigning a new scoped role requires a confirmed scope and impact preview, including when inherited server roles are empty. [Existing panel bindings](../../docs/multicluster-ui.md#user-access) · [Panel permission catalog](../../api/internal/rbac/catalog.go)

## D6 · Explicit exceptions to inherited access

**Decided.** Implement a scoped **Block** managed exclusively by the built-in primary panel admin. An owner, delegated membership manager, fleet-role editor or target-only admin cannot create, change or remove one. Applicable subjects are a user or role. The target is one server UID or an exact cluster/namespace. A rule names the ordinary workload action and applicable selectors, such as a networking field or file subtree. No existing grant is converted into a Block.

A user Block matches that account. A role Block matches an account only where it holds that role on the target. Holding the role on a sibling server is insufficient. Once the subject, target, action and selectors match, the Block wins over every direct or inherited allow for that action. Removing the Block reveals whatever access remains. It never manufactures a grant. Keep platform/credential limits and the built-in panel admin recovery path. Explain the affected action, scope and source to authorized viewers, and audit who imposed or removed it. Validate the same decision on fleet reads, detail, individual/compound writes, live streams and MCP reads. A namespace Block restricts matching actions throughout that cluster/namespace and grants no server membership. An effective `server.view` is a prerequisite for every ordinary action on that server. Blocking it hides the server and closes active streams under FR-09. An owner whose view is blocked keeps ownership but loses the ability to delete, wipe or transfer that UID until the view becomes effective again. The API checks this prerequisite even for an owner acting outside the dashboard. Blocking a narrower view also denies every mutation that depends on it, even if another source grants the mutation. Enforce the same view-before-modify rule at the panel, workload-scope and server layers. For example, editing one settings key needs its view on that exact key. Creating a resource uses its catalogued parent view. The protected panel-admin recovery path still works.

For example, Alex inherits Power User throughout `eu/tournaments` and can also read logs directly on Final. A panel admin's Block on Alex reading logs on Final suppresses both allows there. The scope grant still permits logs on Match A. Removing the Block restores log access on Final if another grant allows it. [Reference comparison](reference-panels.md)

**Decided for console and moderation.** Kick, Ban and Unban are separate Gameplane controls. Each requires support for that operation on the effective module, its permission and its views. Its Block also applies to named actions performing that operation. A user whose raw console access is independently authorized can still send a native game command. Show this in the effective-access preview whenever it matters. [Server action catalog](contracts/permission-catalog.md#operations)

## Decided · Protecting the last panel administrator

Require another enabled built-in primary panel admin before the panel permits removing, suspending or demoting the last one. A delegated user manager or server Administrator does not count. Honor an authoritative OIDC demotion at sign-in for an SSO-managed account, even if it leaves zero primary admins. Operator recovery with `bootstrap-admin` restores a local primary admin. [Panel admin identity](spec.md#roles-grants-and-scope) · [Recovery command](../../docs/security.md#lockout-guard-and-break-glass)

## Decided · Sharing template approvals across installations

Here, **Approve template permissions** is the primary panel admin’s review of a game module’s declarations about access. For example, CS2 can declare **Pause match**, add it to Administrator and offer an optional Match referee role. The preview shows exactly which current and future role holders gain the control. Approving applies the declared base addition to matching servers and makes Match referee available to assign. A recommendation for Power User requires a separate opt-in. Installing the module, creating a game server and inviting a person each have their own workflow.

**Decided.** Reuse an approval across current and future clusters belonging to the same panel when the server’s effective template verifies the same publisher, source and logical module, with matching reviewed permission declarations. Compare the canonical operations, parameter bounds, prerequisites, effects, selectors and the named bases or optional roles receiving the permissions. A new alias or package version can reuse verified, unchanged rights. A fork, an unverified publisher or source change, an expanded permission, a changed role mapping or a separate panel requires its own review. Local or unsigned templates can be reviewed for their own installation. [Module install identity](../../operator/api/v1alpha1/module_types.go) · [Effective template rollouts](../../docs/template-rollouts.md)

Preview the matching installations and aliases, users and server roles, any unavailable cluster counts, and future coverage before confirming. A shared approval makes an optional role available for assignment and leaves recommendations subject to their separate opt-in. A withdrawal follows the approval throughout that panel.

For example, EU installs CS2 as `cs2-league` and US installs it as `cs2-finals`. Both can use the same approved **Pause match** permission. If US later adopts a changed command, it waits for review there while an EU server still using the verified command can continue. Rolling back a package cannot restore a withdrawn permission.
