# Decisions for per-server access

D1 through D6 record the agreed role model, the beta access reset and the view prerequisites. One product decision remains about sharing a GameTemplate permission approval across installations. [Spec](spec.md) · [Implementation plan](plan.md)

## D1 · Editing a base role

**Decided.** A server role has one stable ID and one current permission set. Saving an edit changes what every assignee receives on their next request, across direct assignments and matching cluster or namespace grants. An unreachable cluster does not delay the edit. Existing streams recheck as specified in FR-09. The editor previews who gains or loses access before the single save. Count committed bindings and direct assignments in panel SQL. For inherited access, count distinct affected servers and show template matches from the available workload inventory. Label unavailable or last-known counts separately. Always show the impact preview, including future scope coverage. An offline inventory does not prevent saving after that review. There is no role revision, assignment upgrade or per-user opt-out from the edit. Audit the before/after action delta. An ordinary one-off permission selection is a distinct grant, and any independent source that still grants an action appears in effective access.

## D2 · Who can delegate

**Decided.** Delegation has its own permissions. Holding a gameplay, file or settings permission alone never lets someone give it to another person. Select each duty separately on a target server. Each mutation also requires effective `members.view` there.

| Permission | What the holder may do |
| --- | --- |
| `members.view` | See that server's member roster and the grant details they are authorized to inspect. |
| `members.invite` | Add a new direct assignment for an existing account on that server. This does not provision a panel account or overwrite an existing assignment. |
| `members.edit` | Change an existing direct assignment within the actor's transferable rights. Editing a reusable role definition remains a panel-admin operation. |
| `members.remove` | Revoke an existing direct assignment within the actor's authority. Account deletion and removal of inherited fleet bindings have their own administrative paths. |

A delegated change requires `members.view` on the target server, the specific invite, edit or remove action, and authority over the affected rights and selectors, including dormant actions. For example, a shift lead who can view members, invite, see the player roster and kick on Match 1 can grant that moderation duty there. They cannot grant Ban, remove members, promote themselves or appoint another membership manager. The target-scoped exact-account lookup keeps the global account directory private.

The server owner and an admin authorized for the target may appoint membership managers. Owners can delegate only actions they hold with equal or narrower selectors. Delegates cannot edit or remove a superior assignment, grant membership-management powers onward, change inherited grants or manage Blocks. A panel admin editing a shared role later authorizes that change for every assignee. The edit preview includes people originally assigned by delegates and those who inherit the role through a scoped binding. Losing a delegation permission prevents subsequent membership changes and leaves independently authorized assignments in place.

A workload-scope manager receives `bindings:assign`, `bindings:revoke` and `bindings:read` independently for a registered cluster or exact namespace. Creating or revoking a binding also requires effective `bindings:read` on the same scope and `scopeRoles:read` on the affected definitions. Switching an assignment checks all three keys. A scoped role author has a separate definition permission. On a shared definition edit, check the full effective delegation ceiling in every affected scope, including dormant rights and future coverage. Keep panel-account role assignment separate from both workflows. [Panel and workload catalog](contracts/fleet-permissions.md)

## D3 · Invitations and beta access reset

**Decided.** The inviter must choose the access. Start manual general-account and server invitations with nothing selected. Creating an account requires selecting its panel access explicitly, including **Assigned servers only** if desired. For a direct server assignment, select one or more applicable live roles or choose **Custom permissions** and pick at least one action. For a cluster or namespace assignment, select a scoped role whose definition has an explicit base server role and review its scope-wide effects before saving. Editing an existing person's server access leaves their account role alone. Show **Assigned servers only** as an available account-level choice, never as a preselection. A blank form or omitted grant in an invitation request issues no grant and returns a validation error before creating an account. Keep the configured SSO first-sign-in flow and its independently configured fallback.

**Initial base roles.** The four shipped definitions are cumulative. Viewer receives basic server status and filtered workload events. Power User adds start, stop, restart, wake, live and historical logs, and interactive console input. Operator adds listing, reading, creating and editing approved non-critical files, creating directories within approved writable subtrees, and viewing and editing the server description. The path selectors and description field are explicit. A template with no reviewed editable paths grants no file access through the Operator preset. The preview explains that raw console commands can change game state wherever the game accepts them. [Base roles and selectors](contracts/permission-catalog.md#default-base-server-roles)

Administrator grants all 84 ordinary actions in this server catalog with their reviewed selectors, including member management and deletion of authorized files, backups and schedules. Server deletion, wipe, ownership transfer, personal credentials and share administration keep their existing checks. Other targets, provisioning, panel administration and Blocks have independent authority. Adding a new action or selector to a live role follows the impact review in D1. [Server actions](contracts/permission-catalog.md#operations)

**Breaking 0.x release.** Reset both pre-upgrade sources of shared workload access: server collaborator lists and supplemental cluster/namespace bindings. Preserve ownership and primary OIDC/Helm or manual panel assignment. No legacy role or historical role revision is created. A persistent primary-panel-admin banner lists former assignments for review. For a server, choose named roles or custom permissions. For a cluster or namespace, choose a scoped role with exactly one base and preview the impact on existing and future servers. Choosing **Keep access removed** closes the item. Nothing is preselected or implicitly restored. A pending review grants no access, even when the old cluster reconnects. [Upgrade and reassignment](plan.md#7--reset-beta-access-and-review-assignments)

## D4 · Where assignments live

**Decided.** Panel SQL is the source of truth for direct server memberships, live role definitions, approved GameTemplate permission mappings and base-role additions, scoped bindings and admin Blocks. Direct membership identifies the account, registered cluster, namespace, server name and immutable GameServer UID. Store each scoped binding once. Evaluate it against the trusted cluster, namespace and effective GameTemplate when listing or authorizing a server. Verify the live UID before workload access. A same-name replacement loses the previous direct membership and inherits the grants that match its own scope and template. Kubernetes continues to identify the live workload and its owner.

Identify a scope by the cluster registration’s immutable identity and, for an exact namespace, its Kubernetes Namespace UID. Credential renewal for the same verified cluster keeps that identity. Deleting and re-registering a cluster or recreating a namespace with the same name requires a previewed rebind. Stale exact grants are inactive. If a stale Block could uncover an allow on the replacement, keep the affected subject, action and selectors restricted until the primary panel admin reviews the impact and reapplies or releases the restriction. A valid cluster-wide role still covers a newly created managed namespace in that registration. Unreachability alone is insufficient evidence of replacement.

Run a read-only reset dry run before maintenance and again under the writer fence, with SQL and workload backups and a verified primary admin. Treat the former relationships as review records only. A primary panel admin can revoke a known SQL assignment while its cluster is offline. Creating an assignment requires verified live identity and authority. After a database restore, reconcile the cutover and subsequent policy changes before reopening affected access. [Cutover and recovery](plan.md#7--reset-beta-access-and-review-assignments)

## D5 · Panel, cluster and server access

**Decided.** Use three layers. The primary panel role governs the installation. A cluster or namespace role defines both infrastructure permissions in that scope and the server permissions every member inherits there. Direct assignments and ownership apply to individual server UIDs.

| Layer | Where an admin works | Example |
| --- | --- | --- |
| Panel access | **Users & RBAC** sets the primary role or shows its OIDC/Helm source. The built-in primary panel admin manages the reusable server-role library. | Set the default language, manage accounts or explicitly choose **Assigned servers only** for zero permissions from the primary role. |
| Cluster / namespace access | **Cluster → Roles & permissions** defines the scoped role and assigns it to accounts. **Users → Person → Access** shows the same binding. | A Tournament staff role grants `servers:create` in `eu/tournaments`, Viewer on every server there and Match referee on matching CS2 servers. |
| Individual server access | **Server → Access** shows inherited sources and lets an authorized inviter choose named roles or custom permissions directly for one UID. | Give Alex Power User directly on Match A. Removing Alex's Tournament staff grant leaves that direct assignment intact. |

Every new cluster or namespace role requires exactly one explicitly selected base server role from **Viewer**, **Power User**, **Operator** or **Administrator**, even when its only infrastructure duty is provisioning or inventory. A cluster binding covers all existing and future servers in its managed namespaces. A namespace binding covers all existing and future servers in that exact cluster and namespace. Every member receives the base on each such server. Any applicable admin Block still takes precedence. A bulk direct assignment remains available for a fixed set of existing UIDs.

A GameTemplate can declare individually assignable permissions, add them to any of the four base roles, recommend further additions and offer optional named roles. Each declared permission has a stable ID within the trusted template and maps to reviewed server actions or fields with explicit selectors. Gameplane enforces the canonical action, effects and Blocks through every route. Panel, infrastructure and protected owner operations remain outside the template's authority. Installing or updating a template can present proposals but cannot expand anyone's access.

Only the built-in primary panel admin approves a template’s permission declaration set. After the before/after preview, one confirmation puts its declared `baseRoleAdditions` into effect for the specified bases on that template. The same approval makes the individual permissions and optional roles available for explicit assignment. A `baseRoleRecommendations` entry grants access only after separate activation. Both kinds of additions name each intended base explicitly. Cumulative initial role definitions do not propagate a template addition to another base.

For example, CS2 declares **Pause match** and **Resume match** for Administrator, recommends them separately for Power User, and offers both in the optional **Match referee** role. Approval gives the named controls to direct and inherited CS2 Administrators on their next decision. A CS2 Viewer gains the controls only through a separate grant, such as Match referee. Future matching servers follow the same rule within the binding’s scope. Other games, unnamed bases and independent custom copies keep their own permissions. Previews of approval, change or withdrawal identify the source, affected people and servers, future coverage, surviving grants and Blocks. Changing a server’s effective template re-evaluates its additions. A missing or materially changed underlying operation suspends the affected mapping until fresh review. [GameTemplate declaration and approval contract](contracts/permission-catalog.md#gametemplate-roles)

Always show an impact preview for scoped assignments, edits and removals in either view. Identify the person or affected members, exact scope, base, its declared additions and active recommendations on matching templates, and each selected optional role. Show the distinct number of current servers covered, the matching count per template, and the effect on future servers. Show sources that survive removal where the actor may inspect them. Zero current matches still requires previewing future coverage. For example, granting Tournament staff for a namespace with two CS2 servers and one Valheim server shows Viewer on all three, Match referee on two, and the same rules for future servers there. Mark offline inventory as last known or unavailable. The count describes observed impact and never limits which servers inherit the grant.

Show which actions and data will be newly visible, lost, blocked or retained, including when two sources overlap. For example, an existing `servers:read` grant can still expose files after a new scoped role grants only Viewer. Explain that contribution using the same decision and redaction as an actual request. Direct membership, ownership and a narrower selector each have their own effect on the result.

Cluster discovery, inventory access and server delegation alone do not authorize binding changes. Check the grantor's authority over the account, role, cluster and namespace. Keep a local workload-cluster grant on combined installations distinct from the logical primary panel binding. Preserve the primary role across edits to workload grants, exact namespace eligibility, and restrictions on central/wildcard permissions for whole-cluster workload grants. Node inventory still requires eligible whole-cluster authority. Existing OIDC/Helm primary role mappings retain their configured scope. Pre-upgrade supplemental provisioning and inventory grants expire at activation. Assigning a new scoped role requires explicit base selection and the impact preview. [Existing panel bindings](../../docs/multicluster-ui.md#user-access) · [Panel permission catalog](../../api/internal/rbac/catalog.go)

## D6 · Explicit exceptions to inherited access

**Decided.** Implement a scoped **Block** managed exclusively by the built-in primary panel admin. An owner, delegated membership manager, fleet-role editor or target-only admin cannot create, change or remove one. Applicable subjects are a user or role. The target is one server UID or an exact cluster/namespace. A rule names the ordinary workload action and applicable selectors, such as a networking field or file subtree. No existing grant is converted into a Block.

A user Block matches that account. A role Block matches an account only where it holds that role on the target. Holding the role on a sibling server is insufficient. Once the subject, target, action and selectors match, the Block wins over every direct or inherited allow for that action. Removing the Block reveals whatever access remains. It never manufactures a grant. Keep platform/credential limits and the built-in panel admin recovery path. Explain the affected action, scope and source to authorized viewers, and audit who imposed or removed it. Validate the same decision on fleet reads, detail, individual/compound writes, live streams and MCP reads. A namespace Block restricts matching actions throughout that cluster/namespace and grants no server membership. An effective `server.view` is a prerequisite for every ordinary action on that server. Blocking it hides the server and closes active streams under FR-09. Blocking a narrower view also denies every mutation that depends on it, even if another source grants the mutation. Enforce the same view-before-modify rule at the panel, workload-scope and server layers. For example, editing one settings key needs its view on that exact key. Creating a resource uses its catalogued parent view. The protected panel-admin recovery path still works.

For example, Alex inherits Power User throughout `eu/tournaments` and can also read logs directly on Final. A panel admin's Block on Alex reading logs on Final suppresses both allows there. The scope grant still permits logs on Match A. Removing the Block restores log access on Final if another grant allows it. [Reference comparison](reference-panels.md)

## Open · Sharing template approvals across installations

The same module can be installed under different local GameTemplate names. Two servers can also be running different effective versions during a rollout. The open question is whether a panel admin who approved a permission for one installation must repeat that approval for another installation of the same module. The four base roles, live role edits and the requirement for admin approval of an access expansion are settled. [Module install identity](../../operator/api/v1alpha1/module_types.go) · [Effective template rollouts](../../docs/template-rollouts.md)

| Choice | What a panel admin would see |
| --- | --- |
| Approve per installation | Approving **Pause match** on the EU installation enables that reviewed addition there. The identical US installation needs its own preview and approval. This also permits intentionally different policy on the two installations. |
| Share within one verified module lineage (recommended) | The panel admin approves **Pause match** once for the module from its verified publisher and source. The preview names the covered installations and future matches. EU and US aliases can share it while their effective snapshots prove the same reviewed command, parameters, effects and selectors. A fork, a local template without verified provenance, a changed operation or an unverified change of source or signing identity requires separate review. |

For example, an older EU server still running the approved Pause command can use it. A US server that adopts a changed command waits for review of that change. A withdrawal applies across its approved scope, including a server rolled back to an earlier package. This decision concerns the identity attached to an approval. Role definitions still have a single live permission set. Until a policy is chosen, an ambiguous identity cannot reuse another installation’s approval.
