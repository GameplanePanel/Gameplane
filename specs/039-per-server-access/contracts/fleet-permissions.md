# Panel, cluster and namespace permission catalog

The panel/fleet catalog has 112 keys in this design. The baseline contributes 24. The 88 additions comprise 39 installation-wide keys, 26 limited to a whole workload cluster, and 23 usable at a whole cluster or exact namespace. The protected `*` is separate. A role stores explicit keys and any selected targets. Each table prefix combines with each listed suffix to form a literal key. The [server catalog](permission-catalog.md) defines the server actions, base roles, paths, fields and game action selectors.

## Panel

These keys apply to the installation. Keep OIDC/Helm primary-role mappings and manual assignments. Scope roles on a workload cluster or namespace cannot carry these keys. The protected wildcard `*` belongs to the built-in admin. Its **primary** assignment provides automatic access to current and future registered clusters. Only the primary panel admin edits the four permanent shipped server roles, manages and retires custom server roles, approves GameTemplate grant changes, administers Blocks and changes auth/OIDC configuration.

**Last primary panel admin.** Reject a panel-initiated deletion, suspension or role change that would remove the last enabled account with effective built-in primary admin authority and a usable sign-in method. Check the resulting state in the transaction that changes it. An account with delegated user-management permissions cannot satisfy this requirement. When verified OIDC claims map an SSO-managed admin to a valid lower role, apply that role at the normal synchronization point even if it removes the final admin and user manager. Revoke that authority across sessions, tokens and streams under FR-09. If zero primary admins remain, an installation operator restores access with `bootstrap-admin`. Retain the existing login refusal for deny or missing-role mappings and the existing precedence of manual overrides. A failed authentication does not establish a role change. | `users:` | `lookup`, `list`, `profile:read` | Lookup matches one exact account identifier and returns the minimum identity for selection. List returns directory rows. | `users:` | `invite`, `create`, `edit` | The existing create route uses Invite for a pending account without a local password and Create for a local account with an initial credential. Suspension and reactivation are new operations. Disable rejects local and OIDC sign-in, invalidates sessions and suspends token access while retaining assignments. Keep self-management, superior-target and sign-in protections, with the OIDC role-removal exception above to the last-manager check. Treat recovery-sensitive profile changes as credential management if used to recover the account. |
| `userTokens:` | `read`, `revoke` | Inspect another user's MCP token metadata or revoke one. Preserve self-service token management and never return stored token values. |
| `roles:` | `create`, `edit`, `delete` | Author ordinary panel role definitions. Check the grantor's ceiling, including all affected assignees on an edit. Protect built-in roles, protected keys and the server-role library. Assigning a primary role uses `users:assignRole`. |
| `config:general:`, `config:notifications:`, `config:telemetry:`, `config:i18n:`, `config:modRegistries:` | `read`, `manage` for each | Grant redacted section reads independently and check the section read before changing it. Filter aggregate configuration, status and notice responses to the allowed sections. Preserve Helm and install-time restrictions. Registry configuration includes provider policy and credential-sharing policy. |
| `config:auth:` | `read` | Read redacted sign-in configuration. Sign-in provider, role-mapping and provider-secret mutations require the primary panel admin. |
| `config:notifications:` | `test`, `replaceCredential`, `removeCredential` | Test-send to an already configured sink or supply/remove its credential. Editing the sink configuration alone grants none of these operations. Require a separate credential check on equivalent config writes and keep stored secrets write-only. |
| `config:modRegistries:` | `replaceCredential`, `removeCredential` | Replace or remove an existing provider's stored key independently of changing provider settings. |
| `cluster:` | `registrations:read` | View the redacted panel registration collection or an authorized registration's identity, connection status and credential presence. Scope exact-target grants to the registration generation. This view also works when the registry is empty and exposes neither connection credentials nor workload inventory. |
| `cluster:` | `register`, `remove`, `configureGateway`, `joinNode`, `issueKubeconfig`, `replaceKubeconfig` | Register a remote with its initial connection data, remove a registration, configure/remove its gateway, issue a node join command, mint a short-lived read kubeconfig for the caller, or rotate a registered cluster's connection credential. The preview must distinguish already-issued Kubernetes credentials, which remain subject to their own lifetime and cluster-side revocation. |

**Existing panel keys.** `users:read`, `users:manage`, `roles:read`, `roles:manage`, `audit:read`, `config:read`, `config:manage` and `cluster:manage` retain their documented operations subject to the view prerequisites below. `roles:read` supplies the ordinary panel role catalog and `audit:read` the installation-wide audit view. The remaining broad keys appear with their constituent effects in the preview. A principal who can reset a privileged account's password, assign its role or edit a live role must pass the applicable target and grant checks on every route. Validate every changed field in a mixed account or configuration update before committing any of it. ## Whole workload cluster

These keys bind to one registered workload cluster identity and registration generation. A whole-cluster role may also grant any key in the next table across its current and future managed namespaces, including a replacement namespace with a new UID. An exact namespace role additionally binds the Kubernetes namespace UID. New scope Blocks use the same identity rules. Names label these policies in the UI. A recreated registration or namespace with the old name requires a fresh impact preview and explicit rebind of exact-scope policy. Losing contact alone does not establish replacement. Rotating credentials for the verified same registration retains its identity. On combined installations a local workload binding is distinct from the primary panel binding at logical `local/*`.

| Prefix | New suffixes | Enforcement |
| --- | --- | --- |
| `cluster:` | `health:read`, `nodes:read`, `storage:read`, `usage:read` | Split cluster connectivity, status and version, node inventory, storage inventory, and aggregate usage respectively. Project the combined cluster, info and stats responses. A usage grant can return aggregate capacity without disclosing node names, individual workloads or storage objects. |
| `templates:` | `create`, `edit`, `delete` | Author cluster-wide template objects. Preview deployment effects and retain admission policy and primary-admin review for changes to permission semantics. |
| `modules:` | `catalog:read`, `installed:read`, `install`, `upgrade`, `uninstall`, `author` | Read catalog entries, inspect installed modules, perform each installation lifecycle step, or use the draft builder (scaffold, validate, preview and export). An author publishes through a separately authorized source or template operation. |
| `moduleSources:` | `read`, `create`, `edit`, `delete`, `upload`, `removeUpload` | Inspect or administer trusted sources, or add/remove a bundle in an existing source. Source administration and installation are independently assignable. Retain source validation and trust policy. |
| `captures:node:` | `read`, `enable`, `disable`, `start`, `stop`, `download`, `delete` | Separate redacted metadata/status, host diagnostic opt-in/out, collection, raw packet download and deletion. Node diagnostic opt-in/out also requires the existing cluster-wide admin guard. Enforce host policy, target UID, source backend, retention and capture feature gates. |

## Whole workload cluster or one exact cluster/namespace

| Prefix | New suffixes | Enforcement |
| --- | --- | --- |
| `servers:` | `inventory`, `create` | Inventory lists basic server identity, placement and status. Its payload excludes files, logs, rosters and raw objects. Create provisions at the selected placement. An explicit `servers:inventory` grant exposes its authorized inventory independently of any selected server role. The scope binding itself grants no server visibility. Ownership of a newly created server follows its existing rules. |
| `templates:` | `use` | Select explicit trusted template IDs for provisioning. Authorize placement discovery, the Create form and submission against the same cluster, namespace and template. Return only the minimal permitted choices and creation fields. A template-use grant in one namespace cannot be combined with a creation grant in another. Whole-cluster `templates:read` remains a broader source for template selection. The same placement and template visibility prerequisite applies to provisioning via `servers:write`. |
| `audit:scope:` | `read` | Read audit events attributable to this cluster or namespace. Resolve trusted target identities, redact unrelated actors/subjects and omit ambiguous, cross-scope and panel administration details. Filter before counting and pagination. Server activity remains separately assignable. |
| `bindings:` | `read`, `assign`, `revoke` | Inspect scoped assignments, grant an existing scope role, or withdraw it. Independently authorize both sides of a replacement (revoke old, assign new) atomically. An assigner can resolve the minimal exact account and eligible role choices for that operation. Removing the last inherited role from a definition preserves its independent infrastructure grants. If a scoped definition references a retired custom server role, existing members keep the referenced role on current and future matching servers. Remove or replace that reference, or choose another scoped definition, before assigning a new member. Global directory access, inspection of unrelated bindings and direct server member management remain separate. |
| `scopeRoles:` | `read`, `create`, `edit`, `delete` | Inspect or author the scoped definition, including its optional selection of zero or more named server roles available in that scope. On each current and future server within the scope, apply only the selected shipped, panel-created or approved GameTemplate roles that match that server. Only a selected shipped base receives its approved declared additions and active recommendations on matching templates. Restrict authoring to its declared scope. An edit to a shared definition requires authority over every affected binding and the complete old/new grants, including future coverage. A namespace editor can create a local definition when a shared definition extends beyond their authority. Reject deletion of an assigned definition until its assignments are explicitly replaced or revoked. |
| `destinations:` | `use`, `create`, `edit`, `delete`, `replaceCredential` | Use a selected set of approved destination identities. A server role with `backups.create`, including Administrator, can use the destination approved for that server by policy, including an approved default, or an explicitly selected destination on the server grant. The picker returns only usable choices. A direct server backup grant needs no separate namespace grant. Verify the destination identity in the target namespace and the backup/restore authority. Create may set an initial credential. An update checks each changed field, including credential replacement. Check whether the object already exists atomically. |
| `captures:server:` | `read`, `enable`, `disable`, `start`, `stop`, `download`, `delete` | Separate metadata/status, opt-in/out, collection, raw traffic export and deletion on eligible workloads. Resolve the actual backend from the trusted capture or workload before acting. Shared capture lists filter each item by backend. A server-capture grant cannot expose host capture data through an identical URL. |

**Existing cluster or namespace keys.** `servers:read`, `servers:write`, `servers:console`, `backups:read`, `backups:write`, `backups:restore`, `schedules:read`, `schedules:write`, `destinations:read`, `destinations:manage`, `captures:manage`. Keep baseline target, response and protected checks in addition to the view prerequisites below. A valid `servers:read` grant can expose logs and files. The existing capture permission does not itself authorize opting a server into privileged node diagnostics. Apply the credential and endpoint trust checks on typed and generic writes whenever a sink, provider, gateway or destination edit would deliver a retained secret to a different recipient. For example, a sink manager may change a label. Changing an authenticated sink or repository to a different endpoint requires a credential replacement authorized for that endpoint, or authorized removal where the product supports credential-free operation. Provider credential-sharing controls retain their existing restrictions. Show these dependencies before saving.

## View prerequisites

Every mutation requires effective permission to view the resource being changed. For creation, check the destination collection or the exact provisioning choice before the object exists. Use the catalog's existing read, lookup or selection keys where listed. Check the actual caller and credential, scope identity, relevant selector and redaction on preview and execution. A view can come from another active grant that covers the same target. A missing view denies the write even when the caller knows the target ID. Giving someone a write never silently grants extra reads. The role picker identifies the required view and its reach for explicit selection. Preview shows missing prerequisites and which operations would stop working if a view were withdrawn. Reevaluate the underlying operations on bulk writes and alternate routes.

| Operation | Required visible target |
| --- | --- |
| Account creation and invitations | `users:lookup` for the proposed exact identifier permits checking the creation target without exposing the account directory. The Create form works with an empty directory. Giving the new account a nonzero primary role also requires a view of the selected role under `roles:read`. |
| Account edits, suspension, reactivation, deletion, credential reset and primary-role changes | `users:profile:read` on the target account. For primary-role changes also require `roles:read` for the role being assigned. `users:list` alone supplies directory rows. Another user's token revocation requires `userTokens:read` on that token's metadata. Self-service uses the authenticated user's own account or token metadata view. |
| Panel roles, configuration and registrations | Role writes require `roles:read` for the target role or role collection. Section changes, test sends and credential changes require that section's redacted read. Protected auth changes require `config:auth:read` in addition to primary-admin authority. All six panel cluster operations require `cluster:registrations:read` for the target registration, or the registry collection for registration. |
| Template and module authoring, installation and sources | Template writes require `templates:read` on the cluster and template or collection. Module install requires `modules:catalog:read` on the selected package and `modules:installed:read` on the destination installation collection. Upgrade requires both views and uninstall requires the installed entry view. Draft authoring requires catalog read, plus installed read if importing an installation. Every source mutation, including bundle upload and removal, requires `moduleSources:read` on that source or collection. |
| Provisioning | The readable parent is the permitted placement and selected template's creation fields through `templates:use`, or matching `templates:read` with access to that placement. Where a template is selected, require the create operation and view at the same destination. A future server UID cannot supply this check. Provisioning from a backup additionally checks source backup visibility and restore authority. |
| Scope role and binding changes | Definition writes require `scopeRoles:read` for the definition or its collection. Assigning, replacing or revoking a binding requires `bindings:read` on the target person's scoped binding or its parent and visibility of the affected definition(s) through `scopeRoles:read`. Limit both reads to the authorized scope and targets. Keep exact-account resolution for this operation and all delegation ceilings. |
| Destinations and captures | Destination administration including credential changes requires `destinations:read` on the destination or collection. Selecting a destination for backup uses its minimal redacted `destinations:use` projection or the already authorized server destination policy. Each capture mutation requires the corresponding `captures:node:read` or `captures:server:read` on its actual backend and target. |
| Existing broad server, backup and schedule operations | On an existing UID, resolve each `servers:write` or `servers:console` operation to the server view and specific action view with matching selectors. Backup create, delete and restore require the corresponding backup or restore view, and schedule writes require the schedule view. The broad `backups:read` and `schedules:read` can supply those views for the targets they cover. Apply the [server action prerequisites](permission-catalog.md) across fleet routes. A Block of `server.view` also suppresses ordinary fleet access to that server. |
| Primary-admin operations | Editing a reusable server role, reviewing a template declaration or administering a Block requires the protected target/collection view supplied by the primary admin's recovery authority and the applicable impact preview. These protected views provide only redacted data. |

A broad key satisfies a read prerequisite only if its defined effects include that view at the same target. Thus `config:read` may supply an allowed redacted section view, and `modules:read` may supply its covered catalog or source projections. A write-only grant in a preserved primary role that lacks the required read becomes unusable until an administrator explicitly supplies the missing view. Show this change in the beta dry run. Secret replacement requires a view of the relevant redacted field or credential presence. It never requires disclosing the stored value.

## Assignment, beta reset and effective preview

- A cluster or namespace role may reference zero or more named server roles available in its scope. A provisioner can hold `servers:create` and its placement and template prerequisites with no inherited role on existing servers. The binding defines where each selected role is evaluated. Server visibility and actions come from matching roles and other explicit sources, subject to Blocks and credential limits. A single approved GameTemplate role can be the only selection in a mixed-game namespace. Unmatched servers remain hidden from that person unless another grant covers them. No current or future inventory coverage minimum applies.
- A scoped assigner needs the named binding permission at that exact scope and authority over the account, fleet keys and complete selection of server roles. Check each role’s actions and selectors across the whole scope, including dormant actions, future template matches, and approved additions or active recommendations for any selected shipped base. A delegate cannot expand their own access, edit superior assignments or pass delegation authority onward. Apply the same ceiling to live role edits. A namespace assignment can grant only namespace-eligible keys.
- On beta cutover, stop reading the old collaborator lists and all pre-cutover supplemental cluster/namespace grants for authorization. Preserve independent ownership and the primary panel assignment from OIDC/Helm or manual selection, including its backing primary binding. Apply this distinction even on the local cluster. The protected primary admin has automatic current and future cluster coverage. Existing broad keys on a valid primary assignment continue to cover their defined effects subject to the new view checks. For example, directory administration does not acquire newly added suspension authority. The dry run reports expected losses, retained sources and admin coverage separately.
- An administrator must explicitly issue fresh assignments after the reset. The admin review banner links each old supplemental entry to **Cluster → Roles & permissions**, and each former collaborator to **Server → Access**, with the person's consolidated access view available for either. Keep historical review entries outside authorization. For a cluster or namespace explicitly choose a scoped role and review its infrastructure permissions and any server-role inheritance. A scoped role with no inherited server roles is valid. A direct server assignment requires at least one named role or one explicit custom permission. Run the normal grant preview against the current target identity before saving. A retry or reconnection cannot resurrect revoked grants or remove fresh ones.
- Derive preview and enforcement from the same evaluator. Before saving, compare effective **before** and **after** for panel, scoped infrastructure and server actions. Show what the change adds, withdraws, leaves independently allowed, or Blocks, with sources and relevant selectors. Distinguish unavailable actions and redact detail outside the reviewer's authority. For an infrastructure-only role, show **No inherited server roles**, its infrastructure rights and any visibility independently supplied by an explicit inventory grant. For a role with inheritance, show each selected role, the distinct number of servers it matches, where it can apply in the future, how many visible servers or actions the assignment actually adds, any unavailable inventory and the effect of privileged operations. Recompute when the reviewed grant, definition, target or authority changes before commit.
- For example, a namespace role selecting only CS2 Match referee gives its `server.view` and approved match actions on existing and future matching CS2 servers. With no independent grant, a Valheim server in that namespace stays hidden. If Alex also has Power User directly on one of those servers, removing the namespace grant leaves status, events, logs and power access on that UID. The preview attributes the remaining access to the direct assignment. A matching admin Block takes precedence over ordinary server allows.
