# Panel, cluster and namespace permission catalog

The panel/fleet catalog has 111 keys in this design. The baseline contributes 24. The 87 additions comprise 38 installation-wide keys, 26 limited to a whole workload cluster, and 23 usable at a whole cluster or exact namespace. The protected `*` is separate. A role stores explicit keys and any selected targets. Each table prefix combines with each listed suffix to form a literal key. The [server catalog](permission-catalog.md) defines the server actions, base roles, paths, fields and game action selectors.

## Panel

These keys apply to the installation. Keep OIDC/Helm primary-role mappings and manual assignments. Scope roles on a workload cluster or namespace cannot carry these keys. The protected wildcard `*` belongs to the built-in admin. Its **primary** assignment provides automatic access to current and future registered clusters. Only the primary panel admin manages reusable server roles, approves GameTemplate grant changes, administers Blocks and changes auth/OIDC configuration.

| Prefix | New suffixes | Enforcement |
| --- | --- | --- |
| `users:` | `lookup`, `list`, `profile:read` | Lookup matches one exact account identifier and returns the minimum identity for selection. List returns directory rows. Profile read exposes ordinary contact/profile fields for an identified account. Keep private account data out of search suggestions and grant previews. |
| `users:` | `invite`, `create`, `edit` | The existing create route uses Invite for a pending account without a local password and Create for a local account with an initial credential. An invitation uses the existing onboarding flow. Edit permits ordinary profile fields. Choose primary access explicitly. Either account-creation path can select **Assigned servers only**. A nonzero initial role also requires `users:assignRole` and authority over the selected role. |
| `users:` | `disable`, `enable`, `delete`, `resetPassword`, `assignRole` | Separate suspension, reactivation, deletion, resetting another local account's password and changing the primary role or returning it to SSO control. Suspension and reactivation are new operations. Disable rejects local and OIDC sign-in, invalidates sessions and suspends token access while retaining assignments. Enable permits fresh sign-in and leaves revoked credentials invalid. A disabled identity cannot satisfy the last-usable-manager check. A later SSO login or group sync cannot reactivate it. Keep self-management, superior-target, last-manager and SSO lockout checks. Treat recovery-sensitive profile changes as credential management if used to recover the account. |
| `userTokens:` | `read`, `revoke` | Inspect another user's MCP token metadata or revoke one. Preserve self-service token management and never return stored token values. |
| `roles:` | `create`, `edit`, `delete` | Author ordinary panel role definitions. Check the grantor's ceiling, including all affected assignees on an edit. Protect built-in roles, protected keys and the server-role library. Assigning a primary role uses `users:assignRole`. |
| `config:general:`, `config:notifications:`, `config:telemetry:`, `config:i18n:`, `config:modRegistries:` | `read`, `manage` for each | Independently grant redacted section reads or changes. Manage includes the editable section view. Filter aggregate configuration, status and notice responses to the allowed sections. Preserve Helm and install-time restrictions. Registry configuration includes provider policy and credential-sharing policy. |
| `config:auth:` | `read` | Read redacted sign-in configuration. Sign-in provider, role-mapping and provider-secret mutations require the primary panel admin. |
| `config:notifications:` | `test`, `replaceCredential`, `removeCredential` | Test-send to an already configured sink or supply/remove its credential. Editing the sink configuration alone grants none of these operations. Require a separate credential check on equivalent config writes and keep stored secrets write-only. |
| `config:modRegistries:` | `replaceCredential`, `removeCredential` | Replace or remove an existing provider's stored key independently of changing provider settings. |
| `cluster:` | `register`, `remove`, `configureGateway`, `joinNode`, `issueKubeconfig`, `replaceKubeconfig` | Register a remote with its initial connection data, remove a registration, configure/remove its gateway, issue a node join command, mint a short-lived read kubeconfig for the caller, or rotate a registered cluster's connection credential. The relevant panel key authorizes its operation subject to existing policy. Node joining and credential issuance require the default cluster and enabled cluster operations. Replacing a remote credential validates registration identity, allowed endpoints and ownership of managed Secrets. Removing issuance authority stops future issuance. The preview must distinguish already-issued Kubernetes credentials, which remain subject to their own lifetime and cluster-side revocation. |

**Existing panel keys.** `users:read`, `users:manage`, `roles:read`, `roles:manage`, `audit:read`, `config:read`, `config:manage` and `cluster:manage` retain their documented reach. `roles:read` supplies the ordinary panel role catalog and `audit:read` the installation-wide audit view. The remaining broad keys appear with their constituent effects in the preview. A principal who can reset a privileged account's password, assign its role or edit a live role must pass the applicable target and grant checks on every route. Validate every changed field in a mixed account or configuration update before committing any of it. ## Whole workload cluster

These keys bind to one registered workload cluster. A whole-cluster role may also grant any key in the next table across its managed namespaces. On combined installations a local workload binding is distinct from the primary panel binding at logical `local/*`.

| Prefix | New suffixes | Enforcement |
| --- | --- | --- |
| `cluster:` | `health:read`, `nodes:read`, `storage:read`, `usage:read` | Split cluster connectivity, status and version, node inventory, storage inventory, and aggregate usage respectively. Project the combined cluster, info and stats responses. A usage grant can return aggregate capacity without disclosing node names, individual workloads or storage objects. |
| `templates:` | `create`, `edit`, `delete` | Author cluster-wide template objects. Preview deployment effects and retain admission policy and primary-admin review for changes to permission semantics. |
| `modules:` | `catalog:read`, `installed:read`, `install`, `upgrade`, `uninstall`, `author` | Read catalog entries, inspect installed modules, perform each installation lifecycle step, or use the draft builder (scaffold, validate, preview and export). An author publishes through a separately authorized source or template operation. |
| `moduleSources:` | `read`, `create`, `edit`, `delete`, `upload`, `removeUpload` | Inspect or administer trusted sources, or add/remove a bundle in an existing source. Source administration and installation are independently assignable. Retain source validation and trust policy. |
| `captures:node:` | `read`, `enable`, `disable`, `start`, `stop`, `download`, `delete` | Separate redacted metadata/status, host diagnostic opt-in/out, collection, raw packet download and deletion. Node diagnostic opt-in/out also requires the existing cluster-wide admin guard. Enforce host policy, target UID, source backend, retention and capture feature gates. |

**Existing whole-cluster keys.** `cluster:read`, `templates:read`, `templates:write`, `modules:read`, `modules:manage`. Keep the authorized discovery projection of registered clusters separate from inventory access. ## Whole workload cluster or one exact cluster/namespace

| Prefix | New suffixes | Enforcement |
| --- | --- | --- |
| `servers:` | `inventory`, `create` | Inventory lists basic server identity, placement and status. Its payload excludes files, logs, rosters and raw objects. Create provisions at the selected placement. The required base independently supplies server access on each current and future server. Ownership of a newly created server follows its existing rules. |
| `templates:` | `use` | Select explicit trusted template IDs for provisioning. Authorize placement discovery, the Create form and submission against the same cluster, namespace and template. Return only the minimal permitted choices and creation fields. A template-use grant in one namespace cannot be combined with a creation grant in another. Whole-cluster `templates:read` remains the existing broad source for template selection. An old `servers:write` create path retains its baseline checks. |
| `audit:scope:` | `read` | Read audit events attributable to this cluster or namespace. Resolve trusted target identities, redact unrelated actors/subjects and omit ambiguous, cross-scope and panel administration details. Filter before counting and pagination. Server activity remains separately assignable. |
| `bindings:` | `read`, `assign`, `revoke` | Inspect scoped assignments, grant an existing scope role, or withdraw it. Independently authorize both sides of a replacement (revoke old, assign new) atomically. An assigner can resolve the minimal exact account and eligible role choices for that operation. Global directory access, inspection of unrelated bindings and direct server member management remain separate. |
| `scopeRoles:` | `read`, `create`, `edit`, `delete` | Inspect or author the scoped definition, including its mandatory base and optional GameTemplate additions. Restrict authoring to its declared scope. An edit to a shared definition requires authority over every affected binding and the complete old/new grants, including future coverage. A namespace editor can create a local definition when a shared definition extends beyond their authority. Reject deletion of an assigned definition until its assignments are explicitly replaced or revoked. |
| `destinations:` | `use`, `create`, `edit`, `delete`, `replaceCredential` | Use a selected set of approved destination identities. With only `backups.create`, a server Administrator can use the destination approved for that server by policy, including an approved default, or an explicitly selected destination on the server grant. The picker returns only usable choices. A direct server backup grant needs no separate namespace grant. Verify the destination identity in the target namespace and the backup/restore authority. Create may set an initial credential. An update checks each changed field, including credential replacement. Check whether the object already exists atomically. |
| `captures:server:` | `read`, `enable`, `disable`, `start`, `stop`, `download`, `delete` | Separate metadata/status, opt-in/out, collection, raw traffic export and deletion on eligible workloads. Resolve the actual backend from the trusted capture or workload before acting. Shared capture lists filter each item by backend. A server-capture grant cannot expose host capture data through an identical URL. |

**Existing cluster or namespace keys.** `servers:read`, `servers:write`, `servers:console`, `backups:read`, `backups:write`, `backups:restore`, `schedules:read`, `schedules:write`, `destinations:read`, `destinations:manage`, `captures:manage`. Keep baseline route, target, response and additional protected checks for these grants. In particular, a legacy server reader can view logs and files, and the existing capture permission does not itself authorize opting a server into privileged node diagnostics. [Placement discovery](../../../api/internal/handlers/fleet.go) · [Backup destination upserts](../../../api/internal/handlers/destinations.go) · [Capture routes](../../../api/internal/handlers/capture.go)

Apply the credential and endpoint trust checks on typed and generic writes whenever a sink, provider, gateway or destination edit would deliver a retained secret to a different recipient. For example, a sink manager may change a label. Changing an authenticated sink or repository to a different endpoint requires a credential replacement authorized for that endpoint, or authorized removal where the product supports credential-free operation. Provider credential-sharing controls retain their existing restrictions. Show these dependencies before saving.

## Assignment, compatibility and effective preview

- A scoped assigner needs the named binding permission at that exact scope and authority over the account, all role keys, selectors, base and template additions, including dormant actions and future coverage. Compare delegated rights on the complete target scope. A delegate cannot expand their own access, edit superior assignments or pass delegation authority onward. Apply the same ceiling to live role edits. A namespace assignment can grant only namespace-eligible keys. Each new scoped role still requires exactly one explicitly chosen common base.
- Evaluate each legacy broad key against a frozen route, field, target and effect matrix. Preserve access on equivalent new surfaces and keep later product capabilities opt-in. For example, prior directory administration does not gain a newly added account-suspension operation by virtue of its name. Keep existing ownership, direct grants and OIDC/Helm role resolution independent. Only confirmed conversion of a historical scoped binding introduces base-role inheritance.
- Derive preview and enforcement from the same evaluator. Before saving, compare effective **before** and **after** for panel, scoped infrastructure and server actions. Show what the change adds, withdraws, leaves independently allowed, or Blocks, with sources and relevant selectors. Distinguish unavailable actions and redact detail outside the reviewer's authority. Include server and template counts, future coverage, last-known or unavailable inventory and the effect of privileged operations. Recompute when the reviewed grant, definition, target or authority changes before commit.
- For example, adding Viewer in a namespace grants status and workload events on its twelve current servers and all future servers there. If Alex already has `servers:read` in the cluster, identify that legacy role as the source of log and file access before and after the grant. Removing Viewer alone leaves that independent historical access on all twelve. A matching admin Block takes precedence over ordinary server allows.
