# Server permission catalog

The 91 common server action IDs proposed for [#1063](https://github.com/GameplanePanel/Gameplane/issues/1063) appear in the Operations table, counting view and edit separately for each of the nine settings sections. Fields, paths and template-specific actions are selectors. The operations below exist at baseline `aa3b64f9` unless marked as proposed. Their fine-grained authorization, the presets and the member-management APIs are new. A direct assignment names one server UID. A cluster or namespace assignment may carry infrastructure permissions alone. Any selected server roles apply to matching current and future servers in that scope.

## Where an assignment applies

| Access layer | Permission source and example |
| --- | --- |
| Panel | The primary panel role controls installation-wide operations. Give a language editor `config:i18n:read` and `config:i18n:manage` for the instance default language. The [panel and fleet catalog](fleet-permissions.md) defines the account, role, settings, audit and infrastructure duties, including protected admin operations and existing OIDC/Helm grants. |
| Cluster or namespace | A binding applies eligible [fleet permissions](fleet-permissions.md) to one registered cluster identity or one verified namespace UID within that registration. Grant provisioning with `servers:create` and its placement and template prerequisites. Scope membership by itself grants no visibility or server action. A scoped role can reference zero or more available named server roles. An infrastructure-only role can provision with no inherited server access. The selection may combine permanent shipped roles, panel-created roles and published GameTemplate roles. Resolve each role against the server it covers. |
| Individual server | Ownership applies to the individual workload. A direct membership gives a person one or more live server roles or one or more explicitly selected custom actions on a particular server UID. Evaluate the operations below against this UID. It can receive the same action from a direct grant, any applicable direct or inherited server role, or a shipped role’s approved additions and active recommendations on the matching template. |

**Cluster → Roles & permissions** and **Users → Person → Access** display and edit the same cluster/namespace binding. The Cluster page shows roles eligible for the selected scope. A person with a direct server role can reach that server without a supplemental cluster grant. [Current panel permission catalog](../../../api/internal/rbac/catalog.go) · [Existing cluster grants](../../../docs/multicluster-ui.md#user-access)

Before saving an assignment, editing a live role, rebinding a replacement scope or removing access, show the person's effective rights before and after. For a shared role, show the affected assignees within the reviewer's visibility. When the scope role has no server-role references, show **No inherited server roles** and preview the scoped infrastructure rights. Show any inventory projection under its own permission. When it has server-role references, list the exact scope, all selected roles, each role’s current matches and future coverage, and the distinct total of matching servers. Show which matches gain visibility, which gain actions and which remain visible through another source. Label nonmatches within the reviewer’s authorized inventory. Show approved template additions and active recommendations for each selected shipped role. Report authorized coverage and indicate partial, last-known or unknown counts when visibility or availability limits the result. With roles selected, distinguish zero observed matches from unavailable inventory. Require a fresh preview if the reviewed grant or scope changes.

For each action, distinguish added, retained, lost and blocked access. Attribute it to the specific active panel or fleet grant, shipped or panel-created role, declared addition or separately activated recommendation for the template/base pair, optional template role, direct assignment, ownership or applicable admin Block. For example, a namespace's Viewer grants status and events on 12 servers. If the person's primary role independently grants `servers:read` there, identify the log and file access that survives removing Viewer. Apply the reviewer's own visibility to names, counts and grant details in both preview and effective-access views.

## What a grant selects

A grant names an action and, where required, a selector. The picker shows the expanded choices, affected targets and dependencies. Saving a group selection records its enumerated members. New action IDs and schema keys are opt-in. A previously selected common verb can become usable when a game gains an approved implementation with the same effect. Selecting a new named command requires a reviewed mapping, including when the template names it in an approved base-role addition. Suspend a changed command's grant until its new semantics and impact on live roles are approved. Server-role inheritance is optional on a scoped definition. A direct server assignment requires at least one named role or one explicit custom action. Reject empty direct invitations, and grant no discovery through a deny-only policy. Neither kind of assignment implies `server.view` by itself. Every usable server operation requires effective `server.view` on its UID. Show that dependency when selecting the operation.

For each action show **permitted**, **denied** or **unavailable on this server**. A person assigned the same role on a Factorio server and a CS2 server sees only the actions each target supports. A new sibling inherits all selected roles that apply to it through its scope bindings. Each selected shipped role contributes its approved additions and active recommendations for that effective GameTemplate. Direct membership on another server confers nothing there. On each request use the selected server’s live UID, trusted effective template and configured capabilities. An unavailable or unclassified operation stays closed. Check the same decision on the dashboard, API, local and remote dispatch, and any credential allowed to use that operation. A tab label, HTTP method or game name cannot authorize an operation.

### View prerequisites

Every mutation needs effective permission to view what it changes. The view and mutation may come from different assignments. Resolve both for this caller, credential, server UID and selected target **after Blocks**, on every request. A view on another server, field or path cannot satisfy the check. The editor shows each required view and its scope before saving. If a view is missing, the grantor may explicitly include it within their delegation ceiling. A stored action alone gives no implied read access. Withdrawing or blocking the last applicable view disables every dependent action on the next decision and closes affected streams within five seconds. The preview names the missing prerequisite and identifies any independent source that still supplies it.

| Mutation | Required view in addition to `server.view` on each participating server |
| --- | --- |
| Start, stop, restart or wake | The target is the server itself. Its basic status under `server.view` is sufficient. |
| Raw console input | `logs.live` on the server receiving the command. |
| Kick, ban, unban and allowlist changes | Kick requires `players.roster` for the target connection. Ban creation requires `players.bans` for the target ban list and, when selecting a live player, `players.roster` for that connection. Unban requires `players.bans` for the target entry. Allowlist add and remove require `allowlist.view`. Hidden platform IDs and ban reasons retain their separate gates. |
| Named actions and template-defined permissions | The approved mapping declares the view for its target and every classified effect. A whole-match pause can use `server.view`. A kick requires the roster and kick permissions, and a field edit needs its selected field view. An unclassified target or effect keeps the action unavailable. |
| File and directory mutations | Creating a file, directory or archive requires `files.list` covering the proposed entry. The parent view exposes the permitted path and its breadcrumbs. For nested creation use the nearest existing parent and authorize each new directory. Overwriting or deleting an existing file requires `files.read` on that file. Deleting a directory requires `files.list` on each directory and `files.read` on each file removed. Renaming checks the source and the destination, including an existing victim. Uploads and archives inherit their source and destination checks. Exact-target checks never require disclosing sibling entries. |
| Content installation, update, upload, removal and pack changes | `content.view` for the target server’s installed content. Selecting a project/version from the provider catalog also requires `content.browse` on that catalog. |
| Settings, credentials and networking entries | `settings.<section>.view` for every changed field/key. Tunnel credentials require the redacted credential field under `settings.networking.view`. Mapping changes require the mapping field under that same view. The redacted view reveals presence/status only for a secret. |
| Backups, restore requests and schedules | Backup create, delete and archive download require `backups.view` on the source UID. Upload to staging and subsequent confirmation each require `restores.view` on the destination UID. The [recovery rules](#recovery-targets) distinguish uploaded files from stored backups. Every schedule mutation requires `schedules.view` on its server. Retargeting checks both servers and the permitted destination. Apply the prerequisites for each resulting effect. |
| Membership | Invite, edit and remove each require `members.view` on the server. Invite uses exact-account lookup. Server membership visibility supplies no panel directory access. |

For a new child object, inspect its authorized parent collection before creation. For an existing object, inspect only the authorized projection. Never return a secret value to satisfy a view prerequisite. An admin Block of `server.view` withholds the UID from ordinary discovery, counts, direct reads and mutations, regardless of the other contributing grants. Close existing streams for that UID. Independent access to other UIDs and protected primary-panel-admin recovery still resolve normally.

For server deletion, data wipe and ownership transfer, evaluate `server.view` on the same live UID and the existing owner-or-target-admin authority before acting. An owner with a matching `server.view` Block cannot use any of the three routes, including by direct URL. Keep the ownership record. Removing that Block restores access only if the independent requirements still hold. A primary panel admin can inspect and remove the Block through the protected recovery path. A direct or inherited server Administrator role supplies no ownership authority.

### Player visibility and moderation

For each server, check what its effective module implements and what Gameplane can dispatch through that implementation. The agent advertises Kick, Ban and Unban separately from its declared player commands. An approved, typed module action can also implement a specific operation through its supported transport. A roster, a console or a supported Kick never establishes support for Ban. Disable an unavailable control and reject a direct request for it before dispatch. Use the same canonical permission, views and Blocks for dashboard controls, direct moderation requests and named module actions with that effect. [Agent capability discovery](../../../agent/internal/players/commander.go) · [Module action dispatch](../../../api/internal/ws/actions.go)

For example, a Block on `players.ban` denies the panel’s Ban action and any reviewed module button that bans a player. If the user still has effective `console.send`, show in the preview that they can type commands into the game, including a native ban command if the game accepts it. Gameplane checks `console.send` and its view prerequisites on raw input. A panel moderation grant or Block never grants, revokes or filters raw input.

`players.roster` exposes display names. `players.identityDetails` adds available persistent identifiers and faction to an independently authorized roster, operator or other player listing. `players.bans` exposes basic ban entries. Adding `players.banDetails` reveals the reason and source for entries the person may already see. Neither detail permission grants a list. Apply the same projection to summaries, hydrated entries, repeats of a field elsewhere in the payload, action results and streams. If a game returns a platform ID in the display-name slot, use an opaque label when that ID would be withheld. [Player fields](../../../agent/internal/players/players.go) · [Display name resolution](../../../api/internal/ws/players_hydrate.go)

A moderator can select a displayed player and kick them with `players.roster` and `players.kick`. Where a game needs a hidden identifier, resolve a short-lived opaque target reference on the server and bind it to the issuing account, server UID, operation and current target. Reject ambiguous, expired or cross-server references. A ban reviewer with only `players.bans` sees the basic list. Verify the reason, source, identifiers and raw game response remain hidden through the API and dashboard until the matching detail permissions are granted.

### Delegating membership and applying a Block

An owner or target-authorized admin may appoint a member manager. A shift lead with `server.view`, `members.view` and `members.invite` may inspect this server’s members and invite an existing account within their delegation ceiling. Editing and removing assignments each need their own mutation grant. On every mutation check the live role or individual grant against the caller’s delegable actions on that target, including selectors, prerequisites and dormant actions. A delegate may act only on assignments within that ceiling and cannot change their own rights or pass member-management duties onward. Only the built-in primary panel admin edits a reusable server role definition. For a scoped assignment, check the combined actions and selectors of all selected roles against the grantor’s authority for all applicable current and future servers, including approved template contributions and any `server.view` being granted. A later authorized edit takes effect for every assignee. [Delegation policy](../OPEN-DECISIONS.md#d2--who-can-delegate)

Only the built-in **primary panel admin** may add, edit or remove a **Block**. A Block on one server UID or an exact registered cluster or namespace identity takes precedence over matching ordinary allows, including a direct server grant, any applicable inherited server role, or the existing scope of a panel role. A namespace Block can restrict an existing entitlement and confers no access on its own. Names alone cannot rebind a Block to a replacement. Removing a direct assignment cannot remove a Block. Show the effective restriction and its source in an authorized preview. A Block cannot suppress the primary panel admin’s recovery authority. [Block policy](../OPEN-DECISIONS.md#d6--explicit-exceptions-to-inherited-access)

### Settings and module selectors

Use the section IDs `general`, `version`, `game`, `resources`, `networking`, `environment`, `lifecycle`, `placement` and `security`. For example, General can select the description, Networking can select the hostname or source ranges, and Resources can select the CPU limit separately from storage size. Selecting Version permits choosing a catalog entry when valid. Image overrides, service accounts, arbitrary Secret references, security-context exceptions and privileged capture settings retain their protected policies. A broad section grant expands only to explicitly reviewed fields. Typed writes check all changed and cleared fields, the expected resource version, and platform admission limits before making any mutation. `settings.security.view` selects `runAsUser`, `runAsGroup`, `fsGroup` and `volumeOwnershipCheck` independently, including the selected field’s desired/applied value, source and pending state. Omit changes to hidden fields from that projection. To edit or clear an override on an existing UID, require its field view, the matching `settings.security.edit` selector, an authorized write route and the protected `servers:security` check on the target cluster/namespace. A generic full-object update retains its separate `servers:write` route gate. On create or clone, check the caller’s destination provisioning authority, applicable views and `servers:security` on every supplied override. Existing broad keys cover only their documented baseline effects. Preserve stored protected fields on an unrelated edit and enforce the cluster root-override policy and existing validation for changes on every route. Preview when a saved value takes effect at the next start. A role limited to the ownership-check setting can never change the run-as user by sending both fields together. [Security field gate](../../../api/internal/handlers/security_overrides.go) · [Override API and root policy](../../030-security-context-overrides/contracts/api-server-security.md)

A module setting uses `settings.game.view/edit` with the trusted module identity, config key and approved definition. A game action uses `actions.run` with the trusted module identity, action ID and approved definition. The catalog can offer a cross-game name such as **Maximum players** by enumerating reviewed mappings, for example Factorio `MAX_PLAYERS` and Palworld `PLAYERS`. Each keeps its own validation. A manager may allow editing only Factorio `AUTOSAVE_INTERVAL` and leave `GAME_PASSWORD` untouched. Passwords stay write-only even with view and edit. Clearing a stored password needs its own key selected. The same rule applies to environment-backed keys and keys rendered into config files. Bind an approved definition to its stable source and a versioned semantic mapping that identifies the relevant commands, transport, parameter limits, key type, sensitivity, backing targets, required target views and effects. Pure display-label or translation updates can retain the mapping. A renamed key, reused action ID, changed command, newly permitted parameter, changed prerequisite or change in destination requires review before it can inherit a grant. Unmapped or insufficiently classified inputs are unavailable for narrow delegation. Validate the current mapping again on write/dispatch. An authorized edit may roll the workload per the module's normal apply policy. Surface that effect before save. ### File paths

Record selectors as a canonical, case-sensitive path under the agent data root plus an explicit **exact** or **subtree** mode. For example a subtree at `maps/event` includes `maps/event/round1` and excludes `maps/event-old`. Require an explicit root selection for volume-wide access. List only allowed entries and the minimum ancestor breadcrumbs to reach them. Recheck each resolved path at the agent’s descriptor-based filesystem boundary, including every multipart destination and every descended source or victim. Refuse traversal, ambiguous encodings and symlink redirection. Keep existing hidden-file rules and their narrow read exceptions. [File operations](../../../agent/internal/files/files.go) · [Descriptor-based confinement](../../../agent/internal/files/rooted_linux.go)

- `files.list` returns only visible entry names and the listing projection in an allowed directory. `files.stat` returns metadata for one authorized path. Requests outside the selector must not reveal whether the path exists. File contents and sibling listings have separate gates. An exact read or stat does not require a directory-wide listing. `files.read` allows reading bytes that a user can copy. The explicit download operation, including an SFTP read, checks both `files.read` and `files.download` on the file.
- Create-only writes must fail if the destination exists. The existing write endpoint can replace a file or create one. Require `files.write` to overwrite and `files.create` to create a missing destination. For upload, require `files.upload` and authorize creating or replacing each actual destination, plus `files.mkdir` on any implicitly created parent directories. Check the creation or replacement atomically with the filesystem operation. A late unauthorized part must not leave earlier files or directories behind.
- Rename requires `files.rename` on both canonical paths on the same UID, `files.delete` and its required views on the source, and `files.create` (or `files.mkdir` for a directory) and the parent view at an unused destination. If overwrite is supported and requested, check authorization to replace the existing victim, using `files.write` and `files.read` for a file, or `files.delete` and `files.list` for an empty directory being replaced. Check the corresponding source and resulting destination paths for every moved descendant. Deny a mixed tree before moving any entry. The agent’s protected-path, no-overwrite, type and confinement rules still apply. [Agent rename](../../../agent/internal/files/rename_linux.go)
- For a ZIP download, require `files.archiveDownload` and read/download permission on every source. Writing a ZIP on the server requires `files.archiveCreate`, read permission on every source and create permission on the new destination. Archiving a directory also enumerates its entries, requiring `files.list` on directories traversed. Recursive archive/delete must fail before exporting or deleting any part of a mixed-authorization selection. Preserve the agent’s tighter restrictions on destinations, selection overlap and hidden entries. [Archive behavior](../../../agent/internal/files/archive_linux.go)
- A full raw config file may contain many keys or secrets. A one-key settings grant never opens or rewrites that file. Withhold raw file permissions on protected generated configs, content manifests and other managed paths from narrow roles. A broader raw file or unrestricted console grant can independently change game state. The preview names that authority separately, including when inherited from another role.

At cutover remove the collaborator and supplemental-grant sources. Preserve the existing SFTP reach of surviving primary grants and ownership under the new view and Block rules. Show the compatibility source when it supplies SFTP or file rights. For granular roles `sftp.connect` is independent of the file rights below. Owning credentials or managing an endpoint supplies neither. Keep the existing session-token route and cluster restrictions. ### Scheduled and indirect actions

Classify each changed field after resolving defaults and the stored schedule. `schedules.edit` covers ordinary timing and job options, including cron, deadline, quiesce and power policy. Pause and resume each authorize only their transition. `schedules.retention` covers setting or clearing retention and entering or leaving the destructive `Replace` concurrency policy. `schedules.retarget` covers changing the workload or approved backup destination. Authorize the change on both old and new server UIDs and check the new destination. Creating a schedule needs `schedules.create` on its initial target. Restic requires an approved repository. A CSI volume snapshot has no repository reference and needs no Restic destination permission. An initial pruning policy or `Replace` also needs `schedules.retention`. A combined change needs every applicable grant. Reject it atomically if a field or resulting effect is unauthorized. [BackupSchedule fields](../../../operator/api/v1alpha1/backupschedule_types.go)

On create, change or resume, verify the resulting job's effects. Ordinary jobs need `backups.view` and `backups.create`, stop-copy-restart needs both `power.stop` and `power.start`, and pruning or `Replace` needs `backups.delete`. Pausing alone stops future execution and requires `schedules.view` and `schedules.pause` on the visible server. Display all effects in preview and check applicable effects on one-off backups too. At execution, revalidate the server UID and any destination required by the strategy. Verify a CSI volume-snapshot schedule succeeds without repository access. An admitted server-owned schedule can continue after its creator leaves. Verify that a resume-only operator with the required views and job effect grants can resume it but cannot change the cron, add pruning, swap the target or sneak any such change into the same request. [Schedule execution](../../../operator/internal/controller/backupschedule_controller.go)

### Recovery targets

A recovery from a stored backup checks the backup UID and its source server UID. The backup and target must share the Restore’s registered cluster and namespace. A client-uploaded archive has no source Backup object. Bind that request to its live destination server UID before staging any bytes. For both forms, resolve the strategy and target on the server and repeat identity checks at execution, including on generic Restore APIs and remote gateways. [Restore contract](../../../operator/api/v1alpha1/restore_types.go) · [Archive routes](../../041-downloadable-backup-archives/contracts/api.md)

| Operation | Required authority and release case |
| --- | --- |
| Restic overwrite of an existing server | Require `backups.view` on the source UID and both `restores.view` and `restores.applyExisting` on the destination UID. Preview suspension and overwrite of that server. A pre-created empty destination is still an existing server. Refuse the restore if the destination disappears or is replaced. |
| CSI recovery into a new server | Require `backups.view`, `restores.view` and `restores.createNew` on the source UID, and independent provisioning authority with its placement and template prerequisites. Require a valid, unused server name in the backup’s namespace. Fail on collision, including a server appearing after preview. A recovery operator with these grants can recover a new server and cannot overwrite an existing one. |
| Download a completed archive-capable backup | Require `server.view`, `backups.view` and `backups.download` on the verified source UID before creating a BackupExport or returning bytes in either format. Preserve the snapshot-strategy refusal. The grant exports the whole backup, including captured files that may contain passwords. State that scope in the picker and preview. A metadata-only reader can inspect the backup without exporting it. |
| Stage an uploaded archive | Require `server.view`, `restores.view` and `restores.upload` on the chosen existing destination UID. Bind both managed and plain archives to that UID and the new Restore UID. Preserve archive checks, size limits and any required template confirmation. Accepting the upload changes only staging. An uploader can inspect the authorized staging status and cannot overwrite by setting confirmation fields on create or update. |
| Confirm the staged overwrite | Resolve the stored Restore and original target UID. Require `server.view`, `restores.view` and `restores.applyExisting` on that target for the confirming actor. Match the observed Restore UID, generation and `AwaitingConfirmation` state. A second authorized person can confirm a staged archive without `restores.upload`. Block or replacement of the target between stage and confirmation refuses the overwrite. |

## Default base server roles

Viewer, Power User, Operator and Administrator are permanent, editable roles with stable IDs. The built-in primary panel admin can edit their permissions after impact review. Reject requests to retire or delete a shipped role. The admin can create and retire custom server roles. Retirement removes a custom role from new selections. Existing direct assignments and scoped bindings keep their live reference, including when a new server inherits through an existing binding. A scope definition referencing a retired role must replace or remove it before assigning a new person. Allow deletion of a custom definition only after its last reference is removed.

When defining a cluster or namespace role, leave server-role inheritance empty for infrastructure-only duties or select the available named server roles to inherit. Any combination of shipped, panel-created and published template roles is valid within the grantor’s authority. Evaluate the selection separately for every current and future server in scope. Only applicable roles contribute their actions and selectors. Visibility of the server requires an effective `server.view` from a matching role or an independent source. An unmatched server stays hidden unless another grant supplies that view. A panel-created, game-neutral **Backup Operator** can be selected alone. If its definition includes `server.view` for all games, it supplies basic visibility throughout the scope. A shipped role’s template additions follow only that role’s stable ID.

For example, select **CS2 Match referee** alone for a namespace with two CS2 servers and one Valheim server. The referee role in the example below explicitly grants `server.view`, Pause and Resume on verified matching CS2 servers. The assignee sees those two servers and can referee them. Valheim is absent from their server list and counts unless another source grants it. The admin’s preview shows two current matches, the applicable rights and the same rule for future servers. New matching CS2 servers inherit the role and other games receive nothing from it. Withdrawal or a change of effective template reevaluates each contribution, including any view it supplied, under the normal Block and revocation rules.

| Base server role | Initial grant | Number of distinct action IDs |
| --- | --- | --- |
| Viewer | `server.view`, `events.view` for identity, status and filtered workload events | 2 |
| Power User | Viewer plus `power.start`, `power.stop`, `power.restart`, `power.wake`, `logs.live`, `logs.history`, `console.send` | 9 |
| Operator | Power User plus `files.list`, `files.stat`, `files.read`, `files.create`, `files.write`, `files.mkdir` on approved routine data paths, and `settings.general.view`, `settings.general.edit` on the server description | 17 |
| Administrator | All 91 common server actions in [Operations](#operations), with the selector and protected-operation rules below | 91 |

These are cumulative **initial** sets. Seed each live role with its complete enumerated action IDs and selectors. Later edits to one role update that role's assignees under FR-03. Evaluate each selected role through the same assignment and Block rules. Distinguish the server **Operator** and **Administrator** from similarly named panel or fleet roles in both pickers.

**Viewer and Power User.** Viewer sees basic status and filtered events. Log text, player identities and audit activity have independent gates. Power User can follow current output, read history, and submit commands to the game console. Wake works when supported. Bulk log export uses `logs.download`, available in Administrator or a custom grant. The preview for each role containing `console.send` must explain that the game may accept administrative commands, including changes to in-game settings and moderation. A narrow custom role can instead select reviewed named commands.

**Operator.** Seed the General selector with the description (`metadata.annotations["gameplane.local/description"]`). General also displays an image override and arbitrary Kubernetes labels, which are outside this selector. The common Operator seed grants typed edits only to the description. A template may add a reviewed non-critical game setting for Operator, scoped to that field. Critical settings retain their own protections. Each file operation takes an exact path or subtree keyed to the trusted GameTemplate identity. Gameplane ships the reviewed mappings for bundled templates with the initial role. A module author can propose additional selectors for its actual data layout. A template can include them in its declared Operator additions or offer them as an optional recommendation. Both follow the [template approval rules](#gametemplate-roles). Exact-path metadata is available through `files.stat`. The Operator seed has no `sftp.connect` or bulk-transfer grants. Permit creation and directory creation only where the approved selector covers the new destination. Show the actual paths in the preview. Choose paths for ordinary editable data and verify how the game consumes those files. Exclude secrets, generated configuration, startup scripts, executable/plugin directories, manifests and files that can change protected settings indirectly. If a game has no reviewed safe path, display file editing as unavailable there and retain the description grant. Adding paths to a live preset requires the same impact review as adding fields or game actions. [General settings form](../../../web/src/routes/tabs/settings/General.tsx) · [File paths](#file-paths)

**Administrator.** Seed all 91 currently defined IDs individually. For files, explicitly select the server data root as a subtree subject to agent confinement and protected paths. For typed settings and named game actions, enumerate the currently approved, delegable fields and trusted action mappings. Include `backups.download`, `restores.upload` and `sftp.connect`. Security field selectors are usable for writes only with the separate scoped fleet authority. Apply existing content, credential and backup destination policies. Expose a new template-specific selector to Administrator through the approved template’s declared Administrator additions, a separately activated recommendation, or an explicit grant. A new action ID, game command or schema field requires explicit selection. Each operation still checks server capability, applicable Blocks, admission, credential limits and any independent source, destination or placement permission.

Administrator can ban or unban on modules that support the respective action, manage direct members within the delegation ceiling, replace content, remove files, backups, schedules or mappings, and apply an authorized restore that overwrites server data. Appointing another membership manager requires independent owner or target-admin authority under the delegation rules. Holding the four `members.*` actions alone lets an Administrator manage ordinary direct grants within its ceiling. The separate GameServer delete, wipe, ownership transfer, owner-personal public shares and personal credential controls keep their existing gates. The role grants no automatic authority over siblings, panel administration, privileged node diagnostics, scoped bindings or Blocks. The impact preview distinguishes deleting a child resource from deleting the server itself and names destructive actions before a grant is confirmed.

On the breaking beta upgrade, prior server collaborator entries and supplemental cluster/namespace grants cease granting access. Preserve ownership and primary panel assignments, including manual and OIDC/Helm assignments. An administrator uses the review banner to assign fresh access. On one server, explicitly choose at least one live role or custom permission. For a cluster or namespace, choose a scoped role and preview its infrastructure rights. If the role also grants server-role inheritance, preview which servers match and the visibility and actions each selected role supplies. Leaving the item unassigned grants nothing through that source.

## GameTemplate roles

A GameTemplate may use any of the four declarations below. Gameplane owns the common action IDs, checks the approved scope and selectors, and enforces their actual effects on every transport. The built-in primary panel admin reviews the template’s permission declarations and their effective impact before accepting them.

| Declaration | What approval does |
| --- | --- |
| **Permission** | Publishes an independently selectable template permission for a custom grant or live role. Its stable local ID resolves to an enumerated canonical action and explicit reviewed selectors, such as one game command or editable field. |
| **Declared base-role addition** (`baseRoleAdditions`) | The template assigns the listed permissions to an explicit base on servers using this template. Approval of the template’s permission declarations activates these additions together. Every matching direct or inherited holder of the named base receives them on the next access decision. No second activation or per-person assignment is required. |
| **Optional base-role recommendation** (`baseRoleRecommendations`) | Offers listed permissions for an explicit base. Approving the declaration set leaves the recommendation available for a separate decision. The primary panel admin can activate, change or withdraw the reviewed selection for that template/base pair. |
| **Optional named role** | Publishes a reusable bundle of enumerated local references to reviewed server permissions. An authorized inviter must assign it on a matching UID or select it among the server roles in a cluster/namespace definition before anyone receives it. |

**Authoring example.** This proposed fragment lives under `GameTemplate.spec.serverAccess`. CS2 already declares the underlying commands in its action catalog. Each can be granted individually. The author adds both to Administrator, recommends both for Power User, and offers them with their server status prerequisite in the optional Match referee role. [Existing CS2 actions](https://github.com/GameplanePanel/module/blob/c310076716ce8ccc63619f88ddc69547415dcfc2/cs2/template.yaml)

```yaml
spec:
  serverAccess:
    permissions:
      - id: match-status
        action: server.view
      - id: pause
        action: actions.run
        selector: {actionId: pause-match}
      - id: resume
        action: actions.run
        selector: {actionId: unpause-match}
    baseRoleAdditions:
      - baseRole: administrator
        permissions: [pause, resume]
    baseRoleRecommendations:
      - baseRole: power-user
        permissions: [pause, resume]
    roles:
      - id: match-referee
        displayName: Match referee
        permissions: [match-status, pause, resume]
```

**Validation and authority.** In a declared addition, recommendation or optional role, a bare local ID references a permission from the same declaration. To include a common action, declare a local permission for that canonical ID and its required selectors, then reference that local ID. Resolve local references by trusted template identity, declaration kind and stable local ID. A display name, game name, package version or ID copied from another template cannot establish that identity. Resolve named actions against the trusted effective module. Check command, transport, parameters, backing data, sensitivity, and canonical effects. Reject duplicate identities, unknown or cross-template references, wildcard expansions, unsupported selectors and operations outside ordinary server authority. An action that kicks requires the canonical kick authority. A declaration cannot create accounts or memberships, grant fleet or owner powers, or bypass Blocks, hidden fields, protected files or credential limits.

Use the stable base IDs `viewer`, `power-user`, `operator` and `administrator`. Validate declared additions and recommendations against the effects permitted for that base. Viewer can gain basic read-only information, Power User routine game operations, Operator reviewed non-critical maintenance, and Administrator approved server controls. Reject a write disguised as a Viewer status check or a credential change assigned to Operator. Name every intended base explicitly. The shipped common grants are cumulative (2/9/17/91). GameTemplate contributions apply only to their named bases. An addition for Power User does not flow upward to Operator or Administrator. Additional selectors for an existing action ID do not create new common actions.

**Approval and effective access.** One approval covers current and future installations within the same panel that can verify the same module and reviewed permissions. Match the verified publisher, source and logical module identity, the approved declaration and its targets, and the meaning of each permission used on the server’s effective snapshot. Compare canonical operations, selectors, prerequisites, parameters, transport, backing fields, sensitivity and effects. An installation alias, cluster name or package version alone cannot establish the match. A matching alias on another cluster reuses the current panel decision. A fork, an unverified change of publisher or source, a changed permission, or a new role target needs its own review. Local or unsigned templates remain eligible for a separate installation-specific approval. Another panel makes its own decisions. Installation and rollout consume the applicable decision without writing one. [Approval sharing decision](../OPEN-DECISIONS.md#decided--sharing-template-approvals-across-installations)

In one before/after preview, show every declared addition to each named shipped role, the matching installations and future coverage. The built-in primary panel admin accepts or declines the declared additions as a set. Acceptance publishes the referenced permissions and atomically replaces the approved declared additions. Declining preserves previously approved contributions whose underlying semantics still verify. Review a changed declaration before activating its new rights, even if the canonical permission was approved elsewhere. A primary panel admin can withdraw an approved contribution across its approval scope. A later review must show restoring it as a gain before the admin confirms it. Reinstall, rollback or a new matching alias observes the current withdrawal.

Track declared additions and independently activated recommendations as distinct sources keyed by trusted template identity and stable base ID, separate from the common role definition. An unaccepted recommendation grants nothing. Changing or removing a recommendation in a package leaves a previously activated selection in place while its underlying permissions still verify. Changing a declared addition takes effect with approval of the new declaration set. Deduplicate identical effective actions and selectors across both sources and optional roles. Retain all grant sources for the preview and audit. Withdrawing an individual source removes only its contribution. Controls, assignments, parent scopes and Blocks still apply.

When a permission is removed or its command, parameters, target or effects change meaning, suspend its affected contributions on each server whose effective snapshot no longer verifies the reviewed semantics. Preview the impact on explicit custom selections, optional roles and both kinds of base contributions before reauthorization. A rollback or reappearance of an old ID cannot lift a suspension. Display-only renames retain stable identity. Check the effective definition on each target during a rolling update. A cluster using verified semantics can retain its authorized operations while another awaits review.

Before committing any live grant change, preview the before/after effective actions and selectors, including unchanged rights supplied elsewhere. Identify the verified module, matching current installations across clusters, each affected shipped role and source (declared addition or activated recommendation), optional roles, explicitly selected custom permissions and affected people. Distinguish direct assignments on one UID from cluster/namespace inheritance on distinct matching servers. Show which future servers can inherit the change. Count overlaps once and label partial, last-known or unknown inventories. Validate the reviewer, approved semantics and policy snapshot again in the committing transaction. A changed proposal, role, Block or assignment that invalidates the reviewed effect requires a fresh preview. Committed changes take effect on the next access decision with the existing stream-revocation rules.

In the example, approving the CS2 declaration set immediately adds Pause and Resume to Administrator on matching servers. A person with Administrator on one CS2 UID gains the controls there. A namespace Administrator gains them on every existing and future CS2 server in that namespace. A whole-cluster Administrator also gains them on CS2 servers in newly managed namespaces. Valheim Administrators and custom copies of Administrator receive nothing from the CS2 addition. The Power User recommendation stays inactive until explicitly accepted. A tournament namespace can independently select its panel-created **Backup Operator** and **CS2 Match referee**. A second cluster in the same panel using the identical verified CS2 module under a different name reuses the approval. A person receives match controls there only if their direct or scoped grants apply to that server. Withdrawing the declared Administrator addition leaves an independently assigned referee’s match controls intact, subject to Blocks. A changed pause command closes through each dependent source on the affected installation pending reapproval. Resume can still work. Raw console authority appears separately in the preview.
