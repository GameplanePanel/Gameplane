# Server permission catalog

The 84 common server action IDs proposed for [#1063](https://github.com/GameplanePanel/Gameplane/issues/1063) appear in the Operations table, counting view and edit separately for each of the eight settings sections. Fields, paths and template-specific actions are selectors. The operations below exist at baseline `7ea5be6a` unless marked as proposed. Their fine-grained authorization, the presets and the member-management APIs are new. A direct assignment names one server UID. A cluster or namespace role carries server permissions inherited across its whole scope.

## Where an assignment applies

| Access layer | Permission source and example |
| --- | --- |
| Panel | The primary panel role controls installation-wide operations. Give a language editor `config:i18n:manage` for the instance default language. The [panel and fleet catalog](fleet-permissions.md) defines the account, role, settings, audit and infrastructure duties, including protected admin operations and existing OIDC/Helm grants. |
| Cluster or namespace | A binding applies eligible [fleet permissions](fleet-permissions.md) to the chosen cluster or namespace. Grant provisioning with `servers:create` and access to the selected template. Each new scoped role also references exactly one common base server role, plus any additional roles selected for specific GameTemplates. Existing broad grants keep their documented coverage. |
| Individual server | Ownership applies to the individual workload. A direct membership gives a person one or more live server roles or an explicit custom grant on a particular server UID. Evaluate the operations below against this UID. It can receive the same action from a direct grant, the required scoped base role or a matching GameTemplate role. |

**Cluster → Roles & permissions** and **Users → Person → Access** display and edit the same cluster/namespace binding. The Cluster page shows roles eligible for the selected scope. A person with a direct server role can reach that server without a supplemental cluster grant. [Current panel permission catalog](../../../api/internal/rbac/catalog.go) · [Existing cluster grants](../../../docs/multicluster-ui.md#user-access)

Before saving an assignment, editing a live role, converting a legacy binding or removing access, show the person's effective rights before and after. For a shared role, show the affected assignees within the reviewer's visibility. Identify the exact scope, base, count of distinct existing servers, each selected GameTemplate role and matching count, and which future servers inherit each role. Report authorized coverage and indicate partial, last-known or unknown counts when visibility or availability limits the result. Show zero only for confirmed empty coverage. Require a fresh preview if the reviewed grant or scope changes.

For each action, distinguish added, retained, lost and blocked access. Attribute it to the specific active panel or fleet grant (including a legacy grant), inherited base, template addition, direct assignment, ownership or applicable admin Block. For example, a namespace's Viewer grants status and events on 12 servers. If an existing `servers:read` grant also permits logs and files there, show both sources and identify the access that survives removing Viewer. Apply the reviewer's own visibility to names, counts and grant details in both preview and effective-access views.

## What a grant selects

A grant names an action and, where required, a selector. The picker shows the expanded choices, affected targets and dependencies. Saving a group selection records its enumerated members. New action IDs and schema keys are opt-in. A previously selected common verb can become usable when a game gains an approved implementation with the same effect. A new named command requires a reviewed mapping and explicit selection. Suspend a changed command's grant until its new semantics and impact on live roles are approved. An empty or deny-only assignment grants nothing, including discovery. An assignment allowing a server operation includes `server.view` in the preview.

For each action show **permitted**, **denied** or **unavailable on this server**. A person assigned the same role on a Factorio server and a CS2 server sees only the actions each target supports. A new sibling inherits the base of every applicable scope binding and the selected additions for its effective GameTemplate. Direct membership on another server confers nothing there. On each request use the selected server’s live UID, trusted effective template and configured capabilities. An unavailable or unclassified operation stays closed. Check the same decision on the dashboard, API, local and remote dispatch, and any credential allowed to use that operation. A tab label, HTTP method or game name cannot authorize an operation.

## Operations

| Family | Proposed action IDs | Scope and enforcement |
| --- | --- | --- |
| Overview | `server.view`, `events.view`, `metrics.view` | Basic identity and phase, filtered workload events, and selected module status metrics respectively. Project each event and metric before returning it. Roster names, file paths, console text, actor audit records and sibling-server references have separate visibility rules. |
| Server activity | `activity.view` | Proposed server-specific view of who did what. Return only attributable, redacted entries for this UID. Omit historical entries with ambiguous targets, other subjects in bulk changes, and panel-wide administrative details. Viewing workload events does not disclose this feed. |
| Power | `power.start`, `power.stop`, `power.restart`, `power.wake` | Each allows one lifecycle operation. Changing `spec.suspend` through another control requires the corresponding stop/start grant. Wake depends on the server’s idle configuration. |
| Console and logs | `logs.live`, `logs.history`, `logs.download`, `console.send` | Authorize live output, stored history and bulk export independently. Pod startup logs also require the matching output permission. A duplex console/PTY requires both `console.send` and `logs.live`. An input-only grant can be offered only on a transport that can suppress output. Raw commands can exercise the game’s own administrative powers. Show that explicitly in the picker. |
| Players | `players.count`, `players.roster`, `players.identityDetails`, `players.bans`, `players.banDetails`, `players.operators`, `players.kick`, `players.ban`, `players.unban` | Separate the anonymous count, roster display names, identifying details, basic ban list, ban details and operator list. Kick affects the current connection. Ban and unban are independent. Apply the player visibility rules below on all transports. |
| Allowlist | `allowlist.view`, `allowlist.add`, `allowlist.remove` | Act on the game’s declared allowlist. These entries govern admission to the game. Panel-account membership is a separate family. |
| Named game actions | `actions.run` with a reviewed module/action selector | Publish only a selected action with its validated parameters and classified effects. Both RCON and stdin dispatch use this decision. Where a named action provides an existing operation, use its canonical permission or require it alongside the named action. A template button cannot bypass a ban or power check. |
| Files | `files.list`, `files.read`, `files.download`, `files.create`, `files.write`, `files.upload`, `files.mkdir`, `files.delete`, `files.archiveDownload`, `files.archiveCreate` | Each takes exact paths or directory subtrees below the selected server’s data root. Compound operations also check their underlying reads and mutations. See the path rules below. |
| Mods, plugins and packs | `content.view`, `content.browse`, `content.install`, `content.update`, `content.installUrl`, `content.upload`, `content.remove`, `content.packInstall`, `content.packReplace`, `content.packRemove` | Resolve catalog installs and updates from approved provider/project/version on the server. Update covers replacing an installed version of the same approved project. Direct URL and binary upload are separate choices. Diff bulk replacements and authorize additions, updates and removals individually. Distinguish first pack install, replacing/downgrading the active pack and removing it. Check underlying actions on dependency-mode packs. Preserve loader/provider/host policy and display backup and restart effects. Provider credential management stays in the fleet catalog. |
| Settings | `settings.<section>.view`, `settings.<section>.edit`, `tunnelCredentials.replace`, `tunnelCredentials.remove` | Each settings grant selects explicit fields or reviewed schema keys. Edit includes the selected redacted view. A credential operation exposes only its presence and outcome. Use the same checks wherever a setting or credential can change. |
| Networking entries | `network.mappings.add`, `network.mappings.edit`, `network.mappings.remove` | Apply to supported per-server mapping rows, such as FRP remote ports. View uses the redacted networking field. Require the relevant operation for each entry changed by a submitted list, including clearing it. Check the same changes on a permitted generic save, including any explicit scope block on an otherwise broad fleet writer. A mapping grant never authorizes changing public exposure, allowed source ranges or credentials. |
| Backups and restores | `backups.view`, `backups.create`, `backups.delete`, `restores.view`, `restores.applyExisting`, `restores.createNew` | Inspect recovery separately from overwriting an existing target or creating a new server from a backup. Check the source, target and provisioning requirements below. |
| Backup schedules | `schedules.view`, `schedules.create`, `schedules.edit`, `schedules.pause`, `schedules.resume`, `schedules.retention`, `schedules.retarget`, `schedules.delete` | Grant routine schedule edits, pause, resume, changes to destructive policy, and retargeting independently. Check all changed fields and resulting backup effects. |
| Access management | `members.view`, `members.invite`, `members.edit`, `members.remove` | Grant each independently on the target. View lists its members, invite grants an existing account access, edit changes a member’s direct role or individual permissions, and remove revokes a direct assignment. Each mutation enforces the delegation ceiling below. Account provisioning, fleet role management and ownership transfer retain their own gates. |

The baseline includes a separate same-namespace clone path with ownership semantics. Preserve that path in the frozen legacy mapping. Deleting a server, wiping its data, transferring ownership, managing personal public shares and accessing node diagnostics retain their existing constraints. Traffic capture requires the appropriate [fleet permission](fleet-permissions.md) and existing deployment controls. The new presets grant none of these operations. Server-scoped SFTP credentials, backup archive download or locking, general-purpose scheduled commands, managed database administration and a generic Files “extract” operation have no corresponding baseline control to enable. The separate [SFTP design](../../040-sftp-access/spec.md) specifies per-cluster endpoints, personal credentials and the same per-operation authorization as the Files tab. When both features ship, enforce the selected server UID, file action, path and applicable Blocks on that transport as well. A loader that unpacks a supported plugin package is part of content installation. ### Player visibility and moderation

`players.roster` exposes display names. `players.identityDetails` adds available persistent identifiers and faction to an independently authorized roster, operator or other player listing. `players.bans` exposes basic ban entries. Adding `players.banDetails` reveals the reason and source for entries the person may already see. Neither detail permission grants a list. Apply the same projection to summaries, hydrated entries, repeats of a field elsewhere in the payload, action results and streams. If a game returns a platform ID in the display-name slot, use an opaque label when that ID would be withheld. [Player fields](../../../agent/internal/players/players.go) · [Display name resolution](../../../api/internal/ws/players_hydrate.go)

A moderator can select a displayed player and kick them with `players.roster` and `players.kick`. Where a game needs a hidden identifier, resolve a short-lived opaque target reference on the server and bind it to the issuing account, server UID, operation and current target. Reject ambiguous, expired or cross-server references. A ban reviewer with only `players.bans` sees the basic list. Verify the reason, source, identifiers and raw game response remain hidden through the API and dashboard until the matching detail permissions are granted.

### Delegating membership and applying a Block

An owner or target-authorized admin may appoint a member manager and select which of the four duties they can perform there. For example, a shift lead with only `members.invite` may assign an existing account a permitted role on that server. Listing members, changing existing assignments and removing them each require their own permission. On every mutation check the live role or individual grant against the caller’s delegable actions on that target, including selectors and dormant actions. A delegate may act only on assignments within that ceiling and cannot change their own rights or pass member-management duties onward. Only the built-in primary panel admin edits a reusable server role definition. A later authorized edit takes effect for every assignee. [Delegation policy](../OPEN-DECISIONS.md#d2--who-can-delegate)

Only the built-in **primary panel admin** may add, edit or remove a **Block**. A Block on one server UID or an exact cluster/namespace takes precedence over matching ordinary allows, including a direct server grant, an inherited base or GameTemplate role, or the existing scope of a panel role. A namespace Block can restrict an existing entitlement and confers no access on its own. Removing a direct assignment cannot remove a Block. Show the effective restriction and its source in an authorized preview. A Block cannot suppress the primary panel admin’s recovery authority. [Block policy](../OPEN-DECISIONS.md#d6--explicit-exceptions-to-inherited-access)

### Settings and module selectors

Use the section IDs `general`, `version`, `game`, `resources`, `networking`, `environment`, `lifecycle` and `placement`. For example, General can select the description, Networking can select the hostname or source ranges, and Resources can select the CPU limit separately from storage size. Selecting Version permits choosing a catalog entry when valid. Image overrides, service accounts, arbitrary Secret references, security-context exceptions and privileged capture settings retain their protected policies. A broad section grant expands only to explicitly reviewed fields. Typed writes check all changed and cleared fields, the expected resource version, and platform admission limits before making any mutation. [Settings forms](../../../web/src/routes/tabs/settings/) · [Protected fields](../../../api/internal/handlers/resources.go)

A module setting uses `settings.game.view/edit` with the trusted module identity, config key and approved definition. A game action uses `actions.run` with the trusted module identity, action ID and approved definition. The catalog can offer a cross-game name such as **Maximum players** by enumerating reviewed mappings, for example Factorio `MAX_PLAYERS` and Palworld `PLAYERS`. Each keeps its own validation. A manager may allow editing only Factorio `AUTOSAVE_INTERVAL` and leave `GAME_PASSWORD` untouched. Passwords stay write-only even with view and edit. Clearing a stored password needs its own key selected. The same rule applies to environment-backed keys and keys rendered into config files. [Game configuration](../../../docs/module-authoring.md#editing-configuration-after-creation) · [Factorio template](https://github.com/GameplanePanel/module/blob/c310076716ce8ccc63619f88ddc69547415dcfc2/factorio/template.yaml) · [Palworld template](https://github.com/GameplanePanel/module/blob/c310076716ce8ccc63619f88ddc69547415dcfc2/palworld/template.yaml)

Bind an approved definition to its stable source and a versioned semantic mapping that identifies the relevant commands, transport, parameter limits, key type, sensitivity, backing targets and effects. Pure display-label or translation updates can retain the mapping. A renamed key, reused action ID, changed command, newly permitted parameter or change in destination requires review before it can inherit a grant. Unmapped or insufficiently classified inputs are unavailable for narrow delegation. Validate the current mapping again on write/dispatch. An authorized edit may roll the workload per the module's normal apply policy. Surface that effect before save. [Module actions](../../../api/internal/ws/actions.go) · [Template rollouts](../../../docs/template-rollouts.md)

One dashboard action can invoke more than its name suggests. CS2 `pause-match` and `unpause-match` affect match play. Granting them does not include `restart-round`, `change-map` or raw console input. Palworld’s `announce-restart` actually issues a delayed shutdown to restart the server, so classify it with the restart authority. Palworld exposes its roster over REST and omits kick/ban by display name. Terraria implements `kick-player` and `ban-player` via stdin. A reviewed mapping to `players.kick` must never activate the ban action. [CS2 template](https://github.com/GameplanePanel/module/blob/c310076716ce8ccc63619f88ddc69547415dcfc2/cs2/template.yaml) · [Palworld template](https://github.com/GameplanePanel/module/blob/c310076716ce8ccc63619f88ddc69547415dcfc2/palworld/template.yaml) · [Terraria template](https://github.com/GameplanePanel/module/blob/c310076716ce8ccc63619f88ddc69547415dcfc2/terraria/template.yaml)

### File paths

Record selectors as a canonical, case-sensitive path under the agent data root plus an explicit **exact** or **subtree** mode. For example a subtree at `maps/event` includes `maps/event/round1` and excludes `maps/event-old`. Require an explicit root selection for volume-wide access. List only allowed entries and the minimum ancestor breadcrumbs to reach them. Recheck each resolved path at the agent’s descriptor-based filesystem boundary, including every multipart destination and every descended source or victim. Refuse traversal, ambiguous encodings and symlink redirection. Keep existing hidden-file rules and their narrow read exceptions. [File operations](../../../agent/internal/files/files.go) · [Descriptor-based confinement](../../../agent/internal/files/rooted_linux.go)

- An exact-path read is useful without directory-wide listing. A download also requires content access to that path. Read access exposes the bytes a person views. The download grant controls the separate download endpoint.
- Create-only writes must fail if the destination exists. The existing write endpoint can replace a file or create one. Require `files.write` to overwrite and `files.create` to create a missing destination. For upload, require `files.upload` and authorize creating or replacing each actual destination, plus `files.mkdir` on any implicitly created parent directories. Check the creation or replacement atomically with the filesystem operation. A late unauthorized part must not leave earlier files or directories behind.
- For a ZIP download, require `files.archiveDownload` and read/download permission on every source. Writing a ZIP on the server requires `files.archiveCreate`, read permission on every source and create permission on the new destination. Archiving a directory also enumerates its entries, requiring `files.list` on directories traversed. Recursive archive/delete must fail before exporting or deleting any part of a mixed-authorization selection. Preserve the agent’s tighter restrictions on destinations, selection overlap and hidden entries. [Archive behavior](../../../agent/internal/files/archive_linux.go)
- A full raw config file may contain many keys or secrets. A one-key settings grant never opens or rewrites that file. Withhold raw file permissions on protected generated configs, content manifests and other managed paths from narrow roles. A broader raw file or unrestricted console grant can independently change game state. The preview names that authority separately, including when inherited from another role.

### Scheduled and indirect actions

Classify each changed field after resolving defaults and the stored schedule. `schedules.edit` covers ordinary timing and job options, including cron, deadline, quiesce and power policy. Pause and resume each authorize only their transition. `schedules.retention` covers setting or clearing retention and entering or leaving the destructive `Replace` concurrency policy. `schedules.retarget` covers changing the workload or approved backup destination. Authorize the change on both old and new server UIDs and check the new destination. Creating a schedule needs `schedules.create` on its initial target. Restic requires an approved repository. A CSI volume snapshot has no repository reference and needs no Restic destination permission. An initial pruning policy or `Replace` also needs `schedules.retention`. A combined change needs every applicable grant. Reject it atomically if a field or resulting effect is unauthorized. [BackupSchedule fields](../../../operator/api/v1alpha1/backupschedule_types.go)

On create, change or resume, verify the resulting job's effects. Ordinary jobs need `backups.create`, stop-copy-restart needs both `power.stop` and `power.start`, and pruning or `Replace` needs `backups.delete`. Pausing alone stops future execution and requires only `schedules.pause`. Display all effects in preview and check applicable effects on one-off backups too. At execution, revalidate the server UID and any destination required by the strategy. Verify a CSI volume-snapshot schedule succeeds without repository access. An admitted server-owned schedule can continue after its creator leaves. Verify that a resume-only operator with the job's effect grants can resume it but cannot change the cron, add pruning, swap the target or sneak any such change into the same request. [Schedule execution](../../../operator/internal/controller/backupschedule_controller.go)

### Recovery targets

Resolve the source backup and its server UID before accepting either operation. Both strategies require the backup and target within the same registered cluster and namespace as the Restore. Reject a cross-namespace request even when the caller holds grants in both namespaces. Pin and check the actual strategy and target identity, including on generic restore submissions. Apply the following gates before any restore is created or data changed. [Restore contract](../../../operator/api/v1alpha1/restore_types.go)

| Operation | Required authority and release case |
| --- | --- |
| Restic overwrite of an existing server | Require `backups.view` on the source UID and `restores.applyExisting` on the destination UID. Preview suspension and overwrite of that server. A pre-created empty destination is still an existing server. Refuse the restore if the destination disappears or is replaced. |
| CSI recovery into a new server | Require `backups.view` and `restores.createNew` on the source UID, and independent provisioning authority for the recovered template. Require a valid, unused server name in the backup’s namespace. Fail on collision, including a server appearing after preview. A recovery operator with these grants can recover a new server and cannot overwrite an existing one. |

## Default base server roles

Choose one of the four bases explicitly when defining a cluster or namespace role. Each assignee inherits it on every current and future server in scope, including servers without a selected GameTemplate addition. A direct assignment can select a base, other live roles or a custom grant on one UID.

| Base server role | Initial grant | Number of distinct action IDs |
| --- | --- | --- |
| Viewer | `server.view`, `events.view` for identity, status and filtered workload events | 2 |
| Power User | Viewer plus `power.start`, `power.stop`, `power.restart`, `power.wake`, `logs.live`, `logs.history`, `console.send` | 9 |
| Operator | Power User plus `files.list`, `files.read`, `files.create`, `files.write`, `files.mkdir` on approved routine data paths, and `settings.general.view`, `settings.general.edit` on the server description | 16 |
| Administrator | All 84 common server actions in [Operations](#operations), with the selector and protected-operation rules below | 84 |

These are cumulative **initial** sets. Seed each live role with its complete enumerated action IDs and selectors. Later edits to one role update that role's assignees under FR-03. The four named server roles use the same assignment and Block rules as custom roles. Distinguish the server **Operator** and **Administrator** from similarly named panel or fleet roles in both pickers.

**Viewer and Power User.** Viewer sees basic status and filtered events. Log text, player identities and audit activity have independent gates. Power User can follow current output, read history, and submit commands to the game console. Wake works when supported. Bulk log export uses `logs.download`, available in Administrator or a custom grant. The preview for each role containing `console.send` must explain that the game may accept administrative commands, including changes to in-game settings and moderation. A narrow custom role can instead select reviewed named commands.

**Operator.** Seed the General selector with the description (`metadata.annotations["gameplane.local/description"]`). General also displays an image override and arbitrary Kubernetes labels, which are outside this selector. The Operator preset grants no typed edits to version, game configuration, resources, networking, environment, lifecycle or placement. Each file operation takes an exact path or subtree keyed to the trusted GameTemplate identity in the live Operator role. Gameplane ships the reviewed mappings for bundled templates with the initial role. A module author can propose additional selectors for its actual data layout. A primary panel admin approves additions or changes to an installed live role after seeing their impact. Permit creation and directory creation only where the approved selector covers the new destination. Show the actual paths in the preview. Choose paths for ordinary editable data and verify how the game consumes those files. Exclude secrets, generated configuration, startup scripts, executable/plugin directories, manifests and files that can change protected settings indirectly. If a game has no reviewed safe path, display file editing as unavailable there and retain the description grant. Adding paths to a live preset requires the same impact review as adding fields or game actions. [General settings form](../../../web/src/routes/tabs/settings/General.tsx) · [File paths](#file-paths)

**Administrator.** Seed all 84 currently defined IDs individually. For files, explicitly select the server data root as a subtree subject to agent confinement and protected paths. For typed settings and named game actions, enumerate the currently approved, delegable fields and trusted action mappings. Apply existing content, credential and backup destination policies. Expand the reviewed set on an authorized live-role edit. A new action ID, game command or schema field requires explicit selection. Each operation still checks server capability, applicable Blocks, admission, credential limits and any independent source, destination or placement permission.

Administrator can ban/unban, manage direct members within the delegation ceiling, replace content, remove files, backups, schedules or mappings, and apply an authorized restore that overwrites server data. Appointing another membership manager requires independent owner or target-admin authority under the delegation rules. Holding the four `members.*` actions alone lets an Administrator manage ordinary direct grants within its ceiling. The separate GameServer delete, wipe, ownership transfer, owner-personal public shares and personal credential controls keep their existing gates. The role grants no automatic authority over siblings, panel administration, privileged node diagnostics, scoped bindings or Blocks. The impact preview distinguishes deleting a child resource from deleting the server itself and names destructive actions before a grant is confirmed.

Preserve the frozen Legacy collaborator grant according to the legacy route and response matrix. An upgrade must not substitute a base role for that grant.

## GameTemplate roles

A GameTemplate may publish zero or more named roles and declare game-specific permissions that reference supported actions or settings. Qualify each role and permission by trusted template identity and a stable local ID. Templates use the reviewed action and field mappings above, with the same canonical checks on every transport. Template installation makes approved roles available in the picker. An authorized person selects the role before a user receives its permissions. Display an impact preview and require panel-admin approval before a template update changes a live role’s grants or action semantics. Approved role edits apply to all direct and inherited assignees on their next access decision.

For example, a CS2 template could declare **Match referee** with `actions.run` scoped to `pause-match` and `unpause-match`. A tournament namespace role can select Viewer for all servers and add Match referee for CS2. Existing and future CS2 servers receive both. Valheim servers in the same namespace receive Viewer. If a server changes template, evaluate the additions against its new trusted identity. Removing the namespace binding withdraws both inherited sources and preserves any independent direct grant or ownership.
