# Implementation plan for per-server access

Draft for [#1063](https://github.com/GameplanePanel/Gameplane/issues/1063), based on `7ea5be6a`. Use the [spec](spec.md), [panel and workload permission catalog](contracts/fleet-permissions.md), [server actions and base roles](contracts/permission-catalog.md), [reference comparisons](reference-panels.md) and [decision record](OPEN-DECISIONS.md). The three access layers cover panel authority, grants on a cluster or namespace, and membership on one server. Each new cluster or namespace role carries one base server role and can add optional GameTemplate roles. An approved GameTemplate recommendation can add selected permissions to named base holders on matching servers. Direct memberships use the server action catalog and an immutable server UID. The approved base roles are Viewer, Power User, Operator and Administrator.

## Delivery order

Implement and verify the approved base roles. Map the legacy collaborator grant against observed API behavior before converting memberships. The ordinary permission editor and invitation workflow have their own acceptance gates. Existing installations continue to serve the legacy path during the compatibility phase. Automatic built-in admin coverage can ship as a separately documented change. Repository test and lint suites run in CI per [project instructions](../../AGENTS.md).

### 1 · Define actions and ship the four base roles

New keys and unreviewed game mappings start ungranted. A previously granted canonical action can become available when a game gains an approved implementation of the same action.
- [ ] Freeze the baseline broad keys against observed routes, fields, scope and protected conditions before switching handlers. In CI compare old and new decisions for built-in and custom role fixtures, including fleet logs/files, account and destination reads, capture scope and ownership checks. A compatibility grant never expands to a newly added endpoint or field by matching a prefix. Introduce the granular keys and handlers together before exposing them in the editor.
- [ ] Seed the four cumulative [base server roles](contracts/permission-catalog.md#default-base-server-roles) when an installation first enables this feature, including upgrades. Assert exact initial sets of 2, 9, 16 and 84 action IDs and their field, path and game-specific selectors. Keep the seeds distinct from live role edits so subsequent startups preserve panel-admin customizations. Manual invitations start blank. Historical fleet and collaborator grants enter their separate compatibility flows.
- [ ] Exercise Viewer with basic status and filtered workload events. Exercise Power User with start, stop, restart, supported wake, live/history logs and raw console input. Verify the interactive console checks both `logs.live` and `console.send` and that Power User lacks bulk log export. Show the game-level effects of raw commands for every role that can send them.
- [ ] Exercise Operator with `files.list`, `files.read`, `files.create`, `files.write` and `files.mkdir` on reviewed non-critical paths for the effective template, and `settings.general.view`/`settings.general.edit` on the description. Ship and exercise a reviewed routine-data selector for at least one bundled GameTemplate. Use an actual file layout and verify what consumes the file. Refuse unchecked paths, traversal, protected descendants and file operations outside the five granted. Verify the same bounds through the direct API and compatible file transports.
- [ ] Enumerate Administrator from the 84 ordinary server actions in this release, with reviewed settings, file and game selectors and an explicit server data-root selection subject to protected paths. Exercise child-resource deletion, moderation, backup recovery, and direct membership changes within the delegation ceiling. Verify this role alone cannot forward member-management powers and that an independently authorized owner or target admin can appoint a manager. Check ownership transfer, server delete/wipe, personal shares, panel and fleet operations against their separate gates. Verify protected secrets stay redacted, new registry keys require an approved role edit, and new game-specific selectors require an explicit reviewed grant or activated recommendation, and a Block on stop defeats a stop-copy-restart backup. A direct Administrator on server A can overwrite A only with authorized source backup access and cannot provision a sibling from that grant alone.
- [ ] In `operator/api/v1alpha1/gametemplate_types.go`, the module schema generator and `gp-module/internal/validator/`, implement the [three GameTemplate declarations](contracts/permission-catalog.md#gametemplate-roles). A permission has a stable local ID qualified by the trusted template and maps to canonical server actions, reviewed parameters and selectors. A base recommendation names an exact base ID and proposed grants. An optional named role packages grants for explicit assignment. Validate all references and effects before publication. Reject duplicate local IDs, unknown targets, protected privileges and attempts to reclassify shared actions such as kick. Two distinct trusted templates may reuse a local ID.
- [ ] Check recommendations against the documented base duties at review. Viewer additions expose basic read-only information, Power User additions fit day-to-day operations, and Operator additions fit reviewed non-critical maintenance. Surface the underlying effects and independent gates for Administrator as well. Seed action counts describe the four common definitions. Installing or updating a package only proposes additions. A proposal targeting one base has no effect on another base, including a higher one.
- [ ] Reconcile the Pterodactyl families and AMP delegation, per-setting and folder scopes in the [comparison](reference-panels.md). Record supported equivalents, stricter policies and features without a Gameplane equivalent. CI asserts that every supported equivalent has an allow and a denial case.

### 3 · Store live roles and resolve effective rights

- [ ] Add portable schema under `api/internal/db/migrations/common/` using the next available number. Store one stable server-role ID and its current action/selector rows. Permit several live role references for one direct membership or a distinct one-off custom action set. Reject both forms together. Store scoped fleet keys and their validated target selectors, the required base-role reference and optional references keyed by trusted GameTemplate and server-role ID on each cluster/namespace role definition. Preserve the distinction between selected template use and template administration. The scoped binding identifies the account and full cluster or exact cluster/namespace. Index direct and inherited role references for impact previews and deletion checks. Use transactional guards and explicit SQLite cleanup. Reject deleting an assigned role. Distinguish retirement from revocation.
- [ ] Implement one transaction for editing a role, its action/selector set and its audit delta. Use an opaque stale-write validator on editing requests and return 409 on concurrent edits. There is no retained permission revision or version selector on an assignment. Join the current definition at authorization time with a consistent read across predicates. Authorization across replicas must reflect both additions and removals on the next decision. Read direct membership counts from SQL. Derive inherited coverage from distinct current UIDs in the target scope, with a breakdown for each matching template. Do not rely on reaching remote clusters to acknowledge a role edit or on a propagation job.
- [ ] Store published permission definitions, optional live role definitions and active base additions separately from package proposals. Bind each active addition to the trusted template identity, stable base ID and exact approved mapping semantics. Keep the activation state and its audit record in panel SQL. Require the built-in primary panel admin for publication, edits and activation or withdrawal. Repeated confirmation is idempotent. Keep an approved selection while the package changes only its suggestion and the underlying permissions still verify. A missing or materially changed command/field mapping is unavailable wherever its trusted semantics no longer match. An install, upgrade, rollback or reinstall cannot reinstate a withdrawn approval. Retain the template permission ID and approved semantic mapping when a person selects an alias explicitly or copies it into custom permissions. Track suspensions for affected template installations so a rollback cannot clear them.
- [ ] Store each direct membership in panel SQL under its stable account ID and target cluster registration, namespace, server name and immutable UID. Keep a per-UID conversion record even for an empty membership. Use a unique account/target key, stable role references, explicit transactional cleanup on SQLite and PostgreSQL, optimistic concurrency and idempotent operations. Verify the live target and grantor before adding access or accepting owner/delegate changes. A panel admin can revoke a known converted membership while its cluster is offline. Validate the live UID again before workload operations.
- [ ] Resolve a cluster or namespace membership dynamically against the server’s verified location and effective GameTemplate. Resolve a base reference from either direct membership or an inherited scope. Add only active recommendations for that exact base ID and trusted template. Union any explicitly selected optional roles, individual grants, ownership and existing fleet grants. A custom copy of the base has no base reference and receives no recommended addition. A later approved edit to an assigned optional role reaches its live holders. Evaluate overlapping cluster/namespace bindings separately and deduplicate outcomes. Registering a new server, creating a namespace in the covered cluster or replacing an old UID picks up eligible scope grants on first access without a backfill or a synthetic direct membership. Switching a server’s template re-evaluates its additions and optional roles on the next decision while preserving its common base rights. A new UID never inherits the old UID’s direct membership. Keep panel-only keys out of server roles and server action IDs out of the fleet catalog.
- [ ] Build `api/internal/rbac/server_access.go` around the validated principal, credential, live target, action and selectors. Apply admin-authored Blocks before ordinary allows after platform/credential checks. Match user Blocks and Blocks on live roles held directly or through scope membership for the server UID and cluster/namespace. Policy lookup failure must not authorize the affected action. Reuse `User.Can`, the existing owner checks and `rbac/server_identity.go`. Return the decision and authorized provenance. Test the same action granted independently by two sources, a field/subtree Block, a role held only on a sibling server, removal with and without a surviving allow, the protected recovery path and all read and streaming projections. For a fleet `servers:write` holder test PATCH and generic PUT changing a blocked field and a mixed payload that makes zero writes.
- [ ] **Gate.** Assign the same role to old and new members on multiple clusters. Add and remove an action from it, keep one independent grant, take a remote offline and return it. Test the next authorized request on another replica, open streams, retirement, empty action sets, concurrent role/assignment changes and deleted/recreated usernames or server names. A role edit is one SQL commit regardless of the number of assignees.
