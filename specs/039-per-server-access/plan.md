# Implementation plan for per-server access

Draft for [#1063](https://github.com/GameplanePanel/Gameplane/issues/1063), based on `7ea5be6a`. Use the [spec](spec.md), [panel and workload permission catalog](contracts/fleet-permissions.md), [server actions and base roles](contracts/permission-catalog.md), [reference comparisons](reference-panels.md) and [decision record](OPEN-DECISIONS.md). The three access layers cover panel authority, grants on a cluster or namespace, and membership on one server. Each new cluster or namespace role carries one base server role and can add optional GameTemplate roles. A GameTemplate can add permissions to each base it names. Those additions apply on matching servers when the built-in primary panel admin approves its permission declarations. Optional base recommendations have a separate activation. Direct memberships use the server action catalog and an immutable server UID. The approved base roles are Viewer, Power User, Operator and Administrator.

## Delivery order

Ship the behavior changes in a **breaking 0.x minor release**. At activation, beta server collaborators and supplemental cluster/namespace bindings lose the access those sources supplied. Owners and primary panel assignments remain in place. Built-in primary panel admins review the affected assignments and choose new access explicitly. Manual account invitations require a panel access choice, including **Assigned servers only** where appropriate. New scoped assignments require a role with a base. Publish the reset, maintenance window, dry run, retired collaborator API, view prerequisites and primary-admin reach change in the operator upgrade notes and breaking changelog entry for the implementation release.

Fresh installations start with the four base roles and an empty review queue. Upgrades use one fenced reset. The old release serves the existing policy up to the maintenance window. Repository test and lint suites run in CI per [project instructions](../../AGENTS.md).
