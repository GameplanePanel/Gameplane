# Implementation plan for per-server access

Draft for [#1063](https://github.com/GameplanePanel/Gameplane/issues/1063), based on `7ea5be6a`. Use the [spec](spec.md), [action and starter-role catalog](contracts/permission-catalog.md), [reference comparisons](reference-panels.md) and [decision record](OPEN-DECISIONS.md). The three access layers cover panel authority, grants on a cluster or namespace, and membership on one server. Each new cluster or namespace role carries one base server role and can add roles defined by GameTemplates. Direct memberships use the server action catalog and an immutable server UID. The approved base roles are Viewer, Power User and Administrator.

## Delivery order

Implement and verify the approved base roles. Map the legacy collaborator grant against observed API behavior before converting memberships. The ordinary permission editor and invitation workflow have their own acceptance gates. Existing installations continue to serve the legacy path during the compatibility phase. Automatic built-in admin coverage can ship as a separately documented change. Repository test and lint suites run in CI per [project instructions](../../AGENTS.md).

### 1 · Define actions and ship the three base roles

- [ ] Turn the [permission catalog](contracts/permission-catalog.md) into the API's explicit action registry. Record for each operation its method, target, allowed scope, selectors, implications, output projection, sensitive side effects, applicable game capabilities and credential constraints. Classify HTTP, event, WebSocket and transfer entry points. Unclassified operations fail closed for granular grants. A new capability in a game template never implicitly expands a named role.
- [ ] Seed **Viewer**, **Power User** and **Administrator** with the exact actions in the catalog. Verify that the shipped Administrator set contains every Power User action plus roster, kick, backup view and backup create. Exercise live and historical logs, restart, and a one-off stop-copy-restart backup. Verify that a Block on stop prevents that backup and that console input, member management and backup deletion still require separate grants. Test the three roles on several games, including a module that lacks a selected capability. Manual invitations start without a selection.
- [ ] Extend the GameTemplate API, module schema and validation to declare stable role IDs and reviewed template-specific action or field selectors. Resolve a role by trusted template identity and role ID. Surface accepted presets for explicit selection. A package update proposing added powers or changing an action’s meaning requires review before it can expand a live grant. Test two templates that both declare `referee`, an installation with no selected extra role, and an accepted role edit affecting direct and inherited assignees.
- [ ] Reconcile the Pterodactyl families and AMP delegation, per-setting and folder scopes in the [comparison](reference-panels.md). Record supported equivalents, stricter policies and features without a Gameplane equivalent. CI asserts that every supported equivalent has an allow and a denial case.

### 2 · Resolve panel access and cluster or namespace grants

- [ ] In `api/internal/auth/perms.go`, derive panel-admin authority from the trusted primary role, protected built-in wildcard and matching logical `local/*` binding in one snapshot. Add a virtual all-cluster/all-namespace grant to session, MCP and discovery results. A scoped wildcard alone cannot satisfy the admin identity test. Preserve target registration, standalone mode and native policy checks.
- [ ] Test bootstrap, manual and OIDC admins, manual overrides, OIDC last-manager protections, scoped admins and operator/viewer roles. Register a new remote after login, operate it without creating any new binding, and confirm demotion removes implicit rights. A manually demoted user's old cookie is invalid. Verify surviving grants with a fresh cookie and the existing read-only MCP token. Include a standalone panel with no local workloads.
- [ ] Keep the existing Helm and OIDC contracts, fleet-role IDs and role assignment scopes. Regression fixtures cover both Helm mapping formats, their validation, dashboard overrides, current primary-role selection and supplemental bindings. Keep historical scoped grants distinguishable until explicitly converted. Inventory-only access must not automatically acquire server visibility. Show the before/after rights and require a deliberate base choice and grant preview for conversion. New scope memberships use the base-bearing role model.
- [ ] Use `user_role_bindings` and the existing binding handlers in `api/internal/handlers/users.go` for cluster and namespace grants. Distinguish primary-panel, legacy and workload-scope bindings in storage, keys, mutation APIs and UI. Backfill existing rows without broadening them. A combined installation supports a whole-local-workload binding as well as its protected logical primary `local/*`. Update `SetClusterRoleBinding`, OIDC sync, duplicate checks and deletes to distinguish these rows even when role, user, cluster and namespace coincide. Test changing, revoking and reassigning each independently, and reject a local-workload assignment on a standalone control plane with no local workloads. For a named namespace validate the allowed namespace and the relevant permissions on that target. For an entire local or remote workload cluster reuse the eligibility rules in `remoteWidePermissionsAllowed` on assignment and shared role edits. Eligible permissions cover inventory, modules, templates and namespaced workloads. Reject wildcard or central-administration permissions there. A namespace grant confers no node inventory. Retain role/target management checks, audit and session invalidation when a grant changes. Validate exactly one active base role retaining `server.view` on every new scope role, including provisioning- or inventory-focused roles. Expose the base and any additional template roles whenever a manager assigns that scope role. [Current grant rules](../../docs/multicluster-ui.md#user-access)
- [ ] Register independent panel read/manage permissions for supported settings sections. Start from the section allowlist in `api/internal/handlers/config.go` and the route guards in `api/internal/rbac/rbac.go`. Show only authorized sections in the Settings UI and project the aggregate configuration response accordingly. Test that a language editor can read and change the instance default language but cannot read unrelated configuration through this grant, change notifications, or alter OIDC. Retain existing broad config keys, redaction, and the protected auth-route checks. Review auxiliary endpoints separately before assigning any section-level permission to them.
- [ ] Add `servers:create` to the panel/fleet catalog as a namespaced permission for ordinary provisioning in an authorized cluster and namespace. Also honor `servers:write` wherever it permits creation today. Check the same permissions in the dashboard, placement discovery and create handler. Placement discovery still requires `templates:read`. Test a provisioner with the new permission and template read through to server creation, deny an unauthorized placement, and confirm missing template read suppresses discovery. Keep template and infrastructure policy checks and apply ownership rules to the resulting server. On the person's access page, show a supplemental creation grant under its cluster or namespace.

### 3 · Store live roles and resolve effective rights

- [ ] Add portable schema under `api/internal/db/migrations/common/` using the next available number. Store one stable server-role ID and its current action/selector rows. Permit several live role references for one direct membership or a distinct one-off custom action set. Reject both forms together. Store the required base-role reference on each cluster/namespace role definition and optional references keyed by trusted GameTemplate and server-role ID. The scoped binding identifies the account and full cluster or exact cluster/namespace. Index direct and inherited role references for impact previews and deletion checks. Use transactional guards and explicit SQLite cleanup. Reject deleting an assigned role. Distinguish retirement from revocation.
- [ ] Implement one transaction for editing a role, its action/selector set and its audit delta. Use an opaque stale-write validator on editing requests and return 409 on concurrent edits. There is no retained permission revision or version selector on an assignment. Join the current definition at authorization time with a consistent read across predicates. Authorization across replicas must reflect both additions and removals on the next decision. Read direct membership counts from SQL. Derive inherited coverage from distinct current UIDs in the target scope, with a breakdown for each matching template. Do not rely on reaching remote clusters to acknowledge a role edit or on a propagation job.
- [ ] Store each direct membership in panel SQL under its stable account ID and target cluster registration, namespace, server name and immutable UID. Keep a per-UID conversion record even for an empty membership. Use a unique account/target key, stable role references, explicit transactional cleanup on SQLite and PostgreSQL, optimistic concurrency and idempotent operations. Verify the live target and grantor before adding access or accepting owner/delegate changes. A panel admin can revoke a known converted membership while its cluster is offline. Validate the live UID again before workload operations.
- [ ] Resolve a cluster or namespace membership dynamically against the server’s verified location and effective GameTemplate. Union its base rights with the selected extra roles for that template and any independent ownership, direct or existing fleet grants. Evaluate overlapping cluster/namespace bindings separately and deduplicate outcomes. Registering a new server, creating a namespace in the covered cluster or replacing an old UID picks up eligible scope grants on first access without a backfill or a synthetic direct membership. Switching a server’s template changes the applicable extras and preserves the base. A new UID never inherits the old UID’s direct membership. Keep panel-only keys out of server roles and server action IDs out of the fleet catalog.
- [ ] Build `api/internal/rbac/server_access.go` around the validated principal, credential, live target, action and selectors. Apply admin-authored Blocks before ordinary allows after platform/credential checks. Match user Blocks and Blocks on live roles held directly or through scope membership for the server UID and cluster/namespace. Policy lookup failure must not authorize the affected action. Reuse `User.Can`, the existing owner checks and `rbac/server_identity.go`. Return the decision and authorized provenance. Test the same action granted independently by two sources, a field/subtree Block, a role held only on a sibling server, removal with and without a surviving allow, the protected recovery path and all read and streaming projections. For a fleet `servers:write` holder test PATCH and generic PUT changing a blocked field and a mixed payload that makes zero writes.
- [ ] **Gate.** Assign the same role to old and new members on multiple clusters. Add and remove an action from it, keep one independent grant, take a remote offline and return it. Test the next authorized request on another replica, open streams, retirement, empty action sets, concurrent role/assignment changes and deleted/recreated usernames or server names. A role edit is one SQL commit regardless of the number of assignees.

### 4 · Enforce granular actions across interfaces

- [ ] Apply the resolver to individual, personal and fleet reads, `/servers/{name}/access`, backups, schedules, events and background tab requests. Project authorized fields and expose any necessary minimal server-specific schema/options. Check the live target and its direct and inherited access sources before returning candidates, counts or cluster hints. A scope member with no direct membership sees every authorized server in scope, including on first discovery after creation. Keep compatibility reads for authenticated fleet clients. Add a scoped, redacted per-server activity view for attributable actions, distinct from server events and the central audit feed.
- [ ] Replace whole-server saves for fine-grained users with typed section writes beside `api/internal/handlers/resources.go`. Resolve section, field and module-schema allowlists and validate all changed fields before writing. Reject mixed writes atomically. Use resourceVersion and trusted template identity for race checks. Preserve secret redaction and infrastructure policies. Check field-level settings and game actions against the trusted semantics on each transport. A changed command or field meaning requires review even if its ID was reused.
- [ ] Split player actions, named game actions, files and content routes in `api/internal/ws/` and `agent/internal/`. Enforce root-relative folder limits through listing, archive selection, archive destination, create, edit, upload, download and delete. Include symlinks, canonicalization, replacement and agent-side confinement. Resolve configured registry provider/project/version on the server. Treat upload, supplied URL, removal and replacing a running modpack as separate grants. Cover indirect routes such as a modpack that invokes individual installs. A restricted command or file grant must hold for the direct API as well as the dashboard. When the optional SFTP endpoint is available, verify that its per-operation file checks use the same actions, path selectors and Blocks as the Files tab. [SFTP design](../040-sftp-access/spec.md)
- [ ] For backup/schedule writes, bind source and target UIDs. Check backup creation, stop-copy-restart power actions, retention pruning/deletion, schedule replacement of active backups, and destination eligibility at the appropriate authority boundary. An existing-target restore requires independently verified source read and destination restore authority. Creating a new target via CSI still needs namespace creation rights. Refuse to attribute a historical name-only artifact to a newly created server. Include cloned servers, which receive a new identity and no copied membership.
- [ ] Revalidate the credential, precise action, role actions and target UID for WS/PTY, SSE and long transfers on SQLite and PostgreSQL (including another replica). Keep the five-second stream check and current read-only MCP route/method/upgrade ceiling. Test that a CS2 referee loses the named match action after a role edit, a send-only grant cannot open a duplex PTY and a redacted setting never leaks through detail, list or events.

### 5 · Build the access views, invitations and delegation

- [ ] Add central `/server-roles` CRUD, retirement and impact preview for panel admins. Saving edits updates all holders. Add target-filtered role lookup under `/servers/{name}/access/roles`, membership preview and mutation under `/servers/{name}/access/members`, and person-centric listing under `/users/{id}/server-access` for authorized admins. Membership requests contain an explicit choice of role IDs or custom actions, expected membership state and an idempotency key. Bulk requests list the selected server identities explicitly, authorize each target, write one UID-bound membership per target and return per-target results. Direct bulk selection alone grants nothing on a future server. A scope membership can independently cover that server. Audit the grantor, subject, target, change and outcome.
- [ ] Add a cluster-filtered assignment read backed by `user_role_bindings`. Use the grant mutation path keyed by binding kind, account, role, cluster and namespace for both **Users & RBAC** and **Cluster → Roles & permissions**. Authorize reads and writes on the server. Return only the assignments and scopes the caller may inspect. Show implicit primary panel-admin access as inherited and read-only. Under **Server access** on the scope role, require one of the three base roles and allow explicit selections of additional matching GameTemplate roles. Expose the same base and additions in the user and cluster views. Reuse the existing user-management and role checks for binding changes. If the caller's grant-management authority is scoped, enforce that scope on the list and every mutation, including direct API calls. `members.invite` and ownership of a game server apply only to that server.
- [ ] Enforce `members.view`, `members.invite`, `members.edit` and `members.remove` independently in every API path. Require the matching membership action, the correct target and a grant within the actor's transferable selectors. Verify that a new invite cannot update an existing assignment and that an edit cannot create one. Cover self-elevation, onward delegation, superior assignments, dormant grants, and a target-only admin operating outside scope. Serialize assignment changes against concurrent authority and role changes. Preserve the separate authority of a panel admin's subsequent live-role edit.
- [ ] Remove the preselected Viewer in `web/src/components/ui/admin/InviteUserDialog.tsx` and the omitted-role-to-viewer fallback in `api/internal/handlers/users.go` for manual account creation. Reserve a collision-safe protected zero-permission fleet role as an explicit **Assigned servers only** choice. Separate the account choice from the per-server choice. Reject missing/empty/conflicting choices before side effects. Validate all targets before creating an invited account, and make retried cross-target membership writes resumable with visible outcomes. Do not create local placeholders for unprovisioned OIDC identities.
- [ ] Add a panel-admin Block editor and scoped rule management API. Create, update and delete require the trusted primary panel-admin identity on the server side. Reject owners, target-only admins, delegated managers and mutation via read-only credentials. Persist the policy with stable rule ID, subject, exact scope, action and selectors. Validate action/selector combinations, prevent lost updates, audit before/after, and explain the affected action sources before save. Apply committed changes to authorization immediately on the next request and to active streams within FR-09. Test direct API and dashboard paths.
- [ ] Design all three layers in `design.fig` and regenerate design exports before React changes. Add **Roles & permissions** alongside Overview, Nodes and Configuration on the selected cluster. Extend the cluster detail route's validated tab options and enforce access on direct navigation. Show **Assignments** for the chosen cluster or namespace, **Roles & permissions** for eligible roles and their exact permissions, and **Role definitions** linking authorized editors to the shared definition. Require an impact preview before adding, editing or removing a scope grant or saving a change to a referenced role. Show the base, template-specific additions, current distinct server count, count per matching template, affected users and the rule for future servers in plain language. Count overlapping scopes once per affected server and explain any independent surviving grants or Blocks. Label incomplete or last-known counts for disconnected clusters. Avoid reporting unknown coverage as zero. Recheck authority and the policy being saved at mutation time. Removing one binding affects only that binding. Permission to view the access tab alone confers no node or server inventory. [Cluster detail page](../../web/src/pages/ClusterDetail.tsx) · [Cluster routes](../../web/src/router/tree.tsx)
- [ ] In **Users → Person → Access**, group panel role, cluster/namespace grants and per-server access for that person. Keep **Server → Access** bound to its selected UID. Connect `Users.tsx`, `ServerDetail.tsx`, the server-role library, the invitation dialog and effective-access previews to the same permission decisions. Use translated labels and identify each grant’s origin. On a server, identify the inherited base, each matching template role and the source scope alongside direct grants. Link authorized editors to the scope where inherited access can be changed. Start human invitations with blank access choices. Verify that keyboard and screen-reader users can distinguish inherited, blocked, independently granted and unavailable controls.
- [ ] **Gate.** In the Cluster tab grant Viewer on a namespace with three existing servers and add CS2 Referee on the two matching servers. Check the preview counts and future coverage, the person view and live server access. Create another CS2 server and one with an unmapped template. Both gain Viewer immediately and only the CS2 server gains Referee. Remove the grant from the person view. Verify prompt revocation of inherited access on every target, survival of independent grants, and no effect on a same-named namespace in another cluster. Repeat at whole-cluster scope with a new namespace, overlapping grants, a scoped Block, an offline cluster and a rejected grant with no base. Verify that a direct-only referee on Final cannot create a sibling or operate it. Browser and API tests cover blank invitations, named roles and custom actions, OIDC accounts, concurrent saves, and delegating only within the caller’s authority.

### 6 · Verify the new model before conversion

- [ ] Run the reference-panel cases, the user journeys and all release criteria from the spec with appropriate CI jobs. Use `make test-integration` and the `api-auth`, `api-roles`, `api-rbac`, `multicluster`, `standalone`, `upgrade` and `postgres-ha` E2E buckets. Reuse logins or rebalance `test/e2e/buckets.sh`. Include browser, direct API, MCP, streams, both DBs and cross-replica tests where supported. For SC-10, verify both views show the same binding and enforce the same scope on reads, additions and revocations. Reserve the migration portion of SC-02 for slice 7.
- [ ] Document the new rights of built-in primary admins, live role edits, cluster/namespace inheritance and its preview, template role selection, explicit choices for manual invites (including the API compatibility change), effective-access precedence and supported workloads. Update `docs/security.md`, `docs/multicluster-ui.md`, module specs and release notes with the behavior-changing PRs. Distinguish proposed and verified parity.

### 7 · Convert existing collaborators

**Prerequisites.** Verify the shipped base-role action matrix, complete the old/new collaborator parity matrix and deploy compatible readers on every serving process. New invitations use an explicit role or custom permissions. Conversion imports legacy server memberships into panel SQL.

- [ ] **Prepare.** Ship the additive schema and an API that reads both forms. Eligible, unconverted servers still use the old list and old writer during the compatibility phase. Freeze the compatibility grant against observed old route and response behavior. Keep it out of all manual role pickers. Add a durable panel-wide activation state and an operator status/dry-run view covering every registered workload cluster and managed namespace, including pending/unreachable targets. Inventory current primary admins and their newly reachable clusters for the upgrade report. Back up the panel database and the affected Kubernetes objects together, and record the cutover time and audit position.
- [ ] **Fence old binaries.** Before activation, drain every old API replica or separate writer of the legacy endpoint and bring up only conversion-aware API replicas. Use a controlled stop/start cutover where the installation cannot prove that barrier. Freeze out-of-band legacy annotation automation and direct it to the versioned API. New replicas read the durable activation state, including on restart. No annotated workload or new-style assignment is written before the fence. New installations start in the active state.
- [ ] **Identify the legacy population.** At the fence, persist the pre-upgrade cluster registrations and take a consistent inventory of eligible server UIDs for each reachable cluster. Honor unmarked legacy IDs only for that population. For an offline pre-upgrade registration, hold import pending until reconnection. Verify registration continuity and Kubernetes creation metadata against the cutover, and flag ambiguous objects for explicit reconciliation. Servers created after the fence, newly registered clusters and unverified re-registrations start without imported memberships. A copied CSV annotation on a new UID must never give an account access. This does not delay the built-in admin's access to new registered targets.
- [ ] **Convert once in SQL.** After the writer fence, read the verified live UID, owner and legacy numeric IDs. Deduplicate, check accounts and report malformed or missing IDs. In a single transaction conditionally claim the UID, store its exact compatibility grants, write the audit result and persist the converted record. Preserve an owner's independent collaborator contribution if present. Serialize first import and the first post-upgrade edit against the same row so retrying import cannot overwrite a revocation. Keep the converted record after the last member is removed. Cleanup of stale annotations can be retried separately with UID/resourceVersion preconditions. Every converted-target read ignores legacy annotations.
- [ ] **Handle outages.** An authorized panel admin can revoke a known converted membership in SQL without an online target. Do not treat an offline, unconverted target as successfully revoked. Return explicit pending/unavailable status and reconcile before using legacy access on reconnection when a revocation is pending. New grants and target-dependent delegation require a verified live target/authority. A newer workload cannot match the revoked direct membership. Evaluate its current scope grants independently.
- [ ] **Keep legacy clients bounded.** After activation route the older collaborator update through the new authorizer/transaction only if the complete ACL is representable as legacy membership. Otherwise return 409 with the new editing route. Never issue a broader legacy grant as a fallback. Generic updates, clones and new-server restores cannot copy authorization metadata onto a new identity.
- [ ] **Recovery and release.** Refuse affected requests while recovering a restored database. Reconcile subsequent direct and scope membership changes, base and template role changes and admin Blocks from independent evidence. If the latest blocks/rights cannot be reconstructed, keep the affected scopes closed until a panel admin explicitly rebuilds policy. Clearing direct assignments alone cannot contain inherited grants. A post-activation rollback uses a conversion-aware reader. Exercise import vs revoke/owner transfer, duplicate jobs, unreachable clusters and delete/recreate in SQLite and across PostgreSQL replicas. Record parity, pending scopes and evidence of recovery without resurrecting revoked access.
