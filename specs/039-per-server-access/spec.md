# Panel, cluster and per-server access

Draft for [Gameplane #1063](https://github.com/GameplanePanel/Gameplane/issues/1063), November 22, 2026. The Gameplane baseline is `7ea5be6a`. Use the [permission catalog and starter roles](contracts/permission-catalog.md), [reference-panel comparison](reference-panels.md), [implementation plan](plan.md), [delivery tasks](tasks.md) and [decision record](OPEN-DECISIONS.md) together.

## Access hierarchy

A person can receive access at any combination of three layers. Direct server access works for an account with zero effective panel permissions and no supplemental cluster or namespace grant.

| Access layer | Current Gameplane | Spec 039 |
| --- | --- | --- |
| Panel | A primary role comes from OIDC/Helm or manual assignment. Existing permissions cover accounts, roles and global settings. | Keep that primary role. Allow separate settings permissions and an explicit **Assigned servers only** choice. Give the built-in primary admin access to current and future registered clusters. |
| Cluster / namespace | **Users & RBAC** edits supplemental bindings. A role can apply to one registered cluster or a named namespace on it, subject to the role’s permissions. | Add **Cluster → Roles & permissions** as the cluster-side view of the same bindings. An observer can read EU node inventory at whole-cluster scope. A provisioner can create servers only in `eu/tournaments`. |
| Individual server | Ownership and the collaborator list authorize a fixed set of server operations. | Keep ownership and give a person one or more live roles or custom actions on a specific server UID. Store memberships in panel SQL. The same role can be assigned independently to two servers. |

For example, Alex can receive a provisioner grant in `eu/tournaments` and **Player moderator** on Match A. Creating Match B in that namespace gives Alex no moderator assignment on B. If Alex created B, the server records Alex as its owner independently. Game templates determine available actions and settings. Gameplane supplies the initial role presets and panel admins maintain the role library. [Scope and assignment examples](OPEN-DECISIONS.md#d5--panel-cluster-and-server-access)

## What someone should be able to do

A panel administrator invites Alex, explicitly chooses **Assigned servers only** for the new account, then selects different duties on two servers. The servers can share a namespace. A different account can receive a namespace grant that permits server creation at an authorized placement. A manual invitation opens with blank access choices. A panel admin designs reusable roles, and an inviter can choose custom permissions for a person who needs a different job.

| Priority | Given | When | Expected result |
| --- | --- | --- | --- |
| P1 | Survival, Staging and Production are in the same namespace | Alex receives Power operator on Survival and a custom Networking editor role on Staging | Alex can restart Survival and edit Networking on Staging. Restarting Staging and editing Survival networking are refused. Production is absent from lists, counts, events and direct links. |
| P1 | Referees on two servers hold the Match staff role | A panel admin adds an approved CS2 match action and removes raw console access | Every assignee picks up the new definition on the next request. The same rule applies to assignments on an offline cluster when it reconnects. Unsupported games gain no CS2 controls. |
| P1 | The shipped starter roles have been reviewed and a user collaborates on two servers with a separate OIDC role | The subsequent migration runs while one cluster is offline | The reachable server retains its former collaborator permissions. The other converts when reachable. The OIDC binding and its scope survive both conversions. |
| P1 | A local or OIDC account holds the built-in primary admin role | A second cluster is registered after the admin signed in | The next request can discover the cluster and administer its managed workloads without rebinding or signing in again. A subsequent committed demotion removes that implicit access. |
| P1 | Alex already has Player moderator on Match A | An admin adds a namespace provisioner grant from the EU Cluster tab and removes it from Alex’s access page | Both views show the same change. The Match A assignment survives. Creating Match B in that namespace gives Alex no moderator membership on B. |
| P2 | Alex also holds an existing namespace-scoped panel Viewer role | An owner removes Alex’s direct assignment | The preview identifies the access Alex retains and its source. Only an authorized fleet-role manager can change that source. |

## Roles, grants and scope

**FR-01 · Panel roles and scoped bindings.** The primary panel role controls administrative actions such as changing global settings (`config:manage`) and managing accounts. The existing fleet catalog also supplies the workload permissions used by cluster and namespace grants. Keep `roles`, `role_permissions` and `user_role_bindings`, including the existing scope of panel-wide, cluster-wide and namespaced permissions. An operator or viewer on one cluster retains its existing reach. Preserve OIDC first-match ordering, fallback/deny behavior, manual overrides, return to SSO control, lockout guards, existing Helm `api.oidc.roleRules`, `roleMappings` and `defaultRole`, and dashboard override precedence. Signing in updates the primary fleet role according to those rules. It never creates, replaces or clears a direct server assignment. [Existing SSO contract](../done_034-sso-group-role-rules/spec.md)

Give panel admins independently assignable panel-settings permissions for supported sections, with separate read and manage keys. For example, `config:i18n:manage` allows changing the instance default language and reading that section's editable values. Notification settings require their own key. The broad `config:read` and `config:manage` permissions keep their existing coverage. Filter configuration reads for section-limited roles. Preserve secret redaction, Helm/operator restrictions and the protected admin gate for authentication and OIDC changes. Publish each supported section explicitly in the panel catalog. [Configuration sections](../../api/internal/handlers/config.go) · [Protected routes](../../api/internal/rbac/rbac.go)

Add `servers:create` to the panel catalog for ordinary server creation at an authorized cluster/namespace. Keep existing `servers:write` authorization on routes where it already permits creation, editing or control. For the Create screen, eligible placements require template read and either creation permission at that placement. Reserve the new key for provisioning. Operations on an existing server require their own authorization. The creator’s subsequent ownership is evaluated independently. [Panel catalog](../../api/internal/rbac/catalog.go) · [Placement discovery](../../api/internal/handlers/fleet.go)

**FR-02 · Panel admin identity.** Derive panel-admin status in one authorization snapshot by verifying that the user's primary role is the built-in `admin`, that it carries its protected wildcard, and that its primary binding is present at logical `local/*`. Treat this as a virtual all-clusters/all-namespaces wildcard at request time. Keep the stored primary binding and expose the resolved wildcard and its origin consistently to clients. Do not enumerate clusters at login or write a binding on registration. A scoped binding to the built-in role, a custom role name, `roles:manage`, and a server role are insufficient to promote an account. Bootstrap, manual promotion and OIDC selection of the actual primary admin qualify equally. Demotion takes effect when the role update commits, including an OIDC change applied at sign-in.

Admins can perform every supported panel-admin operation on every **registered** cluster and managed namespace, including owner-or-admin server operations, subject to installation mode, cluster reachability, native Kubernetes permissions and existing admission policies. A standalone panel with zero clusters still has a panel admin and never fabricates a local workload cluster. Unknown targets, unsupported remote operations, owner-personal share links, personal credentials and the read-only MCP token contract keep their existing boundaries. [Standalone contract](../done_025-standalone-panel/spec.md) · [MCP contract](../037-scope-mcp-server-permissions/spec.md)

**FR-03 · Live server role library.** Only the built-in panel admin creates, edits and retires reusable roles under **Administration → Server roles**. Each role has a stable ID, name, description and current grant set. An assignment references the ID. An atomic save changes the grant set for every assignment on the next authorization decision, without a remote write, pin, upgrade step or role revisions. Audit the change and preview affected accounts, servers and scopes. Count committed assignments in SQL even during a cluster outage. Label last-known workload status separately. Retiring a role prevents new assignments while existing memberships still resolve the live role. Refuse deletion while in use. Keep fleet and server role identities distinct. Catalog additions never silently widen a role. [D1](OPEN-DECISIONS.md#d1--editing-a-base-role)

**FR-04 · Direct server assignments and delegation.** A direct assignment binds a panel account to a registered cluster, namespace, server name and immutable GameServer UID. Choose either named live roles (union) or an explicit custom action set. Replacing a live role with custom actions requires a preview. The person then ceases to be a member of that role on that assignment. Delegation uses four independent permissions: `members.view`, `members.invite`, `members.edit` and `members.remove`. On a delegated change, require the correct membership action and authority over the associated actions, selectors and target, including dormant grants. Owners and target-authorized admins may appoint membership managers. Delegates cannot modify themselves, appoint further managers, alter inherited fleet grants or manage Blocks. Only the built-in panel admin edits shared role definitions. Ownership transfer, wipe, deletion and personal share links retain their separate policies. [Delegation contract](OPEN-DECISIONS.md#d2--who-can-delegate)

**FR-05 · Explicit invitations.** Manual account and server invitations start with no selection. For a new local account, require an explicit fleet access choice, including the protected zero-permission **Assigned servers only** option. For each server or explicitly selected group of servers, choose named roles or **Custom permissions** with at least one action. For an existing account require only the requested server assignment and preserve its primary role. The API rejects missing, empty, ambiguous or conflicting selections before creating an account or membership. A general account-only invitation can explicitly select its primary role without granting a server. OIDC's configured first-login defaults, identity matching and Helm mappings continue as configured. [D3](OPEN-DECISIONS.md#d3--invitations-and-migration-order)

## Server permissions

**FR-06 · Action catalog and shipped roles.** Implement the [catalog](contracts/permission-catalog.md) for the work Gameplane exposes. Its rows define native operations, prerequisites, scoped selectors, candidate starter roles and acceptance cases. Keep game-specific action and field identities qualified by their trusted module/template. A meaningful change to the command or field contract requires fresh approval of that action, independent of live role editing. The picker intersects rights with the target’s capabilities. A CS2 referee can pause a match without console access, a Terraria host can broadcast without receiving ban, and a Valheim server does not acquire controls its template omits. [Pinned CS2 template](https://github.com/GameplanePanel/module/blob/c310076716ce8ccc63619f88ddc69547415dcfc2/cs2/template.yaml#L181) · [Pinned Terraria template](https://github.com/GameplanePanel/module/blob/c310076716ce8ccc63619f88ddc69547415dcfc2/terraria/template.yaml#L177)

Every usable server grant includes the minimum identity and navigation needed to exercise it. Editing an individual field includes its redacted view where appropriate and never grants read access to sibling fields, secret values, or an entire settings section. Display a distinguishable status for an unauthorized action, an unsupported module feature and a feature disabled by policy. Directory, field and named-action constraints are enforced on every API and transport that can perform that operation. Platform credentials, arbitrary images, host diagnostics and security-context overrides retain their existing gates. [Security-context contract](../030-security-context-overrides/spec.md)

**Starter roles precede conversion.** Review and approve the exact shipped action matrix against several games before implementing collaborator migration. **Legacy collaborator** describes an upgrade-only compatibility grant and is absent from both the starter-role picker and the manual invite API.

**FR-07 · Data and writes.** Authorize every API operation and project its response using the server and action. A status-only grant returns only identity, status and navigation essentials. Redact unauthorized settings, file contents, rosters, ACLs, log text and cross-server references from detail, fleet, events and nested or aggregated responses. A pre-existing scoped panel grant can still supply the fields covered by its original permission, subject to applicable Blocks. Section writes accept a typed field allowlist and require a matching resource version. Reject a mixed authorized/unauthorized payload as one operation. Reserved metadata and secret values never become writable or readable through a section form. If a field appears on two screens, both use its canonical action. For example clearing an image override, changing server suspension and writing tunnel credentials retain their respective checks wherever exposed. Keep generic full-object writes behind their existing fleet check and protected-field guards. Also authorize the actual field/action diff for any fleet writer subject to a block. A mixed generic PUT changing a blocked networking field must fail atomically. A permitted form receives the minimum server-specific schema/options it needs without requiring catalog-wide or inventory access.

**FR-08 · Related resources.** Verify source and destination independently. A Restic restore requires access to the source backup and permission to restore into the identified existing target. A CSI restore creates a new server and also requires panel provisioning authority at the destination. For a direct grant, scheduling backups requires schedule management and backup creation on that server. A stop-copy-restart policy also requires stop and start. A retention policy that prunes backups also requires backup deletion. Show those dependencies in preview, including defaults applied by the server. An admitted schedule belongs to the server and keeps running if its creator leaves. Its target UID and destination policy are rechecked when it fires. Changing targets requires authorization on both the old and new target. Preserve a trusted server UID when creating a backup or schedule, propagate it to generated children and verify it at execution. Historical resources without reliable identity remain accessible under their existing fleet grants. A same-name replacement or a user-supplied label cannot establish ownership. Preserve legacy same-namespace clone behavior only on paths that already allowed it. A clone gets a fresh UID, the caller as owner, and no copied ACL. [Restore types](../../operator/api/v1alpha1/restore_types.go)

**FR-09 · Discovery and revocation.** Apply the same evaluator to fleet search, personal server lists, server detail, direct URLs, child lists, events, MCP reads, WebSockets, SSE and long transfers. A server-only user can navigate to the assigned remote server without gaining sibling inventory. Use the same missing-resource response for hidden and nonexistent targets for this audience. A forbidden action on a visible server receives 403. Preserve legitimate collection-wide clients. Ordinary requests pick up committed revocations on the next request. Recheck identity, precise action and credential on active streams every five seconds on SQLite and PostgreSQL, including connections on another replica. Cancel when revocation or identity change is observed, or on revalidation failure. MCP keeps its own route/method/upgrade limits, including for panel admins.

**FR-10 · Explain and manage access.** Show **Panel access**, **Cluster / namespace access** and **Server access** in **Users → Person → Access**. Show which layer, role, binding or ownership relation supplied an action, and any applicable admin Block. Label role type and target even when display names match. Use **Server → Access** for direct membership on the selected UID. Role, action and game-field searches and exact-account lookups return only authorized results. Explain the effects of sensitive grants such as raw console commands or unrestricted file writes before assignment. Bulk operations report each target separately.

On the selected Cluster page add **Roles & permissions** alongside **Overview**, **Nodes** and **Configuration**. Under **Assignments**, show the person, role, exact scope and source. Authorized managers can bind a role to the entire eligible cluster or a named namespace. Identify primary-admin coverage as inherited. Under **Roles & permissions**, show which permissions in each role apply at the selected scope. Under **Role definitions**, authorized editors can open the shared definition and preview its effect across bindings. Removing one person’s grant and editing a shared role are distinct operations. Keep Kubernetes credential downloads under Configuration. [Current cluster detail page](../../web/src/pages/ClusterDetail.tsx)

The Cluster and person views read and mutate the same binding records under the same authorization rules. Enforce read, assign, remove and role-edit authority on the API. A viewer confined to one namespace sees only authorized assignments and targets, including via direct API or URL. Viewing inventory, administering the workload or holding server membership-management permissions confers no authority to edit bindings. Opening the tab must not expose node inventory, other users, sibling namespaces or role definitions beyond the viewer’s existing authority. [Current scoped binding workflow](../../docs/multicluster-ui.md#user-access)

## Migrating existing collaborators

**FR-11 · Preserve legacy access in a later phase.** Once the shipped base-role matrix is approved, freeze the old route/field behavior and design the exact legacy mapping. Keep the existing reader and collaborator behavior until parity is demonstrated. Read `gameplane.local/collaborators` as user IDs. Deduplicate valid IDs and report malformed entries and missing accounts. Names are display data. Preserve ownership and all independent fleet grants. Record or import the actual compatibility entitlement rather than approximating it with the closest starter role. The table gives the baseline to verify.

| Legacy contribution to carry forward | Permissions it must not add |
| --- | --- |
| Existing redacted server detail, events, logs, console/game actions, power and wake, same-namespace clone, file reads and mutations, moderation/whitelist, supported content management and tunnel credential operations | General server PUT or settings save, backups, restores, schedules, capture, public share administration, delete, wipe, transfer, or managing access. Separate pre-existing grants still count. |

**FR-12 · Server membership in panel SQL.** Keep the owner on the GameServer. Use panel SQL as the sole authority for new and converted membership, keyed to the registered cluster and immutable workload identity. Store live role IDs or explicit actions. Verify the target UID before exercising workload access. A committed panel-admin revocation of a known, converted membership takes effect centrally even while the cluster is offline. The next request on reconnection uses the current SQL decision. A replacement server receives no old grant. Preserve a durable per-UID converted record even when no members remain. [Storage decision](OPEN-DECISIONS.md#d4--where-assignments-live)

**FR-13 · Upgrade and recovery.** After approval of the starter-role design, fence legacy writers and identify eligible pre-upgrade UIDs. Use a single SQL transaction to create exact legacy memberships and mark that UID converted. Route membership edits through the same serialization point. One-time removal of obsolete Kubernetes annotations is cleanup and must never reactivate them on a converted UID. Track and resume offline targets. Preserve the old collaborator endpoint only for representable legacy lists. Before serving a restored panel DB, reconcile subsequent revocations, Blocks and live role edits against independent records. Keep authorization closed for affected targets until their current policy can be established. [Cutover and recovery](plan.md#7--convert-existing-collaborators)

**FR-14 · Audit and support.** Record the actor, account ID, target and scope, stable role ID or explicit action set, allowed/blocked action changes, result, and operation ID. Record live role edits once with the affected scope, plus assignment changes, transfer, conversion and admin grant provenance. Restrict audit details and omit credential material, log contents and secret values.

**FR-15 · Scope and role boundaries.** Present three access layers using two permission catalogs. Panel roles and scoped cluster/namespace bindings use the existing fleet catalog. Direct server roles use the granular action catalog and a separate set of role IDs. Validate the permission, binding scope and target on the API. Preserve the local primary binding and the remote all-namespace restrictions. A cluster-wide node inventory permission requires cluster-wide scope. A namespaced provisioning permission applies only to eligible placements in that scope. Each granular server grant names one immutable UID. Bulk selection writes one membership per selected UID. A new or same-name replacement server receives no earlier membership. Existing scoped fleet permissions and ownership retain their independent effect. [Three-layer decision](OPEN-DECISIONS.md#d5--panel-cluster-and-server-access)

**FR-16 · Admin-only Block.** Only the built-in primary panel admin can create, edit or remove a Block. A rule identifies a user or live role, an exact server UID or cluster/namespace, an ordinary workload action and applicable selectors. After platform/credential limits, a matching Block takes precedence over every ordinary allow, including inherited fleet or direct role grants. Unspecified actions remain neutral. Removing a Block re-evaluates the surviving grants and does not grant access by itself. Preserve the built-in panel admin recovery path. Authorize the same action on every entry point, including full-object updates and open streams. The decision preview identifies the source within the viewer's authorization. Audit changes with actor and scope. [Block contract](OPEN-DECISIONS.md#d6--explicit-exceptions-to-inherited-access)

## Release criteria

- **SC-01.** The six journeys above pass through the dashboard and direct API, including X/Y/Z within one namespace and same-named servers on two clusters.
- **SC-02.** Approve the base-role matrix first. In the subsequent migration, the SQLite and PostgreSQL legacy parity matrix has zero unexplained differences. Revocation survives retries, concurrent edits, replica restart, offline clusters and same-name replacement.
- **SC-03.** A built-in primary admin manages a newly registered remote on the next request with zero new binding rows. A scoped admin and an ordinary fleet user do not gain that reach. Demotion, including on an existing stream, conforms to FR-09.
- **SC-04.** Existing Helm values and OIDC regression fixtures produce the same primary roles and supplemental grants. The intentional access expansion applies only to the built-in primary admin. A server-role edit cannot change a panel role. A user with template read and the scoped `servers:create` panel permission can provision in that placement. With no other grant they cannot operate another person's server. A server-only Power operator can restart the assigned server and cannot create a sibling or edit panel settings. Reject cross-catalog keys and role IDs, and verify that bulk assignment to two servers grants nothing on a third or on future servers.
- **SC-05.** REST responses, the dashboard, MCP and streams agree for every supported server action within each credential’s limits. Scoped users see no sibling data through summaries, backup metadata, console history, counts or alternate tabs.
- **SC-06.** Every named role holder sees additions and removals on the next request regardless of assignment time, API replica or temporary cluster outage. Active streams revalidate under FR-09. Display independent grants if an action still works. No role-specific remote reconciliation job is required.
- **SC-07.** Blank invite UIs cannot submit. Direct invite/account creation calls with no explicit choice return a validation error and create no account or membership. Test both named-role and custom-action paths with multiple game templates.
- **SC-08.** Verify the [reference comparison](reference-panels.md) against the operation matrix. Every comparable action has an independent positive/negative authorization test or an explicitly documented product/policy gap. Verify independent delegation permissions and Block precedence. Verify the three access layers in the release comparison.
- **SC-09.** An invite-only delegate cannot edit or remove an assignment or grant beyond their ceiling. Only the built-in primary admin can create, edit or remove a Block. A server-specific Block defeats independent direct and existing namespace-scoped panel allows on that server, leaves its sibling unaffected, and takes effect on existing streams within the FR-09 revalidation contract.
- **SC-10.** Add an EU namespace grant from the Cluster tab, verify the same binding on the person, and remove it there. Both views show the committed result, including after refresh. Test an eligible remote all-namespace grant, the protected local primary binding, an ineligible role, and an actor lacking binding authority. Verify that a direct grant on Match A survives removal of an independent namespace grant. A scoped view must not expose another namespace, cluster or the global account directory.
