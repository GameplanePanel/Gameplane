# Panel, cluster and per-server access

Draft for [Gameplane #1063](https://github.com/GameplanePanel/Gameplane/issues/1063), updated November 23, 2026. The Gameplane baseline is `7ea5be6a`. The [panel and workload catalog](contracts/fleet-permissions.md) and [server catalog and base roles](contracts/permission-catalog.md) list the exact permissions introduced by this design. See the [reference-panel comparison](reference-panels.md), [implementation plan](plan.md), [delivery tasks](tasks.md) and [decision record](OPEN-DECISIONS.md).

**Release policy.** Ship 039 as a **breaking 0.x minor release**. At activation, old server collaborator lists and all supplemental cluster and namespace grants stop authorizing access, including on offline servers. Ownership and primary panel role assignments continue. A primary panel admin reviews the affected accounts and explicitly assigns access under the new model. Manual invitation clients must supply an access choice. Existing integrations must replace collaborator-list calls with the panel access API. Fresh installations start directly with the new model. [Beta upgrade and dry run](#beta-access-reset-and-reassignment)

## Access hierarchy

A person can receive access at any combination of three layers. Direct server access works for an account with zero effective panel permissions and no supplemental cluster or namespace grant.

```text
Panel account
├─ 1. Panel access — Users & RBAC
│  ├─ Primary panel role from OIDC/Helm or manual assignment
│  ├─ Panel duties, or the explicit “Assigned servers only” choice
│  └─ Built-in primary panel admin covers every current and future registered cluster
├─ 2. Cluster / namespace access — Cluster → Roles & permissions
│  ├─ Whole cluster → all current and future servers in its managed namespaces
│  ├─ Exact namespace UID in a registered cluster → all current and future servers there
│  └─ Each new scoped role grants
│     ├─ Eligible infrastructure permissions, e.g. servers:create with template access
│     ├─ Exactly one base → Viewer, Power User, Operator or Administrator
│     └─ Optional named GameTemplate roles → selected for matching templates only
└─ 3. Individual server access — Server → Access, one immutable UID
   ├─ Ownership → independent, including protected owner operations
   ├─ Inherited → server rights from all matching cluster and namespace roles
   └─ Direct assignment → choose one form
      ├─ Named live roles → bases and/or matching optional GameTemplate roles
      └─ Custom permissions → selected common actions and/or approved template permissions

On each server, resolve every named base held directly or inherited
├─ Common base permissions
├─ GameTemplate-declared additions for that exact base → active on template approval
└─ GameTemplate recommendations for that exact base → active on separate opt-in

Combine these with other valid grants and explicitly selected optional roles.
Require the target view and the action's own view prerequisites after selector, Block and credential checks.
```

| Access layer | Current Gameplane | Spec 039 |
| --- | --- | --- |
| Panel | A primary role comes from OIDC/Helm or manual assignment. Existing permissions cover accounts, roles and global settings. | Delegate individual account, role, settings and cluster-registration duties. Offer **Assigned servers only** for zero panel permissions. The built-in primary admin reaches every current and future registered cluster. |
| Cluster / namespace | **Users & RBAC** edits supplemental cluster or namespace bindings for fleet permissions. | In **Cluster → Roles & permissions**, assign inventory, provisioning, template use, scoped audit and operational duties independently. Choose exactly one base server role for every existing and future server in scope. Matching templates can contribute approved permissions to that base. A manager can also select optional template roles. The Cluster and person views edit the same binding. |
| Individual server | Ownership and the collaborator list authorize a fixed set of server operations. | Ownership, inherited roles and direct roles or custom actions can each supply access. A direct base role receives its approved declared additions and activated recommendations for the server’s effective template. The assignment in panel SQL targets that server’s immutable UID. |

For example, **Tournament staff** in `eu/tournaments` grants **Viewer** on every server and the **Match referee** role on servers running its CS2 GameTemplate. Alex immediately sees existing servers A, B and C. If A and B run CS2, Alex can referee both. Tomorrow’s server D receives Viewer automatically and adds Match referee if it runs that CS2 template. Alex can also have an independent direct role on one server. Separately, a person assigned Administrator on A directly or through a scoped role receives any CS2-declared Administrator additions approved for that template. Match referee is a separate assignment. [Scope decision](OPEN-DECISIONS.md#d5--panel-cluster-and-server-access)

## What someone should be able to do

A panel administrator invites Alex, explicitly chooses **Assigned servers only** for the new account, then selects different duties on two servers. The servers can share a namespace. A different account can receive a namespace grant that permits server creation at an authorized placement. A manual invitation opens with blank access choices. A panel admin designs reusable roles, and an inviter can choose custom permissions for a person who needs a different job.

| Priority | Given | When | Expected result |

| P1 | Survival, Staging and Production are in the same namespace | With no other grants, Alex receives Power User on Survival and a custom Networking editor role on Staging | Alex can restart Survival and edit Networking on Staging. Restarting Staging and editing Survival networking are refused. Production is absent from lists, counts, events and direct links. |
| P1 | Referees on two servers hold the Match staff role | A panel admin adds an approved CS2 match action and removes raw console access | Every assignee picks up the new definition on the next request. The same rule applies to assignments on an offline cluster when it reconnects. Unsupported games gain no CS2 controls. |

One cluster is offline. | The panel activates the beta reset. | Both old sources stop authorizing immediately across the installation. Alex keeps independently authorized access from the primary role. A primary panel admin sees the outstanding review and can assign new access after verifying each target. Reconnecting a cluster restores no old grant. |
| P1 | A local or OIDC account holds the built-in primary admin role | A second cluster is registered after the admin signed in | The next request can discover the cluster and administer its managed workloads without rebinding or signing in again. A subsequent committed demotion removes that implicit access. |

| P2 | Alex also holds a confirmed namespace role with Viewer | An owner removes Alex’s direct assignment | The preview identifies the access Alex retains and its source. Only an authorized fleet-role manager can change that source. |

## Roles, grants and scope

**FR-01 · Panel roles and scoped bindings.** The primary panel role controls administrative actions such as changing global settings (`config:manage`) and managing accounts. The existing fleet catalog also supplies the workload permissions used by cluster and namespace grants. Keep `roles`, `role_permissions` and `user_role_bindings` for their existing purposes. Add the server-role references described in FR-15 to cluster/namespace role definitions. Keep these scoped definitions distinct from primary panel assignment, even where a fleet role name is shared. Preserve the primary role assignment and its logical panel binding. Retire every pre-upgrade supplemental binding at cutover. All new workload bindings require a base and confirmed scope. A retained primary role is evaluated with the view prerequisites below. Preserve OIDC first-match ordering, fallback/deny behavior, manual overrides, return to SSO control, the lockout rules in FR-02, existing Helm `api.oidc.roleRules`, `roleMappings` and `defaultRole`, and dashboard override precedence. Signing in updates the primary fleet role according to those rules. It never creates, replaces or clears a direct server assignment. [Existing SSO contract](../done_034-sso-group-role-rules/spec.md)

Use the [panel and workload catalog](contracts/fleet-permissions.md) for account lookup and directory listing, account lifecycle and credential operations, primary-role assignment, panel role authoring, infrastructure registration and credential issuance. Authorize the actual changes in a request, including implicit grants in account creation or a role edit, and enforce FR-02 and the applicable identity-provider protections. Section-level panel settings have separate redacted read and write keys for general, notifications, telemetry, i18n and mod registries. An auth-section reader sees the redacted configuration. Authentication/OIDC changes require the protected built-in admin. Preserve Helm/operator restrictions and the historical reach of `config:read` and `config:manage`. [Configuration sections](../../api/internal/handlers/config.go) · [Protected routes](../../api/internal/rbac/rbac.go)

Add `servers:create` for ordinary provisioning at an authorized placement. A narrow provisioner can use a selected GameTemplate via `templates:use` and see only its creation inputs. Intersect the allowed template identities and destination cluster/namespace on discovery and again on submission. Existing `servers:write` may supply creation authority and `templates:read` may supply creation-input visibility within the same authorized placement. Check both sides on submission. Creation grants no independent authority over existing servers. The required base and the creator's ownership have their own effects. [Workload catalog](contracts/fleet-permissions.md) · [Placement discovery](../../api/internal/handlers/fleet.go)

**FR-02 · Panel admin identity.** Derive panel-admin status in one authorization snapshot by verifying that the user's primary role is the built-in `admin`, that it carries its protected wildcard, and that its primary binding is present at logical `local/*`. Treat this as a virtual all-clusters/all-namespaces wildcard at request time. Keep the stored primary binding and expose the resolved wildcard and its origin consistently to clients. Do not enumerate clusters at login or write a binding on registration. A scoped binding to the built-in role, a custom role name, `roles:manage`, and a server role are insufficient to promote an account. Bootstrap, manual promotion and OIDC selection of the actual primary admin qualify equally. Demotion takes effect when the role update commits, including an OIDC change applied at sign-in.

Panel-initiated suspension, deletion, demotion or an equivalent change to an account, binding or enabled sign-in method must leave at least one enabled, usable primary panel admin. Count only an account with the built-in primary admin role, its valid primary binding and an enabled sign-in method. Check the resulting state in the same transaction as the change, including concurrent requests through different replicas. A delegated user manager cannot satisfy this requirement. When a verified OIDC sign-in maps an SSO-managed primary admin to a valid lower role, apply the demotion even if this was the last primary admin or the last user manager. Audit the change and loss of admin coverage, revoke the previous admin authority under FR-09, and require operator recovery if no primary admin remains. The operator can use `bootstrap-admin` to create a local admin and enable local login if needed. Manual role overrides and refused sign-ins for deny or missing-role decisions follow the existing SSO rules. [Operator recovery](../../docs/security.md#lockout-guard-and-break-glass)

Admins can perform every supported panel-admin operation on every **registered** cluster and managed namespace, including owner-or-admin server operations, subject to installation mode, cluster reachability, native Kubernetes permissions and existing admission policies. A primary panel admin can administer a standalone panel before its first cluster is registered. Unknown targets, unsupported remote operations, owner-personal share links, personal credentials and the read-only MCP token contract keep their existing boundaries. [Standalone contract](../done_025-standalone-panel/spec.md) · [MCP contract](../037-scope-mcp-server-permissions/spec.md)

**FR-03 · Live server role library.** Gameplane ships the four base roles in FR-06. The built-in primary panel admin manages reusable server roles and approves publication of GameTemplate permissions and optional roles. Approving the template permission declarations applies the author’s declared base additions in the same transaction. Optional recommendations have a separate activation decision under FR-18. Each live role has a stable ID, name and action set. Direct memberships and scoped definitions reference that ID. One edit changes all applicable assignments on the next authorization decision without role revisions or pinning. Audit the before/after actions and preview the effect on direct and inherited access across scopes. Count direct SQL assignments separately from covered workloads, labeling last-known or unavailable inventory. Retiring a role prevents new selection while existing references continue to resolve. Refuse deletion while a membership or scoped definition references it. A scoped definition must retain one usable base with `server.view`. [Live-edit decision](OPEN-DECISIONS.md#d1--editing-a-base-role)

**FR-04 · Direct server assignments and delegation.** A direct assignment binds a panel account to a registered cluster, namespace, server name and immutable GameServer UID. Choose either named live roles (union) or an explicit custom action set. Replacing a live role with custom actions requires a preview. The person then ceases to be a member of that role on that assignment. Delegation uses four separately assignable permissions, `members.view`, `members.invite`, `members.edit` and `members.remove`. On a delegated change, require effective `members.view` on that server, the specific membership mutation and authority over the associated actions, selectors and target, including dormant grants. For a named base, include its approved declared additions and separately activated recommendations on the target template. For an inherited grant, check approved additions across its entire delegable scope, including future matching workloads. A later primary-admin approval is a separate live policy decision. Owners and target-authorized admins may appoint membership managers. Delegates cannot modify themselves, appoint further managers, alter inherited fleet grants or manage Blocks. Only the built-in panel admin publishes changes to shared server-role definitions. Ownership transfer, wipe, deletion and personal share links retain their separate policies. [Delegation contract](OPEN-DECISIONS.md#d2--who-can-delegate)

**FR-05 · Explicit invitations.** Manual account and server invitations start with no selection. For a new local account, require an explicit fleet access choice, including the protected zero-permission **Assigned servers only** option. For each server or explicitly selected group of servers, choose named roles or **Custom permissions** with at least one action. For an existing account require only the requested server assignment and preserve its primary role. The API rejects missing, empty, ambiguous or conflicting selections before creating an account or membership. A general account-only invitation can explicitly select its primary role without granting a server. Assigning a configured cluster/namespace role presents its selected base, matching GameTemplate roles and scope for confirmation. A manual invitation never preselects a binding. OIDC's configured first-login defaults, identity matching and Helm mappings continue as configured. [D3](OPEN-DECISIONS.md#d3--invitations-and-beta-access-reset)

## Server permissions

**FR-06 · Action catalog and shipped roles.** Implement the [catalog](contracts/permission-catalog.md) for the work Gameplane exposes. Its rows define native operations, prerequisites, scoped selectors, the approved base roles and acceptance cases. Keep game-specific action and field identities qualified by their trusted module/template. A meaningful change to the command or field contract requires fresh approval of that action, independent of live role editing. The picker intersects rights with the target’s capabilities. A CS2 referee can pause a match without console access, a Terraria host can broadcast without receiving ban, and a Valheim server does not acquire controls its template omits. [Pinned CS2 template](https://github.com/GameplanePanel/module/blob/c310076716ce8ccc63619f88ddc69547415dcfc2/cs2/template.yaml#L181) · [Pinned Terraria template](https://github.com/GameplanePanel/module/blob/c310076716ce8ccc63619f88ddc69547415dcfc2/terraria/template.yaml#L177)

**View before modify applies at all three layers.** Every user-initiated mutation requires its catalogued read/view of the same resource or field and its own write action. Evaluate both against the current target, selectors, credential and Blocks at execution. For creation, require the relevant parent or destination view before the object exists. A view may come from another effective source. Do not add reads silently when a role needs them. Show the prerequisites in the picker and preview, highlight any missing ones and deny the operation until they are satisfied. A retained primary role with only a write key keeps its assignment but loses use of that operation until the view is granted. Use the canonical read key for the domain, including `:read`, `.list` or `.roster` where applicable. Viewing a redacted credential field never reveals its secret. [Panel and placement prerequisites](contracts/fleet-permissions.md) · [Server prerequisites](contracts/permission-catalog.md)

Every ordinary operation on an existing server also requires effective `server.view` on its UID. Effective `server.view` supplies basic identity and navigation. Blocking `server.view` hides the server and suppresses all ordinary reads, mutations and streams there, even if an independent grant supplies the action. Preserve the protected primary panel admin recovery path. Directory, field and named-action constraints apply on every transport. Distinguish lack of permission from an unsupported or disabled capability on visible targets. Platform credentials, arbitrary images, host diagnostics and security-context overrides retain their existing gates. [Security-context contract](../030-security-context-overrides/spec.md)

A roster reader sees display names. Persistent identifiers, faction and similar identity details require `players.identityDetails` as well. Basic ban entries and their reasons or issuing actors have separate visibility. Apply these projections to the initial response and live updates. Enable Gameplane’s Kick, Ban and Unban controls individually when the effective module supports that operation through a Gameplane integration and the actor has the required permissions and views. Enforce both conditions when dispatching a request, including a named template action that performs moderation. A moderator with kick authority on a supported module can select an allowed player without receiving their persistent ID. The new privacy keys are optional additions to a role. [Player, ban and moderation contract](contracts/permission-catalog.md#operations)

**Approved base server roles.** Viewer grants basic status and filtered workload events. Power User adds start, stop, restart, wake, live and historical logs, and raw game console input. Operator adds routine file creation, reading and editing only at reviewed paths and allows editing the server description. Administrator receives all 84 enumerated server actions with their approved selectors, including member management and deletion of child resources. Deleting or wiping the GameServer, transferring ownership and owner-personal operations retain their existing gates. Separate panel, placement and other-target authority still applies. These are the shipped common grants. A template can add approved actions or selectors to any explicitly named base on matching servers. It can also offer optional recommendations for separate activation. [Exact base permissions and selectors](contracts/permission-catalog.md#default-base-server-roles)

**FR-07 · Data and writes.** Authorize every API operation and project its response using the server and action. A status-only grant returns only identity, status and navigation essentials. Redact unauthorized settings, file contents, rosters, ACLs, log text and cross-server references from detail, fleet, events and nested or aggregated responses. A current grant can supply the fields covered by a broad fleet key, subject to applicable Blocks. Section writes accept a typed field allowlist and require a matching resource version. Reject a mixed authorized/unauthorized payload as one operation. Reserved metadata and secret values never become writable or readable through a section form. If a field appears on two screens, both use its canonical action. For example clearing an image override, changing server suspension and writing tunnel credentials retain their respective checks wherever exposed. Keep generic full-object writes behind their existing fleet check and protected-field guards. Also authorize the actual field/action diff for any fleet writer subject to a block. A mixed generic PUT changing a blocked networking field must fail atomically. A permitted form receives the minimum server-specific schema/options it needs without requiring catalog-wide or inventory access.

**FR-08 · Related resources.** A Restic overwrite requires source backup access and `restores.applyExisting` on the verified destination UID. A CSI restore to a new server requires source backup access, `restores.createNew` on the verified source UID and provisioning authority at the destination. Both recovery modes stay in the backup’s cluster and namespace. Authorize the mode resolved by the backend. Ordinary schedule timing, resume, retention policy and retargeting have separate checks. Require every permission implicated by a mixed change, including on both old and new targets for retargeting. Show the effects of policy defaults in preview. Scheduling and running a backup requires backup creation on its target. Stop-copy-restart adds stop and start. Pruning or replacing in-flight backups adds deletion. An admitted server-owned schedule can outlive its creator. Recheck its target and any repository required by the backup strategy when it runs. CSI snapshots need no Restic repository. Preserve trusted UIDs for backups, schedules and their children. Historical resources without reliable identity remain accessible only through a currently authorized fleet path. A clone retains its existing same-namespace gate, receives a fresh UID and caller ownership, and copies no ACL. [Backup and scheduling rules](contracts/permission-catalog.md#scheduled-and-indirect-actions) · [Restore types](../../operator/api/v1alpha1/restore_types.go)

**FR-09 · Discovery and revocation.** Apply the same evaluator to fleet search, personal server lists, server detail, direct URLs, child lists, events, MCP reads, WebSockets, SSE and long transfers. A server-only user can navigate to the assigned remote server without gaining sibling inventory. Use the same missing-resource response for hidden and nonexistent targets for this audience. A forbidden action on a visible server receives 403. Preserve legitimate collection-wide clients. Ordinary requests pick up committed revocations on the next request. Recheck identity, target view, action-specific prerequisites, precise action and credential on active streams every five seconds on SQLite and PostgreSQL, including connections on another replica. Cancel when revocation or identity change is observed, or on revalidation failure. MCP keeps its own route/method/upgrade limits, including for panel admins.

**FR-10 · Explain and manage access.** Show **Panel access**, **Cluster / namespace access** and **Server access** in **Users → Person → Access**. Show each permission’s sources, including ownership, direct grants, the named base (direct or inherited), template-declared additions and separately activated recommendations for that base, and any separately assigned optional GameTemplate role, plus any applicable admin Block. Label role type and target even when display names match. Use **Server → Access** for direct membership on the selected UID. Role, action and game-field searches and exact-account lookups return only authorized results. Explain the effects of sensitive grants such as raw console commands or unrestricted file writes before assignment. Bulk operations report each target separately.

On the selected Cluster page add **Roles & permissions** alongside **Overview**, **Nodes** and **Configuration**. Under **Assignments**, show the person, role, exact scope and source. Authorized managers can bind a role to the entire eligible cluster or a verified namespace UID in that registration. Identify primary-admin coverage as inherited. Under **Roles & permissions**, show which permissions in each role apply at the selected scope. Under **Role definitions**, authorized editors can set the required base and select additional live roles by trusted GameTemplate identity. Assigning a server role directly continues to target one UID. Removing one person’s grant and editing a shared role are distinct operations. Keep Kubernetes credential downloads under Configuration. [Current cluster detail page](../../web/src/pages/ClusterDetail.tsx)

Always show the impact preview before confirming a scope grant, change, rebind or removal from either view. Name the person or affected members, cluster and namespace, required base, template additions, and the count of distinct existing servers covered with matches per template. Explicitly state that future servers in that scope inherit the base and matching additions. Show zero when an empty inventory is confirmed, and last-known or unknown counts when a cluster is unreachable. On removal or a shared definition edit, identify independent access that survives. Show only authorized detail. Confirm against the previewed definition and immutable scope identity, and request a fresh preview when the policy changes before save. Ordinary changes to server population are covered by the stated future scope.

Use the same authorization evaluator for preview and execution. For each changed or independently retained capability show the before/after decision, allowed data or action, effective selectors, and attributable sources visible to the reviewer. Include active broad fleet grants and ownership alongside direct and inherited roles. Show a missing prerequisite, matching Block, unavailable game capability or credential limit when it affects the result. For example, adding Viewer to someone who already has `servers:read` can leave logs, players and files visible throughout that namespace. The preview must identify that existing source and distinguish retained access from anything the new grant adds. Reconfirm if role contents, relevant grants, Blocks or the reviewer's authority change before save. Redact identities, names and counts the reviewer cannot inspect. For these four presets show raw game-console authority where granted, the Operator’s actual editable paths and description field, and the Administrator’s destructive child operations and restore effects.

The Cluster and person views use the same scoped `bindings:read`, `bindings:assign` and `bindings:revoke` checks. Mutating a binding requires `bindings:read` on that scope and `scopeRoles:read` for each affected definition. A replacement requires authority for both the removed and the new grant. Editing a shared scoped role is a separate duty and must account for all its assignments. A delegate can look up an exact account and preview the proposed assignment within the delegation workflow without browsing the global directory. Filter assignments, lookup results, previews and role definitions to the caller's authority. ## Beta access reset and reassignment

**FR-11 · Reset beta access.** At cutover, stop accepting `gameplane.local/collaborators` as authorization for any server and retire all historical supplemental cluster/namespace bindings, including whole-cluster and exact-namespace rows on local and remote clusters. Do not import either source into a role, copy its permissions or choose a default. Retain accounts, owner identities, primary OIDC/Helm and manual role assignments, overrides and their logical primary binding. Distinguish that binding using the authoritative primary role and binding identity, including where workload and panel labels both say `local/*`. Treat inconsistent primary records as a preflight error. Report access still supplied independently, the effect of missing views, and the built-in primary admin’s automatic cluster reach.

**Administrator review.** Show the built-in primary panel admin a persistent **Review beta access** banner with outstanding account/target counts. Link each item to **Server → Access** for named roles or custom permissions on a verified server UID, or **Cluster → Roles & permissions** for a scoped role with exactly one base and optional GameTemplate roles. **Users → Person → Access** shows both workflows for the selected person. Start each choice blank. Always preview effective changes, scope and future coverage. Allow the admin to explicitly close an item with **Keep access removed**. Dismissing the banner never resolves an item. Only that admin can complete reassignment for a pending entry, including through an alternate route. Show affected users a generic access-change notice without disclosing hidden targets or other people.

Record former relationships as review evidence only. Show offline, unverified and invalid references separately from verified rows. When inventory becomes available, verify the original identity before offering reassignment. A same-name replacement is a fresh target and requires a fresh grant. Retrying the reset or discovering more history never clears a new grant, opens a completed review again or authorizes an old assignment. Fresh installs have no beta review queue.

**FR-12 · Server membership in panel SQL.** Keep the owner on the GameServer. Store new direct memberships in panel SQL against the registration and immutable GameServer UID, with live role IDs or explicit actions. Verify the live identity before exercising workload access. An admin can revoke a known SQL assignment centrally while its cluster is offline. On reconnection use current SQL policy. A replacement server receives only the grants its own verified scope and template qualify for. [Storage decision](OPEN-DECISIONS.md#d4--where-assignments-live)

**FR-13 · Cutover and recovery.** Fence old readers and writers before atomically activating the new access model for the installation. An offline cluster cannot continue serving cached decisions. Retire `PUT /servers/{name}:collaborators`, including no-op and removal requests. Stop exposing the obsolete list as current membership on server reads. Return `410 Gone` to authorized legacy clients with the new access route, respecting hidden-resource responses for other callers. Stale annotation writes and old supplemental binding records have no effect after activation. Reconcile any restored database against the cutover record and subsequent grants, revocations, Blocks, role and template changes before serving affected access. Keep it closed where current authorization cannot be verified. [Cutover and recovery](plan.md#7--reset-beta-access-and-review-assignments)

### Dry run and maintenance window

1. **Inventory without changing access.** A primary panel admin runs a read-only report before the window and again under the writer fence. For each old source, show the account and verified target, rights that will disappear, access retained from independent sources, unavailable inventory, missing views on retained grants and the separate primary-admin expansion. Unknown counts stay unknown. The report never writes grants or assigns a base.
2. **Prepare recovery.** Confirm a usable primary panel admin and an independent recovery path, back up SQL and relevant Kubernetes objects, and record the audit position. If the panel cannot distinguish primary from supplemental assignments or cannot fence old evaluators, abort before activation. Offline inventory may wait for review because the cutover invalidates that source globally.
3. **Activate during panel maintenance.** Stop old panel replicas and external ACL writers, drain streams and stale access caches, repeat the dry run, then commit the reset and its audit record. Running games need no restart. Reopen the panel once the old sources are inert across replicas, owners and primary assignments are accounted for, and the review banner and new assignment paths work.
4. **Review in the panel.** The primary panel admin can work through the outstanding items after reopening. Explicit grants use current identities and the usual impact preview. Verify the result on both SQLite and PostgreSQL, including independent grants, offline targets, retries and restore. [Implementation runbook](plan.md#7--reset-beta-access-and-review-assignments)

## Audit, inheritance and template permissions

**FR-14 · Audit and support.** Record the actor, account ID, target and scope, stable role ID or explicit action set, allowed/blocked action changes, result, and operation ID. Record live role edits once with the affected scope, plus assignment changes, transfer, beta reset, review decisions and admin grant provenance. For template decisions, record the trusted template identity, reviewed semantics, published permission or optional role IDs, selected base ID, exact delta, reviewer and outcome. Record whether authority came from the approved template declaration set, a separately activated recommendation, or an explicitly granted permission or optional role. Restrict audit details and omit credential material, log contents and secret values.

Fleet-wide audit, scoped audit and `activity.view` for one server have distinct audiences. For a scoped query, filter by verified cluster/namespace before aggregation, pagination, search and totals. Expose only attributable entries and redact or omit bulk/global details outside the caller's reach. [Audit scope](contracts/fleet-permissions.md)

**FR-15 · Scope-wide server inheritance.** A cluster/namespace role definition holds scope-eligible fleet permissions, exactly one live base server role (**Viewer**, **Power User**, **Operator** or **Administrator**), and zero or more live GameTemplate roles keyed by trusted template identity. No base is preselected when defining a role. Reject a new scoped role or grant that lacks a valid base, has multiple bases or references a template role under the wrong template. Require authority to grant the complete definition across the target scope, including its future servers. A combined installation can bind the entire local workload cluster independently of the logical primary `local/*` panel binding. Distinguish their binding kinds during authorization, OIDC sync, edits and revocation. Apply the same workload-only permission restrictions to whole local and remote cluster roles. Standalone mode with no local workload offers no local workload target.

Store one binding per person, role and scope. Resolve it on discovery and on each server action against the registered cluster, managed namespace, live target and effective GameTemplate. A whole-cluster grant covers every current and future server in its managed namespaces, including namespaces added later. An exact-namespace grant covers the immutable Kubernetes Namespace UID within the original cluster registration. A name is a display label. Renewing credentials for the same verified cluster keeps its registration identity. Re-registering a cluster creates a new identity. A matching member receives the base everywhere. On each server, resolve the approved declared additions and activated recommendations for that exact base and trusted template, then union the separately selected optional template roles. A server with no applicable additions still receives the base. A template change immediately re-evaluates all template-derived grants. Overlapping cluster, namespace, direct and owner rights combine, subject to explicit Blocks and existing credential and platform limits. Revoking one source removes only its contribution. A scope grant needs no fan-out, backfill or copied per-server membership. Direct assignments and explicit bulk target selections keep their UID semantics. [Three-layer decision](OPEN-DECISIONS.md#d5--panel-cluster-and-server-access)

Scoped definitions store the chosen base and optional role IDs. The panel tracks the template’s approved declarations separately from recommendation opt-ins. Both follow the named base whether assigned directly or through a scope. Neither writes memberships for individual servers. [GameTemplate declarations and approval](contracts/permission-catalog.md#gametemplate-roles)

On verified namespace deletion/recreation or registration replacement, mark exact grants and Blocks on the prior identity stale. Never retarget by name. Rebinding a grant requires an actor authorized for the new scope and its full grant. Only a primary panel admin can rebind a Block. Both require a fresh identity check and impact preview. A valid whole-cluster grant continues to include new managed namespaces within its own registration. If a stale Block could expose previously blocked access through another grant, hold just the affected subject, action and selectors on the replacement pending primary-admin review. The admin may confirm a replacement Block or explicitly release the hold after preview. Temporary unreachability alone does not establish replacement. Unverified targets never authorize a new binding or workload action.

**FR-16 · Admin-only Block.** Only the built-in primary panel admin can create, edit or remove a Block. A rule identifies a user or live role, an exact server UID or cluster/namespace, an ordinary workload action and applicable selectors. After platform/credential limits, a matching Block takes precedence over every ordinary allow, including inherited bases, matching GameTemplate roles, current fleet grants and direct grants. Blocking a required view denies dependent operations. A Block on `server.view` suppresses every ordinary server action on the matched UID, including discovery and active connections. Other independently usable actions stay available when a narrower view is blocked. Removing a Block re-evaluates the surviving grants and does not grant access by itself. Preserve the built-in panel admin recovery path. Authorize the same action on every entry point, including full-object updates and open streams. The decision preview identifies the source within the viewer's authorization. Raw console input is a separate action. A Block on Kick or Ban covers the corresponding Gameplane moderation operation and its named wrappers. A person with effective `console.send` and its required views can still enter commands accepted by the game. Show that remaining ability in the impact preview. Audit changes with actor and scope. [Block contract](OPEN-DECISIONS.md#d6--explicit-exceptions-to-inherited-access)

**FR-17 · Narrow workload permissions and compatibility.** Register the [workload permissions](contracts/fleet-permissions.md) with their permitted grant scopes. Split server inventory, cluster health, nodes, storage, usage, template management, modules and trusted sources, packet capture, backup destinations and scoped audit. A new cluster/namespace grant with inventory duties still receives the required base on every covered server. The inventory permission itself returns only identity and status. Enforce target, selector, operation and sensitivity on every corresponding read, mutation and credential response. Keep existing broad fleet keys for compatibility on their supported routes and fields, subject to their effective view prerequisites, scope and protections. Register new capabilities explicitly and show what each broad key contributes in the role picker and preview.

**FR-18 · GameTemplate permissions, declared base additions, recommendations and optional roles.** A template may declare any combination of the following in its proposed `spec.serverAccess` contract. The template author chooses which permissions belong to each base and which to offer as suggestions. The trusted template identity and stable local IDs identify them independent of display names or translations. Which installations can share one approval is an [open decision](OPEN-DECISIONS.md#open--sharing-template-approvals-across-installations). [Declaration format and examples](contracts/permission-catalog.md#gametemplate-roles)

| Declaration | What the panel admin approves | Who receives access |
| --- | --- | --- |
| Individual permission | Publish a named, validated mapping to a canonical server action and explicit selectors. | Someone whose effective grant selects it, individually or through a declared base addition, active recommendation or assigned role. Publication alone creates no grant. |
| Declared base-role addition (`baseRoleAdditions`) | Approve the template permission declaration set and its effective impact as one decision. Each declared permission is added to its author-specified base in the same commit. | Existing and future direct or inherited holders of that exact base on matching servers. There is no second activation or per-user assignment. |
| Base-role recommendation | Separately opt in to an enumerated set for one trusted template and one explicit base ID. Review each base independently. | Direct and inherited holders of that exact base on servers running the matching template. The shared base definition and the other three bases keep their own permissions. |
| Optional named role | Publish a reusable template role with its reviewed permissions. Preview later changes to an assigned role as a live role edit. | Someone explicitly assigned that role on a matching server or through a cluster/namespace role that selects it. |

Before accepting or updating a template declaration set, activating a recommendation, or withdrawing either source, the built-in primary panel admin opens **GameTemplate proposals** in the server-role library and reviews the effective before/after results for the affected assignments. Show the base, template, permissions and selectors, direct and inherited holders, distinct affected servers, Blocks, access retained from other sources, and coverage of future matching servers. Distinguish matching servers from servers where someone actually gains or loses access. Mark partial or last-known counts. Confirm against the reviewed semantics and current policy. Do not copy grants onto users or server UIDs. An approver may decline a declaration set and keep the previous verified policy. Accepting it applies its entire declared base-addition diff atomically, including removals. The panel admin can explicitly withdraw an active contribution after preview. The next approval must explicitly show any restoration of withdrawn rights as a gain. Installing an update or rolling back the package cannot undo that withdrawal.

A named base assignment follows approved changes on the next decision. A custom grant copied from that base follows its own explicit selection. If an explicitly selected template permission changes meaning, its dependency on the approved mapping still applies. Include all dependent custom grants, optional roles and base mappings in the reapproval preview. Enforce canonical checks, including moderation or power effects behind game buttons, alongside existing selectors, Blocks and platform limits. Installing or updating a package alone cannot grant a declared addition, activate a recommendation or assign an optional role. Changing or removing only an optional recommendation leaves the previously approved selection active while its underlying permissions still verify. If a trusted permission or its command or field disappears or changes meaning, suspend the affected contribution, preserve independently valid grants, and require a fresh review before reactivation. Reusing an ID or rolling back a package cannot silently reinstate a withdrawn approval. Verify the server’s effective definition at dispatch during mixed-version rollouts.
