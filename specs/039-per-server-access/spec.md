# Panel, cluster and per-server access

Draft for [Gameplane #1063](https://github.com/GameplanePanel/Gameplane/issues/1063), updated November 23, 2026. The Gameplane baseline is `7ea5be6a`. The [panel and workload catalog](contracts/fleet-permissions.md) and [server catalog and base roles](contracts/permission-catalog.md) list the exact permissions introduced by this design. See the [reference-panel comparison](reference-panels.md), [implementation plan](plan.md), [delivery tasks](tasks.md) and [decision record](OPEN-DECISIONS.md).

**Release policy.** Ship 039 as a **breaking 0.x minor release**. Manual invitation clients must send an explicit access choice. After cutover, administration tools must use the panel access API for membership changes. The legacy collaborator endpoint supports only assignments it can represent and returns a conflict for a mixed or granular assignment. Existing installations receive an access-preserving migration. Fresh installations start directly with the new model. [Upgrade and dry run](#migrating-existing-collaborators)

## Access hierarchy

A person can receive access at any combination of three layers. Direct server access works for an account with zero effective panel permissions and no supplemental cluster or namespace grant.

```text
Panel account
├─ 1. Panel access — Users & RBAC
│  ├─ Primary panel role from OIDC/Helm or manual assignment
│  ├─ Panel duties, or the explicit “Assigned servers only” choice
│  └─ Built-in primary panel admin covers every current and future registered cluster
├─ 2. Cluster / namespace access — Cluster → Roles & permissions
│  ├─ Whole cluster → all current and future servers in its managed namespaces
│  ├─ Exact cluster + namespace → all current and future servers there
│  └─ Each new scoped role grants
│     ├─ Eligible infrastructure permissions, e.g. servers:create with template access
│     ├─ Exactly one base → Viewer, Power User, Operator or Administrator
│     └─ Optional named GameTemplate roles → selected for matching templates only
└─ 3. Individual server access — Server → Access, one immutable UID
   ├─ Ownership → independent, including protected owner operations
   ├─ Inherited → server rights from all matching cluster and namespace roles
   └─ Direct assignment → choose one form
      ├─ Named live roles → bases and/or matching optional GameTemplate roles
      └─ Custom permissions → selected common actions and/or approved template permissions

On each server, resolve every named base held directly or inherited
├─ Common base permissions
├─ GameTemplate-declared additions for that exact base → active on template approval
└─ GameTemplate recommendations for that exact base → active on separate opt-in

Combine these with other valid grants and explicitly selected optional roles.
Apply canonical operation checks, selector limits, applicable admin Blocks and platform policy.
```

| Access layer | Current Gameplane | Spec 039 |
| --- | --- | --- |
| Panel | A primary role comes from OIDC/Helm or manual assignment. Existing permissions cover accounts, roles and global settings. | Delegate individual account, role, settings and cluster-registration duties. Offer **Assigned servers only** for zero panel permissions. The built-in primary admin reaches every current and future registered cluster. |
| Cluster / namespace | **Users & RBAC** edits supplemental cluster or namespace bindings for fleet permissions. | In **Cluster → Roles & permissions**, assign inventory, provisioning, template use, scoped audit and operational duties independently. Choose exactly one base server role for every existing and future server in scope. Matching templates can contribute approved permissions to that base. A manager can also select optional template roles. The Cluster and person views edit the same binding. |
| Individual server | Ownership and the collaborator list authorize a fixed set of server operations. | Ownership, inherited roles and direct roles or custom actions can each supply access. A direct base role receives its approved declared additions and activated recommendations for the server’s effective template. The assignment in panel SQL targets that server’s immutable UID. |

For example, **Tournament staff** in `eu/tournaments` grants **Viewer** on every server and the **Match referee** role on servers running its CS2 GameTemplate. Alex immediately sees existing servers A, B and C. If A and B run CS2, Alex can referee both. Tomorrow’s server D receives Viewer automatically and adds Match referee if it runs that CS2 template. Alex can also have an independent direct role on one server. Separately, a person assigned Administrator on A directly or through a scoped role receives any CS2-declared Administrator additions approved for that template. Match referee is a separate assignment. [Scope decision](OPEN-DECISIONS.md#d5--panel-cluster-and-server-access)

## What someone should be able to do

A panel administrator invites Alex, explicitly chooses **Assigned servers only** for the new account, then selects different duties on two servers. The servers can share a namespace. A different account can receive a namespace grant that permits server creation at an authorized placement. A manual invitation opens with blank access choices. A panel admin designs reusable roles, and an inviter can choose custom permissions for a person who needs a different job.

| Priority | Given | When | Expected result |
| --- | --- | --- | --- |
| P1 | Survival, Staging and Production are in the same namespace | With no other grants, Alex receives Power User on Survival and a custom Networking editor role on Staging | Alex can restart Survival and edit Networking on Staging. Restarting Staging and editing Survival networking are refused. Production is absent from lists, counts, events and direct links. |
| P1 | Referees on two servers hold the Match staff role | A panel admin adds an approved CS2 match action and removes raw console access | Every assignee picks up the new definition on the next request. The same rule applies to assignments on an offline cluster when it reconnects. Unsupported games gain no CS2 controls. |
| P1 | A user collaborates on two servers with a separate OIDC role | The subsequent migration runs while one cluster is offline | The reachable server retains its former collaborator permissions. The other converts when reachable. The OIDC binding and its scope survive both conversions. |
| P1 | A local or OIDC account holds the built-in primary admin role | A second cluster is registered after the admin signed in | The next request can discover the cluster and administer its managed workloads without rebinding or signing in again. A subsequent committed demotion removes that implicit access. |
| P1 | Alex has direct Power User on Match A. A and B run CS2 and C runs Valheim in EU tournaments. | From the Cluster tab, assign Tournament staff with required Viewer and CS2 Match referee. Add D, then remove the binding from Alex’s access page. | The preview shows three current servers, two CS2 matches and future coverage. All four inherit Viewer while assigned. Only matching CS2 servers inherit Referee. Removal leaves Alex’s direct Power User on A. |
| P1 | CS2 declares Pause match and Resume match as additions to Administrator, recommends the same controls for Power User, and offers Match referee. Alex holds Administrator directly on CS2 A and inherits it on CS2 B. | The primary panel admin previews and approves the template permission declarations, leaving the Power User recommendation inactive. | Alex gets both named controls on A and B with that approval. Valheim Administrator receives its common base. CS2 Power User receives no named controls from the recommendation until opt-in. A CS2 Viewer explicitly assigned Match referee can use both independently. |
| P2 | Alex also holds an existing namespace-scoped panel Viewer role | An owner removes Alex’s direct assignment | The preview identifies the access Alex retains and its source. Only an authorized fleet-role manager can change that source. |

## Roles, grants and scope

**FR-01 · Panel roles and scoped bindings.** The primary panel role controls administrative actions such as changing global settings (`config:manage`) and managing accounts. The existing fleet catalog also supplies the workload permissions used by cluster and namespace grants. Keep `roles`, `role_permissions` and `user_role_bindings` for their existing purposes. Add the server-role references described in FR-15 to cluster/namespace role definitions. Keep these scoped definitions distinct from primary panel assignment, even where a fleet role name is shared. An existing operator or viewer keeps its previous reach on upgrade. Present historical supplemental bindings as legacy until an authorized manager explicitly chooses a base and confirms the impact of conversion. New cluster/namespace role assignments always require the base. Preserve OIDC first-match ordering, fallback/deny behavior, manual overrides, return to SSO control, lockout guards, existing Helm `api.oidc.roleRules`, `roleMappings` and `defaultRole`, and dashboard override precedence. Signing in updates the primary fleet role according to those rules. It never creates, replaces or clears a direct server assignment. [Existing SSO contract](../done_034-sso-group-role-rules/spec.md)

Use the [panel and workload catalog](contracts/fleet-permissions.md) for account lookup and directory listing, account lifecycle and credential operations, primary-role assignment, panel role authoring, infrastructure registration and credential issuance. Authorize the actual changes in a request, including implicit grants in account creation or a role edit, and preserve existing lockout and identity-provider protections. Section-level panel settings grant redacted reads and supported writes independently for general, notifications, telemetry, i18n and mod registries. An auth-section reader sees the redacted configuration. Authentication/OIDC changes require the protected built-in admin. Preserve Helm/operator restrictions and the historical reach of `config:read` and `config:manage`. [Configuration sections](../../api/internal/handlers/config.go) · [Protected routes](../../api/internal/rbac/rbac.go)

Add `servers:create` for ordinary provisioning at an authorized placement. A narrow provisioner can use a selected GameTemplate via `templates:use` and see only its creation inputs. Intersect the allowed template identities and destination cluster/namespace on discovery and again on submission. Preserve existing `servers:write` creation and `templates:read` discovery behavior for legacy callers. Creation grants no independent authority over existing servers. The required base and the creator's ownership have their own effects. [Workload catalog](contracts/fleet-permissions.md) · [Placement discovery](../../api/internal/handlers/fleet.go)

**FR-02 · Panel admin identity.** Derive panel-admin status in one authorization snapshot by verifying that the user's primary role is the built-in `admin`, that it carries its protected wildcard, and that its primary binding is present at logical `local/*`. Treat this as a virtual all-clusters/all-namespaces wildcard at request time. Keep the stored primary binding and expose the resolved wildcard and its origin consistently to clients. Do not enumerate clusters at login or write a binding on registration. A scoped binding to the built-in role, a custom role name, `roles:manage`, and a server role are insufficient to promote an account. Bootstrap, manual promotion and OIDC selection of the actual primary admin qualify equally. Demotion takes effect when the role update commits, including an OIDC change applied at sign-in.

Admins can perform every supported panel-admin operation on every **registered** cluster and managed namespace, including owner-or-admin server operations, subject to installation mode, cluster reachability, native Kubernetes permissions and existing admission policies. A standalone panel with zero clusters still has a panel admin and never fabricates a local workload cluster. Unknown targets, unsupported remote operations, owner-personal share links, personal credentials and the read-only MCP token contract keep their existing boundaries. [Standalone contract](../done_025-standalone-panel/spec.md) · [MCP contract](../037-scope-mcp-server-permissions/spec.md)

**FR-03 · Live server role library.** Gameplane ships the four base roles in FR-06. The built-in primary panel admin manages reusable server roles and approves publication of GameTemplate permissions and optional roles. Approving the template permission declarations applies the author’s declared base additions in the same transaction. Optional recommendations have a separate activation decision under FR-18. Each live role has a stable ID, name and action set. Direct memberships and scoped definitions reference that ID. One edit changes all applicable assignments on the next authorization decision without role revisions or pinning. Audit the before/after actions and preview the effect on direct and inherited access across scopes. Count direct SQL assignments separately from covered workloads, labeling last-known or unavailable inventory. Retiring a role prevents new selection while existing references continue to resolve. Refuse deletion while a membership or scoped definition references it. A scoped definition must retain one usable base with `server.view`. [Live-edit decision](OPEN-DECISIONS.md#d1--editing-a-base-role)

**FR-04 · Direct server assignments and delegation.** A direct assignment binds a panel account to a registered cluster, namespace, server name and immutable GameServer UID. Choose either named live roles (union) or an explicit custom action set. Replacing a live role with custom actions requires a preview. The person then ceases to be a member of that role on that assignment. Delegation uses four independent permissions: `members.view`, `members.invite`, `members.edit` and `members.remove`. On a delegated change, require the correct membership action and authority over the associated actions, selectors and target, including dormant grants. For a named base, include its approved declared additions and separately activated recommendations on the target template. For an inherited grant, check approved additions across its entire delegable scope, including future matching workloads. A later primary-admin approval is a separate live policy decision. Owners and target-authorized admins may appoint membership managers. Delegates cannot modify themselves, appoint further managers, alter inherited fleet grants or manage Blocks. Only the built-in panel admin publishes changes to shared server-role definitions. Ownership transfer, wipe, deletion and personal share links retain their separate policies. [Delegation contract](OPEN-DECISIONS.md#d2--who-can-delegate)

**FR-05 · Explicit invitations.** Manual account and server invitations start with no selection. For a new local account, require an explicit fleet access choice, including the protected zero-permission **Assigned servers only** option. For each server or explicitly selected group of servers, choose named roles or **Custom permissions** with at least one action. For an existing account require only the requested server assignment and preserve its primary role. The API rejects missing, empty, ambiguous or conflicting selections before creating an account or membership. A general account-only invitation can explicitly select its primary role without granting a server. Assigning a configured cluster/namespace role presents its selected base, matching GameTemplate roles and scope for confirmation. A manual invitation never preselects a binding. OIDC's configured first-login defaults, identity matching and Helm mappings continue as configured. [D3](OPEN-DECISIONS.md#d3--invitations-and-migration-order)

## Server permissions

**FR-06 · Action catalog and shipped roles.** Implement the [catalog](contracts/permission-catalog.md) for the work Gameplane exposes. Its rows define native operations, prerequisites, scoped selectors, the approved base roles and acceptance cases. Keep game-specific action and field identities qualified by their trusted module/template. A meaningful change to the command or field contract requires fresh approval of that action, independent of live role editing. The picker intersects rights with the target’s capabilities. A CS2 referee can pause a match without console access, a Terraria host can broadcast without receiving ban, and a Valheim server does not acquire controls its template omits. [Pinned CS2 template](https://github.com/GameplanePanel/module/blob/c310076716ce8ccc63619f88ddc69547415dcfc2/cs2/template.yaml#L181) · [Pinned Terraria template](https://github.com/GameplanePanel/module/blob/c310076716ce8ccc63619f88ddc69547415dcfc2/terraria/template.yaml#L177)

Every usable server grant includes the minimum identity and navigation needed to exercise it. Editing an individual field includes its redacted view where appropriate and never grants read access to sibling fields, secret values, or an entire settings section. Display a distinguishable status for an unauthorized action, an unsupported module feature and a feature disabled by policy. Directory, field and named-action constraints are enforced on every API and transport that can perform that operation. Platform credentials, arbitrary images, host diagnostics and security-context overrides retain their existing gates. [Security-context contract](../030-security-context-overrides/spec.md)

A roster reader sees display names. Persistent identifiers, faction and similar identity details require `players.identityDetails` as well. Basic ban entries and their reasons or issuing actors have separate visibility. Apply these projections to the initial response and live updates. A moderator with kick authority can select an allowed player without receiving their persistent ID. The new privacy keys are optional additions to a role. [Player, ban and moderation contract](contracts/permission-catalog.md#operations)

**Approved base server roles.** Viewer grants basic status and filtered workload events. Power User adds start, stop, restart, wake, live and historical logs, and raw game console input. Operator adds routine file creation, reading and editing only at reviewed paths and allows editing the server description. Administrator receives all 84 enumerated server actions with their approved selectors, including member management and deletion of child resources. Deleting or wiping the GameServer, transferring ownership and owner-personal operations retain their existing gates. Separate panel, placement and other-target authority still applies. These are the shipped common grants. A template can add approved actions or selectors to any explicitly named base on matching servers. It can also offer optional recommendations for separate activation. The Legacy collaborator grant is reserved for upgrades. [Exact base permissions and selectors](contracts/permission-catalog.md#default-base-server-roles)

**FR-07 · Data and writes.** Authorize every API operation and project its response using the server and action. A status-only grant returns only identity, status and navigation essentials. Redact unauthorized settings, file contents, rosters, ACLs, log text and cross-server references from detail, fleet, events and nested or aggregated responses. A pre-existing scoped panel grant can still supply the fields covered by its original permission, subject to applicable Blocks. Section writes accept a typed field allowlist and require a matching resource version. Reject a mixed authorized/unauthorized payload as one operation. Reserved metadata and secret values never become writable or readable through a section form. If a field appears on two screens, both use its canonical action. For example clearing an image override, changing server suspension and writing tunnel credentials retain their respective checks wherever exposed. Keep generic full-object writes behind their existing fleet check and protected-field guards. Also authorize the actual field/action diff for any fleet writer subject to a block. A mixed generic PUT changing a blocked networking field must fail atomically. A permitted form receives the minimum server-specific schema/options it needs without requiring catalog-wide or inventory access.

**FR-08 · Related resources.** A Restic overwrite requires source backup access and `restores.applyExisting` on the verified destination UID. A CSI restore to a new server requires source backup access, `restores.createNew` on the verified source UID and provisioning authority at the destination. Both recovery modes stay in the backup’s cluster and namespace. Authorize the mode resolved by the backend. Ordinary schedule timing, resume, retention policy and retargeting have separate checks. Require every permission implicated by a mixed change, including on both old and new targets for retargeting. Show the effects of policy defaults in preview. Scheduling and running a backup requires backup creation on its target. Stop-copy-restart adds stop and start. Pruning or replacing in-flight backups adds deletion. An admitted server-owned schedule can outlive its creator. Recheck its target and any repository required by the backup strategy when it runs. CSI snapshots need no Restic repository. Preserve trusted UIDs for backups, schedules and their children. Historical resources without reliable identity remain accessible under their existing fleet grants. A clone retains its existing same-namespace gate, receives a fresh UID and caller ownership, and copies no ACL. [Backup and scheduling rules](contracts/permission-catalog.md#scheduled-and-indirect-actions) · [Restore types](../../operator/api/v1alpha1/restore_types.go)

**FR-09 · Discovery and revocation.** Apply the same evaluator to fleet search, personal server lists, server detail, direct URLs, child lists, events, MCP reads, WebSockets, SSE and long transfers. A server-only user can navigate to the assigned remote server without gaining sibling inventory. Use the same missing-resource response for hidden and nonexistent targets for this audience. A forbidden action on a visible server receives 403. Preserve legitimate collection-wide clients. Ordinary requests pick up committed revocations on the next request. Recheck identity, precise action and credential on active streams every five seconds on SQLite and PostgreSQL, including connections on another replica. Cancel when revocation or identity change is observed, or on revalidation failure. MCP keeps its own route/method/upgrade limits, including for panel admins.

**FR-10 · Explain and manage access.** Show **Panel access**, **Cluster / namespace access** and **Server access** in **Users → Person → Access**. Show each permission’s sources, including ownership, direct grants, the named base (direct or inherited), template-declared additions and separately activated recommendations for that base, and any separately assigned optional GameTemplate role, plus any applicable admin Block. Label role type and target even when display names match. Use **Server → Access** for direct membership on the selected UID. Role, action and game-field searches and exact-account lookups return only authorized results. Explain the effects of sensitive grants such as raw console commands or unrestricted file writes before assignment. Bulk operations report each target separately.

On the selected Cluster page add **Roles & permissions** alongside **Overview**, **Nodes** and **Configuration**. Under **Assignments**, show the person, role, exact scope and source. Authorized managers can bind a role to the entire eligible cluster or a named namespace. Identify primary-admin coverage as inherited. Under **Roles & permissions**, show which permissions in each role apply at the selected scope. Under **Role definitions**, authorized editors can set the required base and select additional live roles by trusted GameTemplate identity. Assigning a server role directly continues to target one UID. Removing one person’s grant and editing a shared role are distinct operations. Keep Kubernetes credential downloads under Configuration. [Current cluster detail page](../../web/src/pages/ClusterDetail.tsx)

Always show the impact preview before confirming a scope grant, change, conversion or removal from either view. Name the person or affected members, cluster and namespace, required base, template additions, and the count of distinct existing servers covered with matches per template. Explicitly state that future servers in that scope inherit the base and matching additions. Show zero when an empty inventory is confirmed, and last-known or unknown counts when a cluster is unreachable. On removal or a shared definition edit, identify independent access that survives. Show only authorized detail. Confirm against the previewed definition and scope, and request a fresh preview when the policy changes before save. Ordinary changes to server population are covered by the stated future scope.

Use the same authorization evaluator for preview and execution. For each changed or independently retained capability show the before/after decision, allowed data or action, effective selectors, and attributable sources visible to the reviewer. Include broad legacy fleet grants and ownership alongside direct and inherited roles. Show a matching Block, unavailable game capability or credential limit when it affects the result. For example, adding Viewer to someone who already has `servers:read` can leave logs, players and files visible throughout that namespace. The preview must identify that existing source and distinguish retained access from anything the new grant adds. Reconfirm if role contents, relevant grants, Blocks or the reviewer's authority change before save. Redact identities, names and counts the reviewer cannot inspect. For these four presets show raw game-console authority where granted, the Operator’s actual editable paths and description field, and the Administrator’s destructive child operations and restore effects.

The Cluster and person views use the same scoped `bindings:read`, `bindings:assign` and `bindings:revoke` checks. A replacement requires authority for both the removed and the new grant. Editing a shared scoped role is a separate duty and must account for all its assignments. A delegate can look up an exact account and preview the proposed assignment within the delegation workflow without browsing the global directory. Filter assignments, lookup results, previews and role definitions to the caller's authority. [Scope and delegation catalog](contracts/fleet-permissions.md) · [Current binding workflow](../../docs/multicluster-ui.md#user-access)

## Migrating existing collaborators

**FR-11 · Preserve legacy access in a later phase.** Before shipping the conversion, verify the compatibility grant against the old evaluator’s routes, scope, field visibility and protected operations. Keep the existing reader and collaborator behavior until parity is demonstrated. Read `gameplane.local/collaborators` as user IDs. Deduplicate valid IDs and report malformed entries and missing accounts. Names are display data. Preserve ownership and all independent fleet grants. Import the actual entitlement as a frozen, migration-only **Legacy collaborator** grant for the original server UID. It confers no named base, GameTemplate additions, sibling access or rights on a later replacement UID. Keep it out of the invitation and role pickers. The table gives the baseline to verify.

| Legacy contribution to carry forward | Permissions it must not add |
| --- | --- |
| Existing redacted server detail, events, logs, console/game actions, power and wake, same-namespace clone, file reads and mutations, moderation/whitelist, supported content management and tunnel credential operations | General server PUT or settings save, backups, restores, schedules, capture, public share administration, delete, wipe, transfer, or managing access. Separate pre-existing grants still count. |

**Existing cluster and namespace grants.** Keep each historical binding’s registered cluster, namespace selection, role and permission checks, including its original reach over future matching workloads. For example, existing cluster inventory access keeps its node inventory, and an existing namespace `servers:read` grant keeps its log and file reads there. Historical bindings get no base or additional template roles during migration. Each new-style scoped assignment requires an explicit choice of one of the four base roles. Replacing an old binding requires an explicit base choice and a before/after preview of existing and future coverage. Preserve ownership, OIDC/Helm primary roles, manual overrides and overlapping grants independently. Report the built-in primary panel admin’s automatic all-cluster coverage under FR-02 as the sole intentional automatic access expansion.

**FR-12 · Server membership in panel SQL.** Keep the owner on the GameServer. Use panel SQL as the sole authority for new and converted direct memberships, keyed to the registered cluster and immutable workload identity. Store live role IDs or explicit actions. Verify the target UID before exercising workload access. A committed panel-admin revocation of a known, converted membership takes effect centrally even while the cluster is offline. The next request on reconnection uses the current SQL decision. A replacement server receives no old direct membership. Its own verified scope and template determine any current inherited rights. Preserve a durable per-UID converted record even when no members remain. [Storage decision](OPEN-DECISIONS.md#d4--where-assignments-live)

**FR-13 · Upgrade and recovery.** After verifying the legacy mapping, fence legacy writers and identify eligible pre-upgrade UIDs. Use a single SQL transaction to create exact legacy memberships and mark that UID converted. Route membership edits through the same serialization point. One-time removal of obsolete Kubernetes annotations is cleanup and must never reactivate them on a converted UID. Track and resume offline targets. Preserve the old collaborator endpoint only for representable legacy lists. Before serving a restored panel DB, reconcile subsequent direct and scoped grant changes, Blocks, live role edits, template publication and the latest approvals or withdrawals of declared additions and recommendations against independent records. Keep authorization closed for affected targets until their current policy can be established. [Cutover and recovery](plan.md#7--convert-existing-collaborators)

### Migration dry run and maintenance window

1. **Preview the upgrade.** Before the scheduled window, run the proposed read-only migration report using the old authorization rules and the proposed imported state against the same inventory. Identify each grant by account ID and its source, registered cluster, exact scope and server UID where applicable. Compare allowed and denied operations, visible fields and discovery for each source **and** the effective result after combining sources. Show the legacy scope rule for future workloads. Report counts of verified, pending and ambiguous targets separately and list any invalid account references. Confirmed zero and unknown are distinct. The report simulates authorization. It never invokes a permission writer or workload operation, invalidates a session, or writes grants, conversion markers or workload annotations.
2. **Decide what is ready.** Require parity for ordinary grants on each target eligible for conversion. If a collaborator would lose log access from their membership but still sees logs through a fleet role, the source difference must still block that conversion. Report built-in primary admins and their newly reachable clusters separately. Mark an offline cluster pending and an ambiguous identity for reconciliation. Neither can be counted as verified or converted by guessing.
3. **Cut over during a scheduled panel maintenance window.** Stop old panel replicas and out-of-band membership writers, and prevent concurrent changes to the access inputs being verified. Take coordinated backups of panel SQL and relevant Kubernetes objects, record the audit position, then repeat the dry run against the fenced state. Recheck identities and input versions when committing. Keep unresolved targets isolated. Abort before activation if a mismatch cannot be isolated or the writer barrier or backups cannot be verified. This is a panel-access maintenance window. Running game servers need no restart for the migration.
4. **Verify before reopening writes.** Import verified original UIDs transactionally and compare actual post-import access with the preview. Preserve the distinction between pending, failed and complete, and retry without duplicating memberships. Resume an offline target only after verifying its original identity and reconciling pending revocations. After activation, use conversion-aware recovery and reconcile revocations before restoring access. [Cutover and recovery runbook](plan.md#7--convert-existing-collaborators)

## Audit, inheritance and template permissions

**FR-14 · Audit and support.** Record the actor, account ID, target and scope, stable role ID or explicit action set, allowed/blocked action changes, result, and operation ID. Record live role edits once with the affected scope, plus assignment changes, transfer, conversion and admin grant provenance. For template decisions, record the trusted template identity, reviewed semantics, published permission or optional role IDs, selected base ID, exact delta, reviewer and outcome. Record whether authority came from the approved template declaration set, a separately activated recommendation, or an explicitly granted permission or optional role. Restrict audit details and omit credential material, log contents and secret values.

Fleet-wide audit, scoped audit and `activity.view` for one server have distinct audiences. For a scoped query, filter by verified cluster/namespace before aggregation, pagination, search and totals. Expose only attributable entries and redact or omit bulk/global details outside the caller's reach. [Audit scope](contracts/fleet-permissions.md)

**FR-15 · Scope-wide server inheritance.** A cluster/namespace role definition holds scope-eligible fleet permissions, exactly one live base server role (**Viewer**, **Power User**, **Operator** or **Administrator**), and zero or more live GameTemplate roles keyed by trusted template identity. No base is preselected when defining a role. Reject a new scoped role or grant that lacks a valid base, has multiple bases or references a template role under the wrong template. Require authority to grant the complete definition across the target scope, including its future servers. A combined installation can bind the entire local workload cluster independently of the logical primary `local/*` panel binding. Distinguish their binding kinds during authorization, OIDC sync, edits and revocation. Apply the same workload-only permission restrictions to whole local and remote cluster roles. Standalone mode with no local workload offers no local workload target.

Store one binding per person, role and scope. Resolve it on discovery and on each server action against the registered cluster, managed namespace, live target and effective GameTemplate. A whole-cluster grant covers every current and future server in its managed namespaces, including namespaces added later. A namespace grant covers that exact cluster/namespace. A matching member receives the base everywhere. On each server, resolve the approved declared additions and activated recommendations for that exact base and trusted template, then union the separately selected optional template roles. A server with no applicable additions still receives the base. A template change immediately re-evaluates all template-derived grants. Overlapping cluster, namespace, direct and owner rights combine, subject to explicit Blocks and existing credential and platform limits. Revoking one source removes only its contribution. A scope grant needs no fan-out, backfill or copied per-server membership. Direct assignments and explicit bulk target selections keep their UID semantics. [Three-layer decision](OPEN-DECISIONS.md#d5--panel-cluster-and-server-access)

Scoped definitions store the chosen base and optional role IDs. The panel tracks the template’s approved declarations separately from recommendation opt-ins. Both follow the named base whether assigned directly or through a scope. Neither writes memberships for individual servers. [GameTemplate declarations and approval](contracts/permission-catalog.md#gametemplate-roles)

**FR-16 · Admin-only Block.** Only the built-in primary panel admin can create, edit or remove a Block. A rule identifies a user or live role, an exact server UID or cluster/namespace, an ordinary workload action and applicable selectors. After platform/credential limits, a matching Block takes precedence over every ordinary allow, including inherited bases, matching GameTemplate roles, legacy fleet grants and direct grants. Unspecified actions remain neutral. Removing a Block re-evaluates the surviving grants and does not grant access by itself. Preserve the built-in panel admin recovery path. Authorize the same action on every entry point, including full-object updates and open streams. The decision preview identifies the source within the viewer's authorization. Audit changes with actor and scope. [Block contract](OPEN-DECISIONS.md#d6--explicit-exceptions-to-inherited-access)

**FR-17 · Narrow workload permissions and compatibility.** Register the [workload permissions](contracts/fleet-permissions.md) with their permitted grant scopes. Split server inventory, cluster health, nodes, storage, usage, template management, modules and trusted sources, packet capture, backup destinations and scoped audit. A new cluster/namespace grant with inventory duties still receives the required base on every covered server. The inventory permission itself returns only identity and status. Enforce target, selector, operation and sensitivity on every corresponding read, mutation and credential response. Keep existing broad fleet keys for compatibility with their baseline routes, response fields, scopes and protections. Register new capabilities explicitly and expose legacy breadth in the role picker and preview.

**FR-18 · GameTemplate permissions, declared base additions, recommendations and optional roles.** A template may declare any combination of the following in its proposed `spec.serverAccess` contract. The template author chooses which permissions belong to each base and which to offer as suggestions. The trusted template identity and stable local IDs identify them across installs and translations. [Declaration format and examples](contracts/permission-catalog.md#gametemplate-roles)

| Declaration | What the panel admin approves | Who receives access |
| --- | --- | --- |
| Individual permission | Publish a named, validated mapping to a canonical server action and explicit selectors. | Someone whose effective grant selects it, individually or through a declared base addition, active recommendation or assigned role. Publication alone creates no grant. |
| Declared base-role addition (`baseRoleAdditions`) | Approve the template permission declaration set and its effective impact as one decision. Each declared permission is added to its author-specified base in the same commit. | Existing and future direct or inherited holders of that exact base on matching servers. There is no second activation or per-user assignment. |
| Base-role recommendation | Separately opt in to an enumerated set for one trusted template and one explicit base ID. Review each base independently. | Direct and inherited holders of that exact base on servers running the matching template. The shared base definition and the other three bases keep their own permissions. |
| Optional named role | Publish a reusable template role with its reviewed permissions. Preview later changes to an assigned role as a live role edit. | Someone explicitly assigned that role on a matching server or through a cluster/namespace role that selects it. |

Before accepting or updating a template declaration set, activating a recommendation, or withdrawing either source, the built-in primary panel admin opens **GameTemplate proposals** in the server-role library and reviews the effective before/after results for the affected assignments. Show the base, template, permissions and selectors, direct and inherited holders, distinct affected servers, Blocks, access retained from other sources, and coverage of future matching servers. Distinguish matching servers from servers where someone actually gains or loses access. Mark partial or last-known counts. Confirm against the reviewed semantics and current policy. Do not copy grants onto users or server UIDs. An approver may decline a declaration set and keep the previous verified policy. Accepting it applies its entire declared base-addition diff atomically, including removals. The panel admin can explicitly withdraw an active contribution after preview. The next approval must explicitly show any restoration of withdrawn rights as a gain. Installing an update or rolling back the package cannot undo that withdrawal.

A named base assignment follows approved changes on the next decision. A custom grant copied from that base follows its own explicit selection. If an explicitly selected template permission changes meaning, its dependency on the approved mapping still applies. Include all dependent custom grants, optional roles and base mappings in the reapproval preview. Enforce canonical checks, including moderation or power effects behind game buttons, alongside existing selectors, Blocks and platform limits. Installing or updating a package alone cannot grant a declared addition, activate a recommendation or assign an optional role. Changing or removing only an optional recommendation leaves the previously approved selection active while its underlying permissions still verify. If a trusted permission or its command or field disappears or changes meaning, suspend the affected contribution, preserve independently valid grants, and require a fresh review before reactivation. Reusing an ID or rolling back a package cannot silently reinstate a withdrawn approval. Verify the server’s effective definition at dispatch during mixed-version rollouts.
